## 一、先建立直觉

### 1.1 为什么需要“提权”

Linux 把 root 的特权拆成两套东西：**uid 0** 与 **capability 位**。日常需要提权的场景，本质都是
“某个操作要求 uid 0 或某个 capability，而发起者没有”：

| 场景 | 真正需要的东西 | 不提权会怎样 |
|---|---|---|
| 普通用户改自己的密码（`passwd`） | 写 `/etc/shadow`（mode 640 root:shadow） | `EACCES` |
| 非 root 进程监听 80 端口（nginx） | `CAP_NET_BIND_SERVICE` 或 `ip_unprivileged_port_start=0` | `EACCES` |
| `ping` 构造 ICMP 原始套接字 | `CAP_NET_RAW` | `socket: Operation not permitted` |
| 普通用户挂载 U 盘（`mount`） | uid 0 + 内核 mount 权限（+ 策略） | `EPERM` |
| `sudo` 执行一条管理命令 | 目标用户身份 + 完整 capability 集 | 拒绝 |

验证：上表前两条在 07/08 章有完整复现；`ping` 在容器默认 cap 下可用（Docker 默认含 `cap_net_raw`，
见 1.5 的 `capsh --print`），宿主上是否可用取决于发行版是否给 `ping` 设了文件 capability。

### 1.2 四种提权路径总表

| 路径 | 谁在“授予” | 授予的东西 | 触发方式 | 本章位置 |
|---|---|---|---|---|
| **setuid 二进制** | 文件属主（通常 root） | euid=属主，saved=euid；若属主是 root，P/E 获得 `Bounding` 内全部 cap | 执行带 SUID 位的可执行文件 | 2.1 |
| **文件 capability** | 文件 xattr `security.capability` | 只授予列出的 capability（进 P，按 e 标志进 E） | 执行设了 cap 的文件 | 2.2 |
| **sudo** | sudoers 规则 | 以目标用户（默认 root）身份启动**新进程** | `sudo` 命令 + 认证 | 2.3 |
| **docker.sock** | dockerd（root 运行） | 等于宿主机 root 的 API 访问权 | 能读写 socket 的用户（`docker` 组） | 只点到，详见 [07-Docker用户与权限实战](07-Docker用户与权限实战.md) |

前两种是**内核在 execve 时自动完成**的提权；后两种是**一个已存在的特权进程替你做事**。
这个区别决定了它们能否被 `no_new_privs`/`nosuid` 拦住：

- SUID / 文件 capability：内核在 exec 时决定，`no_new_privs` 与 `nosuid` 直接让它失效；
- sudo / docker.sock：特权进程 fork+exec 新进程，`no_new_privs` 管不到（它只约束当前进程树）。

验证：`no_new_privs` 让 SUID 失效见 2.1；`sudo` 在宿主被 `no_new_privs` 拦住是因为
**宿主这个 shell 本身**带 `NoNewPrivs: 1`（`sudo` 需要 exec 一个 setuid-root 程序，被内核忽略 SUID 位），
并非 sudoers 配置问题（04 章 2.1 有 `/proc/self/status` 输出）。

```text
                  ┌─────────────────────────────────────────────┐
  普通进程 ──────▶│ execve(2) 时的内核决定                      │
  (uid=1000)      │  setuid bit   → euid = 文件属主             │
                  │  file caps    → P/E 并入列出的 capability   │
                  │  no_new_privs / nosuid → 忽略上面两项       │
                  └─────────────────────────────────────────────┘
  普通进程 ──────▶ sudo（setuid root 程序）──▶ 认证 ──▶ fork+exec 目标命令（uid=0）
  普通进程 ──────▶ docker.sock ──▶ dockerd(root) ──▶ 以 root 启动容器
```

图：四条路径。上面一条是“内核改凭证”，下面两条是“特权程序代劳”，
最下面一条（docker.sock）实际是“把 root 的 API 交给你”，详见 07 章。

### 1.3 提权改的到底是哪几个字段

| 路径 | ruid | euid | saved | P/E（capability） | 环境变量 |
|---|---|---|---|---|---|
| SUID root 程序 | 不变（1000） | **0** | **0** | 变为 `Bounding` 内全部 cap | 被清理（secure-execution） |
| 文件 capability | 不变 | 不变（1000） | 不变 | 只并入文件列出的 cap | 不变 |
| sudo | **目标用户**（默认 0） | 目标用户 | 目标用户 | 目标用户的（通常全量，受 `Bounding` 限制） | 按 `env_reset` 重置 |
| docker.sock | 不变 | 不变 | 不变 | 不变（但能指挥 root 做任何事） | 不变 |

验证：前两行在容器内用 `uidinfo`/`capstat` 实测（2.1、2.2）；sudo 行用 `sudo -n /usr/bin/id`
看到 `uid=0(root) gid=0(root) groups=0(root)`（2.3）；docker.sock 行见 07 章。

“SUID 程序会拿到 `Bounding` 内全部 cap”这条常被忽略：容器里 SUID root 程序的 `CapEff`
是 Docker 默认的 `a80425fb`，而不是“全部 41 个 cap”（2.2 实测）。

### 1.4 降权为什么比提权难

提权只需要一个文件属性或一条规则；降权要在**一个进程内把“已经是 root”的状态安全地交出去**，
失败点有四个：

1. 顺序：`setgroups` / `setgid` 必须在 `setuid` **之前**，否则失去 `CAP_SETGID` 后改不了组（2.5 实测）；
2. capability：从 uid 0 切到非 0 时，内核会清空 P/E/A（2.5 实测），但**如果保留 saved uid 0**，
   程序还能用 `seteuid(0)` 涨回来；
3. 新特权：降权后要防止 exec 再通过 SUID/文件 cap 涨权，需要 `PR_SET_NO_NEW_PRIVS`；
4. 继承与边界：子进程会继承 capability 的 `Bounding`、`Ambient`，要把它们一起清掉。

### 1.5 本机限制与容器底座

宿主（本会话）做不了提权实验，原因与替代：

| 想验证 | 宿主结果 | 替代 |
|---|---|---|
| `sudo` | `sudo: 已设置“no new privileges”标志，它阻止 sudo 以 root 身份运行` | 容器内 `su alice -c "sudo -n ..."` |
| SUID 提权 | `/home` 挂载 `nosuid`，且没有 root 属主可执行文件 | 容器 overlay 上做 |
| `getcap/setcap/capsh` | 未安装 | 容器内 `apt-get install libcap2-bin` |
| `useradd` | 未安装 | 容器内 `useradd` |


## 二、机制与实测

### 2.1 SUID 二进制：内核在 exec 时换 euid

#### 规则

当执行一个带 setuid 位的**可执行文件**时：

- `euid = 文件属主`，`saved uid = 新的 euid`；ruid 不变；
- 若文件属主是 root，进程在 exec 后获得 `Bounding` 集内的全部 capability（见 2.2 的 root 特殊规则）；
- 程序可以用 `seteuid()` 在 ruid 与 saved uid 之间来回切，这就是“临时提权再降权”的经典写法；
- 脚本上的 setuid 位被**忽略**（2.1.3）。

`来源：man 2 execve`（“If the set-user-ID bit is set ... effective user ID is changed to that of the
owner”）、`来源：man 7 credentials`（saved set-user-ID 的用途）。

#### 真实例子：`passwd`、`su`、`mount`

```text
# 容器内
-rwsr-xr-x 1 root root  72072 Jul 31 15:34 /usr/bin/mount
-rwsr-xr-x 1 root root  18816 Jul 31 15:34 /usr/bin/newgrp
-rwsr-xr-x 1 root root 118168 Apr 19  2025 /usr/bin/passwd
-rwsr-xr-x 1 root root  84360 Jul 31 15:34 /usr/bin/su
```

验证：容器内 `ls -l /usr/bin/passwd /usr/bin/su /usr/bin/mount /usr/bin/newgrp`。

`passwd` 是最干净的演示：alice 读不了 `/etc/shadow`，但 `passwd -S` 可以，因为 `passwd`
以 euid 0 运行、由它代读代写：

```text
# 容器内
$ ls -l /etc/shadow
-rw-r----- 1 root shadow 526 Oct 18 01:45 /etc/shadow
$ su alice -c "cat /etc/shadow"
cat: /etc/shadow: Permission denied
$ su alice -c "passwd -S"
alice L 2026-10-18 0 99999 7 -1
```

验证：上述三条容器内命令。`passwd -S` 输出的字段含义（锁定状态/最后修改日/期限）见
[02-用户与组数据库](02-用户与组数据库.md)，这里只关心“alice 自己没有读权限，`passwd` 有”。

#### 程序怎么“临时提权再降回”

容器内 `suidrecover`（root 属主、4755）演示：

```text
# 容器内：alice 执行 SUID root 程序
after exec: real=1000 effective=0 saved=0
after seteuid(real): real=1000 effective=1000 saved=0
seteuid(0) again: real=1000 effective=0 saved=0
```

验证：容器内 `su alice -c /usr/local/bin/suidrecover`。
读法：exec 后 euid=0；`seteuid(1000)` 把自己降回普通用户，但 saved uid 仍是 0；
再 `seteuid(0)` 又恢复 root。这就是 `passwd` 这类程序“只在写 shadow 的几行代码里是 root”的原理。

安全推论：**只要 saved uid 还是 0，程序被攻破就还能拿回 root**。所以真正的降权必须连
saved uid 一起放弃：从 root 调用 `setuid(target)` 会同时设置 real/effective/saved 三个 ID（2.5）。

#### 为什么 SUID 脚本无效

```text
# 容器内
$ ls -l /usr/local/bin/suidscript
-rwsr-xr-x 1 root root 13 Oct 18 01:40 /usr/local/bin/suidscript
$ su alice -c "/usr/local/bin/suidscript"
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)
```

验证：上述容器内命令。原因是内核执行脚本时实际 exec 的是解释器（`/bin/sh`），
setuid 位作用在“被忽略的脚本文件”上；`来源：man 2 execve`（Interpreter scripts 一节）。
同样地，脚本上的文件 capability 也会被忽略（2.2 实测）。

#### 为什么挂载 `nosuid` 会让它失效

宿主 `/home` 的挂载选项（04 章 2.5 有完整 `findmnt` 输出）：

```text
TARGET       SOURCE                                FSTYPE OPTIONS
...          /dev/mapper/demo--vg-root[...] ext4   rw,nosuid,nodev,relatime,errors=remount-ro
```

验证：宿主 `findmnt -T "$HOME" -o TARGET,SOURCE,FSTYPE,OPTIONS`；`nosuid` 即 MS_NOSUID。

容器内用 `--tmpfs /x:nosuid,exec` 做对照实验：同一份二进制、同样的 `-rwsr-xr-x root root`，
在 `nosuid` 挂载点上 euid 不变，在普通挂载点上 euid 变 0：

```text
# 容器内
TARGET FSTYPE OPTIONS
/x     tmpfs  rw,nosuid,nodev,relatime,size=10240k,inode64

$ su alice -c "/x/uidinfo"
real=1000 effective=1000 saved=1000 | gid real=1000 eff=1000 saved=1000

$ su alice -c "/usr/local/bin/uidinfo"
real=1000 effective=0 saved=0 | gid real=1000 eff=1000 saved=1000
```

验证：`docker run --rm --tmpfs /x:nosuid,exec,size=10m -v "$PWD/.tmp/bin":/b:ro ...`；
两个文件都是 `chown root:root; chmod 4755`。`来源：man 2 execve`（nosuid 时忽略 SUID/SGID 位与文件 cap）。

#### 为什么 `no_new_privs` 会让它失效

```text
# 容器内
$ su alice -c "/usr/local/bin/uidinfo"
real=1000 effective=0 saved=0 | ...
read /root/secret.txt: OK -> TOP-SECRET
$ su alice -c "setpriv --no-new-privs /usr/local/bin/uidinfo"
real=1000 effective=1000 saved=1000 | ...
read /root/secret.txt: DENIED (euid=1000)
```

验证：上述两条容器内命令。`no_new_privs` 是**进程属性**，一旦设置不可撤销、子进程继承，
使 execve 不再授予 SUID/SGID/文件 capability 带来的特权（`来源：man 2 prctl`）。
04 章 2.2 已给出“它会被子进程继承”的实测。

#### SUID 程序拿到多少 capability

SUID root 程序不是“拿到 41 个 cap”，而是拿到**当前 Bounding 集**：

```text
# 容器内：capstat 是 SUID root 程序
uids=1000/0/0
CapInh:	0000000000000000
CapPrm:	00000000a80425fb
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
read /root/secret.txt: OK -> TOP-SECRET
```

验证：容器内 `chown root:root /usr/local/bin/capstat; chmod 4755 /usr/local/bin/capstat;
su alice -c /usr/local/bin/capstat`。`a80425fb` 正是 1.5 节 `capsh --print` 的 Docker 默认 14 cap 位图。

> 结论：**SUID 是“大而全”的提权**（只要 Bounding 里有就给），文件 capability 才是“按需提权”。
> 这也是现代发行版尽量把 SUID root 程序改写成文件 capability 的原因（2.2 对比）。

### 2.2 文件 capability：按需授予

#### 五集合（P/E/I/B/A）

| 集合 | 全称 | 含义 | 谁能改 | 典型用途 |
|---|---|---|---|---|
| P | Permitted | 进程**最多可以拥有**的 cap，是 E 的上限 | capset、exec 规则 | 拿到后可按需启用 |
| E | Effective | **内核检查时真正看**的 cap | capset、exec 的 `F(effective)` | 程序执行特权操作的那一刻 |
| I | Inheritable | 跨 execve 保留的“种子”，与文件 `F(inheritable)` 相与 | capset（受 B 限制） | 需要把 cap 传给子进程 |
| B | Bounding | 进程能拥有的 cap 上限；**exec 时与文件 permitted 相与** | `PR_CAPBSET_DROP`（不可恢复） | 守护进程自我设限 |
| A | Ambient | 非特权进程跨 execve 保留的 cap（Linux 4.3+） | `PR_CAP_AMBIENT_RAISE` | 非 root 服务保留 `NET_BIND_SERVICE` |

`来源：man 7 capabilities`（Capabilities 一节的五套集合定义；Ambient 的规则见同页 Ambient capabilities）。

#### 文件上的三个标志：e / i / p

`setcap` 的 `=ep`、`=p`、`=eip` 是三个标志位：

| 标志 | 名字 | 作用 |
|---|---|---|
| `p` | Permitted | 该 cap 进入进程的 P（再与 `P(bounding)` 相与） |
| `i` | Inheritable | 该 cap 进入文件的 `F(inheritable)`，与进程 I 相与后进 P |
| `e` | Effective | 单个开关位：置 1 时，exec 后新 P 全部进 E；置 0 时只有 Ambient 进 E |

`来源：man 7 capabilities`（File capabilities 一节：Effective 不是集合，而是一个 bit）。

#### execve 的转换公式

`来源：man 7 capabilities`（Transformation of capabilities during execve），原文公式：

```text
P'(ambient)     = (file is privileged) ? 0 : P(ambient)

P'(permitted)   = (P(inheritable) & F(inheritable)) |
                  (F(permitted) & P(bounding)) | P'(ambient)

P'(effective)   = F(effective) ? P'(permitted) : P'(ambient)

P'(inheritable) = P(inheritable)          [即不变]

P'(bounding)    = P(bounding)             [即不变]
```

其中“privileged file”指**带 capability 或带 setuid/setgid 位**的文件；带文件 cap 的可执行文件
即使没有 setuid 位，在执行时也会清空 Ambient。

逐项解释：

- `F(permitted) & P(bounding)`：文件 permitted 必须与进程 Bounding 相与——**Bounding 是硬上限**；
- `P(inheritable) & F(inheritable)`：只有“进程 I”和“文件 i”同时有的 cap 才能通过继承进入 P；
- `P'(ambient)`：Ambient 直接进 P，并在 `F(effective)=0` 时也进 E（这就是 Ambient 的意义）；
- `P'(effective)`：**只看文件 e 标志**。所以 `setcap ...=p` 之后 `CapPrm` 有、`CapEff` 没有，
  程序必须自己 `capset` 启用才能用。

root 的特殊规则（同一 man 页）：当进程 ruid 或 euid 为 0，或执行 setuid-root 程序时，
文件 I/P 集合被“当作全 1”，公式化简为：

```text
P'(permitted) = P(inheritable) | P(bounding)
P'(effective) = P'(permitted)
```

这正是 2.1 中“SUID root 程序拿到 Bounding 内全部 cap”的来源。

#### 公式的逐条实测

容器内 `capstat`（打印 `/proc/self/status` 的 Cap 字段并尝试读 root-only 文件），
文件 cap 由 `setcap` 设置：

| `setcap` 写法 | `CapInh` | `CapPrm` | `CapEff` | 读 `/root/secret.txt` |
|---|---|---|---|---|
| `cap_dac_override=ep` | 0 | `...2` | `...2` | OK |
| `cap_dac_override=p` | 0 | `...2` | `0` | DENIED |
| `cap_dac_override=eip` | 0 | `...2` | `...2` | OK |
| `=ep` + `no_new_privs` | 0 | 0 | 0 | DENIED |
| `=ep` + Bounding 去掉该 cap | — | （exec 直接 EPERM） | — | — |
| Ambient（`setpriv --ambient-caps`） | `...2` | `...2` | `...2` | OK |

验证：容器内分别执行 `setcap ... /usr/local/bin/capstat` 与 `su alice -c /usr/local/bin/capstat`，
输出如下（完整）：

```text
# =ep
uids=1000/1000/1000
CapInh:	0000000000000000
CapPrm:	0000000000000002
CapEff:	0000000000000002
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
read /root/secret.txt: OK -> TOP-SECRET

# =p（只有 permitted，没有 effective）
CapPrm:	0000000000000002
CapEff:	0000000000000000
read /root/secret.txt: DENIED

# =eip
CapPrm:	0000000000000002
CapEff:	0000000000000002
read /root/secret.txt: OK -> TOP-SECRET

# =ep + no_new_privs
CapPrm:	0000000000000000
CapEff:	0000000000000000
read /root/secret.txt: DENIED

# Ambient（setpriv --inh-caps=+dac_override --ambient-caps=+dac_override）
CapInh:	0000000000000002
CapPrm:	0000000000000002
CapEff:	0000000000000002
CapAmb:	0000000000000002
read /root/secret.txt: OK -> TOP-SECRET
```

验证：以上五行输出均来自容器内 `capstat`；`...2` 即 `CAP_DAC_OVERRIDE`（bit 1，值 2）。

注意 `=eip` 的 `CapInh` 仍是 0：公式里 `P'(inheritable) = P(inheritable)`，**进程原本 I 为空，
文件 i 标志不会改变进程 I**。要利用 i 标志，得先有一个带 I 的父进程（例如 `capsh --inh=...`）。

#### Bounding 的两条硬规则

`来源：man 7 capabilities`（Capability bounding set）：

1. execve 时 `F(permitted) & P(bounding)` 决定 P ——所以 Bounding 里没有的 cap，文件 cap 也授不了；
2. Bounding 是进程**添加 I 集合**的上限：不在 B 里的 cap 不能加入 I。

实测（容器内，用 `capsh --drop=cap_dac_override` 先清掉 Bounding 中的该位）：

```text
# 文件 cap =p（没有 e 标志）：不会被 capability-dumb 检查拦，exec 成功
$ setcap cap_dac_override=p /usr/local/bin/capstat
$ capsh --drop=cap_dac_override -- -c "grep -E '^(CapBnd|CapEff)' /proc/self/status; /usr/local/bin/capstat"
CapBnd:	00000000a80425f9
CapEff:	00000000a80425f9
uids=0/0/0
CapPrm:	00000000a80425f9
CapEff:	00000000a80425f9
read /root/secret.txt: OK -> TOP-SECRET

# 文件 cap =ep（带 e 标志）：execve 直接 EPERM
$ setcap cap_dac_override=ep /usr/local/bin/capstat
$ capsh --drop=cap_dac_override -- -c "/usr/local/bin/capstat"
/bin/bash: line 1: /usr/local/bin/capstat: Operation not permitted
```

验证：上述两条容器内命令。第一段里读 `/root/secret.txt` 成功是因为 `capsh` 以 **root(uid 0)** 运行、
文件属主也是 root（属主读权限），**不是**被 Bounding 截掉的 `CAP_DAC_OVERRIDE` 生效；
要看的是 `CapBnd/CapPrm` 里该 bit 已经消失。第二个现象是 man 页的 **capability-dumb binary 安全检查**：
带 e 标志的文件在执行时，若进程没有获得文件 permitted 里的全部 cap（这里被 Bounding 截掉），
execve 返回 `EPERM`，防止“程序以为自己有特权、实际没有”导致的降权漏洞
（`来源：man 7 capabilities`，Safety checking for capability-dumb binaries）。

#### Ambient 解决什么问题

场景：非 root 服务需要监听 80（`CAP_NET_BIND_SERVICE`），但不想整个进程是 root。
把 cap 放进 **I** 不够——I 只有在文件也有 i 标志时才转入 P；把 cap 放进文件 p 又要求可执行文件本身设过 cap。
**Ambient 让“进程自己带着 cap 跨 execve 走”**：

- 前提：cap 必须在进程的 P 和 I 里，才能 `PR_CAP_AMBIENT_RAISE`；
- exec 后 Ambient 进 P，且当文件 e 标志为 0 时也进 E；
- 执行 privileged file（带 cap 或 setuid/setgid）会**清空** Ambient（`来源：man 7 capabilities`）。

容器内实测（`setpriv` 与 `capsh` 都能设置）：

```text
# 容器内：以 root 启动，设置 I+Ambient，再切到 alice(1000) 执行
$ setpriv --reuid=1000 --regid=1000 --clear-groups \
    --inh-caps=+dac_override --ambient-caps=+dac_override /usr/local/bin/capstat
uids=1000/1000/1000
CapInh:	0000000000000002
CapPrm:	0000000000000002
CapEff:	0000000000000002
CapAmb:	0000000000000002
read /root/secret.txt: OK -> TOP-SECRET
```

验证：上述容器内命令（`capstat` 未设任何文件 cap）。同样的结果也可以用
`capsh --keep=1 --uid=1000 --inh=cap_dac_override --addamb=cap_dac_override -- -c ...` 得到。

#### `setcap` / `getcap` 用法

```bash
setcap cap_dac_override=ep /usr/local/bin/capstat   # 写入 security.capability xattr
getcap /usr/local/bin/capstat                       # 查看
getcap -r /usr/local/bin                            # 递归审计
setcap -r /usr/local/bin/capstat                    # 移除文件上的全部 cap
getcap -r / 2>/dev/null                             # 全盘审计（10 章）
```

```text
# 容器内
$ getcap -r /usr/local/bin
/usr/local/bin/capstat cap_dac_override=ep
```

验证：上述 `getcap -r` 输出为容器内实测。写入该 xattr 需要 `CAP_SETFCAP`；普通用户不能给自己
的可执行文件加 cap，这本身就是“提权”的一部分（`来源：man 7 capabilities`，File capabilities）。
`getcap -r /` 的完整审计清单见 [10-账户安全基线与审计](10-账户安全基线与审计.md)。

#### 常用 capability 与风险

| capability | 能做什么 | 为什么危险 | 最小化建议 |
|---|---|---|---|
| `CAP_NET_BIND_SERVICE` | bind < 1024 端口 | 可冒充低端口服务 | 非 root 服务的首选 cap |
| `CAP_DAC_OVERRIDE` | 绕过文件读/写/执行权限检查 | **等于文件系统上的 root**（读 shadow、改任何文件） | 几乎不该给 |
| `CAP_DAC_READ_SEARCH` | 绕过读/目录搜索 | 可读全部文件（含 shadow） | 只给需要全盘读的工具 |
| `CAP_SETUID` / `CAP_SETGID` | 任意切 uid/gid | 直接变成任意用户 | 只给 su/sudo 类程序 |
| `CAP_SETPCAP` | 修改自身 cap 集、Bounding | 可重新分配权限 | 守护进程启动后应丢弃 |
| `CAP_SYS_ADMIN` | mount、namespace、大量管理操作 | **“新 root”**，容器逃逸面大 | 禁止；用具体 cap 替代 |
| `CAP_SYS_PTRACE` | ptrace 任意进程 | 可注入/读取任意进程内存 | 仅在需要调试时临时给 |
| `CAP_NET_RAW` | 原始套接字 | 可伪造/嗅探网络包 | 只给 ping 类工具 |
| `CAP_CHOWN` | 任意 chown | 可把文件送给自己 | 文件服务需要时再给 |
| `CAP_SETFCAP` | 给文件写 capability xattr | 可制造提权文件 | 只给包管理器 |

表中的“能做/危险”依据 `来源：man 7 capabilities` 的 Capabilities list 一节；
`CAP_SYS_ADMIN` 在容器默认集中**不存在**（1.5 的 `capsh --print` 可验证）。

### 2.3 sudo：由特权程序代劳

#### sudoers 语法

`来源：man 5 sudoers`（SUDOERS FILE FORMAT），核心产生式：

```text
User_Spec    ::= User_List Host_List '=' Cmnd_Spec_List
Cmnd_Spec    ::= Runas_Spec? Option_Spec* (Tag_Spec ':')* Cmnd
Runas_Spec   ::= '(' Runas_List? (':' Runas_List)? ')'
```

翻译成一句话：**谁 在哪些主机 = (以谁:哪个组) 可以运行什么命令**。
`Runas_Spec` 省略时默认以 root（`runas_default`）运行；`Tag_Spec` 里最常用的是 `NOPASSWD:`。

| 规则示例 | 含义 | 验证 |
|---|---|---|
| `alice ALL=(ALL) NOPASSWD: /usr/bin/id` | alice 在任意主机可免密以任意用户跑 `id` | 2.3 实测 |
| `alice ALL=(root) NOPASSWD: /usr/bin/id` | 只能以 root 跑 `id`；`-u bob` 被拒 | 2.3 实测 |
| `%devs ALL=(ALL) NOPASSWD: /usr/bin/whoami` | `devs` 组全体成员 | 2.3 实测 |
| `alice ALL=(root:devs) NOPASSWD: /usr/bin/id` | 以 root、组 devs 运行 | 2.3 实测 |
| `Defaults secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"` | 覆盖 PATH | 2.3 实测 |
| `Defaults env_reset`（默认开） | 清理环境变量 | 2.3 实测 |

#### 三条规则 + 运行结果（容器内实测）

```text

/etc/sudoers.d/demo: parsed OK

# 越权：差一个命令就不行

```

验证：上述容器内命令。注意“越权”的报错是 `a password is required` 而不是“not allowed”：
sudo 对未授权命令会先尝试认证（这里 `-n` 禁交互，所以直接失败）。

```text

$ su alice -c "sudo -n /usr/bin/whoami"

```

验证：上述容器内命令（alice 在 `devs` 组，`usermod -aG devs alice`）。组规则用 `%组名`。

### 2.4 `su` / `runuser` / `setpriv` 对比

| 维度 | `su`（util-linux） | `runuser`（util-linux） | `setpriv`（util-linux） |
|---|---|---|---|
| 认证 | 目标用户密码（root 调用时免密） | **不认证**，仅 root 可用 | 不认证，**只有 root 能切 uid** |
| PAM | 使用 PAM（会话、limits） | 用 PAM 的会话部分，不做认证 | 不涉及 PAM |
| 环境 | 默认重置（`su -` 更彻底） | 默认重置 | **不重置**（沿用调用者环境） |
| 辅助组 | 按目标用户初始化 | 按目标用户初始化 | **必须显式指定** `--clear-groups`/`--init-groups` |
| capability | 按目标用户凭证重算 | 同 su | 可精确控制 I/A/B（2.2 用过） |
| 典型用途 | 交互式切用户 | 脚本/服务里以其他用户跑命令 | 精细降权/设 cap |

容器内实测：

```text
# su：初始化 alice 的组与环境
$ su alice -c "id; echo HOME=$HOME"
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)
HOME=/home/alice

# runuser：同样初始化组
$ runuser -u alice -- sh -c "id; echo HOME=$HOME"
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)
HOME=/home/alice

# setpriv：必须指定组策略，否则报错
$ setpriv --reuid=1000 --regid=1000 id
setpriv: --[re]gid requires --keep-groups, --clear-groups, --init-groups, or --groups

$ setpriv --reuid=1000 --regid=1000 --clear-groups id
uid=1000(alice) gid=1000(alice) groups=1000(alice)

$ setpriv --reuid=1000 --regid=1000 --init-groups id
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)

# setpriv 不重置环境：HOME 仍是 root 的
$ setpriv --reuid=1000 --regid=1000 --init-groups env | grep -E '^(HOME|PATH)='
HOME=/root
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# alice 想 su 到 bob：没有密码就失败
$ su alice -c "su bob -c id"
Password: su: Authentication failure
```

验证：上述六组容器内命令。`setpriv` 的环境不重置是设计使然：它只做“凭证/命名空间”层面的设置，
不模拟登录（`来源：man 1 setpriv`）；`su`/`runuser` 的 PAM 与会话行为见 `man 1 su`、`man 1 runuser`
（本机宿主没有这些手册页，在容器内核对）。

### 2.5 降权：正确顺序与实测

#### 目标

一个从 root 启动的守护进程（nginx、sshd、自定义服务）要在完成特权初始化后，
把进程变成“普通用户 + 空 capability + 不可再提权”：

```text
1. setgroups(0, NULL)        # 先清辅助组（需要 CAP_SETGID）
2. setgid(target_gid)        # 再改 gid（需要 CAP_SETGID）
3. setuid(target_uid)        # 最后改 uid（改完 P/E/A 被内核清空）
4. prctl(PR_SET_NO_NEW_PRIVS, 1)   # 禁止后续 exec 通过 SUID/文件 cap 涨权
5. 清空 Bounding（可选但推荐）     # PR_CAPBSET_DROP 逐个丢，进程内不可恢复
```

为什么是“组 → 用户”而不是反过来：`setgid`/`setgroups` 需要 `CAP_SETGID`，
而 uid 变成非 0 的瞬间内核会清空 capability。反序就会卡在第二步（实测）。

#### 正确顺序（容器内实测）

```text
# 容器内：droporder 以 root 启动
start                  uid=0/0/0 gid=0/0/0
after setgid           uid=0/0/0 gid=1000/1000/1000
after setuid           uid=1000/1000/1000 gid=1000/1000/1000
late setgid(0): Operation not permitted
read /root/secret.txt: Permission denied
```

验证：容器内 `chown root:root /b/droporder; /b/droporder`
（`/b` 是只读挂载的实验目录）。注意最后两行：降权后再 `setgid(0)` 失败、读 root 文件失败。

#### 反序（错误示范）

```text
# 容器内：dropwrong 先 setuid 再 setgid
start                          uid=0/0/0 gid=0/0/0
setgroups(0): ok
setuid(1000): ok
after setuid                   uid=1000/1000/1000 gid=0/0/0
setgid(1000): Operation not permitted
```

验证：容器内 `/b/dropwrong`。此时进程是“uid 1000、gid 0”的畸形状态：
文件权限按 uid 1000 判定，但 gid 还是 root——既没有达到降权目的，也改不回目标组。

#### capability 什么时候被清空

```text
# 容器内：dropcaps 打印 CapPrm / CapEff
start          CapPrm=00000000a80425fb CapEff=00000000a80425fb
after setgid   CapPrm=00000000a80425fb CapEff=00000000a80425fb
after setuid   CapPrm=0000000000000000 CapEff=0000000000000000
```

验证：容器内 `/b/dropcaps`（root 启动，依次 `setgroups`、`setgid`、`setuid`）。
`来源：man 7 capabilities`（Effect of user ID changes）：当 ruid/euid/suid 中原本有 0，
且改动后全部非 0 时，P/E/A 全部清空。**所以“setuid 之后 capability 自动没了”是对的，
但仍建议显式清 Bounding（第 5 步）**：它是纵深防御，且必须放在 `setuid` 之前（下一节）。

#### 代码骨架

```c
/* 以 root 启动的守护进程：完成 bind/open 等特权操作后降权 */
if (setgroups(0, NULL) != 0)                 fail("setgroups");
if (setgid(target_gid) != 0)                 fail("setgid");
if (setuid(target_uid) != 0)                 fail("setuid");
if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0))  fail("no_new_privs");
/* 想让 Bounding 也变空：逐个 prctl(PR_CAPBSET_DROP, cap) —— 需要 CAP_SETPCAP，
   所以要在 setuid 之前做；setuid 后没有 CAP_SETPCAP，只能通过 no_new_privs + 空 P 兜底。 */
```

关键点：**`PR_CAPBSET_DROP` 需要 `CAP_SETPCAP`，必须在 `setuid` 之前执行**。
一个常见错误是把 Bounding 清理写在 `setuid` 之后，此时已经无力回天（`来源：man 7 capabilities`；
本机未单独实测这一步，标注未验证）。

#### 用 `setpriv` 一步到位（适合脚本/容器启动）

```bash
# 容器内实测：清组、切用户、加 ambient、设置 no_new_privs
setpriv --reuid=1000 --regid=1000 --clear-groups \
        --inh-caps=+dac_override --ambient-caps=+dac_override \
        --no-new-privs /usr/local/bin/capstat
```

验证：2.2 节最后一段的容器内输出（`CapAmb=...2`、读文件成功）。
注意 `--no-new-privs` 与“文件 cap 提权”是互斥的：设了它，之后 exec 的 SUID/文件 cap 全部失效。

#### 真实服务：nginx 的 master/worker

```text
# 容器内（nginx:1.20-alpine，默认启动）
$ id nginx
uid=101(nginx) gid=101(nginx) groups=101(nginx),101(nginx)
$ ps -o pid,ppid,user,args
PID   PPID  USER     COMMAND
    1     0 root     nginx: master process nginx -g daemon off;
   31     1 nginx    nginx: worker process
   32     1 nginx    nginx: worker process
   ...   ...  ...      ...
```

验证：`docker run -d --name c nginx:1.20-alpine` 后 `docker exec c sh -c 'id nginx; ps -o pid,ppid,user,args'`。
master 保持 root（要 bind 80、打开日志/pid），worker 以 nginx(101) 运行；worker 不需要
`CAP_NET_BIND_SERVICE`，因为 listen socket 已由 master 打开并继承。完整权限矩阵见
[08-Nginx用户与权限实战](08-Nginx用户与权限实战.md)。

`sshd` 的 privilege separation 同理（父进程 root 监听 22，子进程降权处理连接），
但本机未安装 sshd，**未实测**。

### 2.6 systemd 服务侧：把降权写进 unit

`来源：man 5 systemd.exec`（本机无 systemd，未实测；以下选项语义来自该手册页）：

| 选项 | 作用 | 对应本章机制 |
|---|---|---|
| `User=` / `Group=` | exec 前切换到目标用户/组 | `setgid`/`setuid` |
| `SupplementaryGroups=` | 设置辅助组 | `setgroups` |
| `NoNewPrivileges=` | 置位 no_new_privs，后代不能再通过 exec 涨权 | 2.2/2.5 |
| `CapabilityBoundingSet=` | 设置 Bounding（列表外的 cap 全部移除；`~` 前缀表示取反） | 2.2 的 B |
| `AmbientCapabilities=` | 给非 root 服务保留 cap；会自动加 `keep-caps` securebit | 2.2 的 A |
| `SecureBits=` | 设置 securebits（如 `keep-caps`） | 2.5 的“保留 P/E” |
| `DynamicUser=` | 动态分配 61184~65519 的 uid/gid（隐含 NoNewPrivileges 与只读系统盘） | 为一次性服务降权 |

示例（把一个需要绑 80 的非 root 服务写成最小权限）：

```ini
[Service]
User=nginx
Group=nginx
NoNewPrivileges=true
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
```

要点：`CapabilityBoundingSet=` 既限制“能拿到的上限”，也影响 E/P/I（手册原文说它
“also affects the respective capabilities in the effective, permitted and inheritable capability sets”）；
`AmbientCapabilities=` 才是让**非 root** 进程真正拿到该 cap 的开关。
`systemd-analyze capability` 可以列出本机 capability 名（本机未验证该命令）。

## 三、动手验证

本章对应实验：[labs/04-setuid-caps](../labs/04-setuid-caps/)（SUID、no_new_privs、file capability、`CapEff` 位）。

10 条可直接粘贴的命令与观察点：

```bash
# 1) 容器底座：装工具、建用户（后面所有命令复用同一套）
docker run --rm --name learnugroup-c05 -v "$PWD/.tmp/bin":/b:ro debian:13 bash -c '
  apt-get update -qq && apt-get install -y -qq --no-install-recommends sudo libcap2-bin >/dev/null
  groupadd -g 2000 devs; useradd -m -u 1000 -s /bin/bash alice; usermod -aG devs alice
  echo TOP-SECRET > /root/secret.txt; chmod 600 /root/secret.txt'

# 2) SUID：euid 变 0，saved 也是 0
#    容器内：cp /b/uidinfo /usr/local/bin/; chown root:root /usr/local/bin/uidinfo; chmod 4755 /usr/local/bin/uidinfo
#    然后 su alice -c /usr/local/bin/uidinfo

# 3) no_new_privs 让 SUID 失效
#    容器内：su alice -c "setpriv --no-new-privs /usr/local/bin/uidinfo"

# 4) 脚本的 SUID 无效
#    容器内：printf '#!/bin/sh\nid\n' > /usr/local/bin/s; chmod 4755 /usr/local/bin/s; su alice -c /usr/local/bin/s

# 5) 文件 capability：permitted 与 effective 的差别
#    容器内：setcap cap_dac_override=p /usr/local/bin/capstat → CapPrm 有、CapEff 0、读文件失败
#            setcap cap_dac_override=ep /usr/local/bin/capstat → CapEff 有、读文件成功

# 6) Bounding 截断文件 capability（capability-dumb 会 EPERM）
#    容器内：setcap cap_dac_override=ep /usr/local/bin/capstat
#            capsh --drop=cap_dac_override -- -c /usr/local/bin/capstat

# 7) Ambient：非 root 也能带着一个 cap 跨 execve
#    容器内：setpriv --reuid=1000 --regid=1000 --clear-groups \
#              --inh-caps=+dac_override --ambient-caps=+dac_override /usr/local/bin/capstat

# 8) sudo：NOPASSWD 最小授权 + 越权被拒
#    容器内：echo "alice ALL=(ALL) NOPASSWD: /usr/bin/id" > /etc/sudoers.d/demo; chmod 440 /etc/sudoers.d/demo
#            visudo -cf /etc/sudoers.d/demo
#            su alice -c "sudo -n /usr/bin/id"; su alice -c "sudo -n cat /etc/shadow"

# 9) 降权顺序：先组后用户；反序会 EPERM
#    容器内：/b/droporder（正确）与 /b/dropwrong（反序）对比

# 10) 宿主上只读观察：/home 的 nosuid 与当前进程的 no_new_privs
findmnt -T /home -o TARGET,FSTYPE,OPTIONS
grep -E '^(NoNewPrivs|CapEff|CapBnd)' /proc/self/status
```

| 观察点 | 宿主 | 容器 |
|---|---|---|
| 当前凭证、`NoNewPrivs`、`CapEff` | ✅ 只读 | ✅ |
| `/home` 的 `nosuid` | ✅ `findmnt` | ❌ bind mount 不继承该选项（04 章 2.5） |
| SUID 提权 | ❌ 无 root 文件 + nosuid | ✅ |

## 四、常见误解

❌ 「SUID 程序就是“以 root 运行”。」 → ✅ 它只把 **euid/saved** 设为文件属主；ruid 仍是调用者。`uidinfo` 实测 `real=1000 effective=0 saved=0`（2.1）。

❌ 「给 shell 脚本 `chmod 4755` 就能提权。」 → ✅ 内核忽略脚本上的 setuid 位，并以解释器执行；实测 euid 仍是 1000（2.1，`来源：man 2 execve`）。

❌ 「root 属主的 SUID 程序能拿到全部 41 个 capability。」 → ✅ 只能拿到当前 `Bounding` 集内的 cap；容器里 SUID 程序的 `CapEff=00000000a80425fb`（Docker 默认 14 个），2.1 实测。

❌ 「文件 capability 设成 `=p` 就生效了。」 → ✅ `p` 只进 Permitted，`CapEff` 仍为 0，实际特权操作会失败；要生效需 `=ep` 或程序自己 `capset`（2.2 实测）。

❌ 「`Bounding` 只是“理论上的上限”，不影响我执行文件 cap。」 → ✅ execve 时 `F(permitted) & P(bounding)`；Bounding 去掉某 cap 后文件 cap 授不出来，带 e 标志时 execve 直接 `EPERM`（2.2 实测）。

❌ 「Ambient 和 Inheritable 是一回事。」 → ✅ Inheritable 只是“种子”，要配合文件 i 标志才进 P；Ambient 在 exec 后直接进 P，并在文件无 e 标志时进 E，是“非 root 服务保留一个 cap”的正解（2.2）。

❌ 「降权时先 `setuid` 再 `setgid` 没关系。」 → ✅ `setgid` 需要 `CAP_SETGID`，而 `setuid(非0)` 会清空 capability；反序实测 `setgid: Operation not permitted`（2.5）。

❌ 「`sudo` 会把我的环境变量原样带过去。」 → ✅ 默认 `env_reset` + `secure_path`：实测 `FOO` 消失、`PATH` 被替换、`HOME/USER/LOGNAME` 变成目标用户（2.3）。

❌ 「`NOPASSWD` 等于“以后一直免密”。」 → ✅ `NOPASSWD` 是逐条规则的标签；`PASSWD` 规则才涉及 15 分钟时间戳，且本机 sudo 是 tty_tickets（按终端隔离），换一个无 tty 的会话就要重新认证（2.3 实测）。

❌ 「给服务 `User=nginx` 就够了。」 → ✅ 还要看 `NoNewPrivileges=`、`CapabilityBoundingSet=`、`AmbientCapabilities=`；否则进程仍会在 exec 时通过 SUID/文件 cap 获得新特权，或保留不需要的 cap（2.6，`来源：man 5 systemd.exec`）。

## 五、速查表

| 命令 / 配置 | 作用 | 现象 / 判读 |
|---|---|---|
| `chmod 4755 f` + `ls -l` | 设 setuid 位 | `-rwsr-xr-x`；脚本无效 |
| `su alice -c ./prog` | 以 alice 执行，观察 euid | `real=1000 effective=0 saved=0` |
| `setpriv --no-new-privs ./prog` | 禁止 exec 提权 | SUID/文件 cap 失效，euid 不变 |
| `setcap cap_x=ep f` | 给文件加 capability | `getcap f` 显示 `cap_x=ep` |
| `setcap cap_x=p f` | 只进 Permitted | `CapEff=0`，特权操作失败 |
| `capsh --print` | 看 Current/Bounding/Ambient | 容器 root 默认 14 cap |
| `capsh --drop=cap_x -- -c cmd` | 清 Bounding 中的某 cap | 文件 cap 被截断；e 标志时 EPERM |
| `getcap -r /usr/local/bin` | 审计文件 capability | 列出 `文件 cap_x=...` |
| `setpriv --inh-caps=+cap_x --ambient-caps=+cap_x cmd` | 设置 Ambient | `CapAmb` 位出现，跨 exec 保留 |
| `sudo -n cmd` | 非交互执行 | 未授权/需密码时失败 |
| `sudo -l` | 列出规则与 Defaults | 看 `secure_path`、`env_reset` |
| `visudo -cf file` | 检查 sudoers 语法 | `parsed OK` |
| `sudo -u user -g group cmd` | 限制目标身份 | 看 Runas_Spec |
| `su - user` / `runuser -u user -- cmd` | 切用户 | 组/环境按目标用户初始化 |
| `setpriv --reuid --regid --clear-groups` | 精细切身份 | 不重置环境、必须显式组策略 |
| `findmnt -T /home` | 看 nosuid | SUID 在该挂载点失效 |
| `systemctl show -p NoNewPrivileges -p CapabilityBoundingSet svc` | 看服务配置 | 本机无 systemd，未验证 |
