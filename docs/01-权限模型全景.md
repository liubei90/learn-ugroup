## 一、先建立直觉

### 1.1 三个真实现象，一个模型

先看三个看起来很不一样的问题（都是本课程里真实出现过的）：

```text
现象 A：普通用户 cat /etc/shadow
        cat: /etc/shadow: Permission denied

现象 B：把自己加到 docker 组后，普通用户可以
        docker run -v /home/demo:/w -it debian sh
        然后在容器里以 uid=0 读写宿主文件

现象 C：nginx 容器里放一个 600 的 HTML 文件，浏览器访问返回 403，
        但宿主机上 root 明明能读
```

三者的共同点是：**总有一个进程，在某一刻，试图访问某个资源，内核按一套规则放行或拒绝**。
把这句话拆成三个问题：

```text
① 谁在访问？    → 进程的“凭证”（credentials）：uid/gid/capability
② 访问什么？    → 资源的“权限信息”：mode/ACL/capability 文件属性/LSM 标签
③ 规则是什么？  → 内核的检查顺序：属主 → 属组 → other → ACL → capability → LSM
```

> 图：权限问题的三要素。任何一个 `Permission denied` 都能落到这张图的某个节点上。

```text
        ┌──────────────────────────────┐
        │  ① 主体：进程凭证 cred        │
        │  ruid euid suid fsuid         │
        │  rgid egid sgid fsgid + 辅助组│
        │  caps: P/E/I/B/A 五集合       │
        │  no_new_privs / user_ns       │
        └──────────────┬───────────────┘
                       │  发起系统调用 open()/execve()/bind()/...
                       ▼
        ┌──────────────────────────────┐
        │  ③ 规则：内核检查             │
        │  mode 位 → ACL → capability   │
        │  → LSM（AppArmor/SELinux）    │
        │  → 挂载选项/只读/quota        │
        └──────────────┬───────────────┘
                       │  读/写/执行/遍历/绑定
                       ▼
        ┌──────────────────────────────┐
        │  ② 客体：资源权限信息         │
        │  inode: mode uid gid          │
        │  ACL、xattr、security.capability│
        │  socket/端口/设备/IPC 的规则  │
        └──────────────────────────────┘
```

### 1.2 一次 `open()` 的旅程（简化版）

用户执行 `cat /etc/shadow`，内核大致做这些事：

```text
shell 执行 /usr/bin/cat
  └─ cat 进程继承 shell 的凭证：uid=1000, euid=1000, 组=..., caps=空（普通用户）
      └─ cat 调用 open("/etc/shadow", O_RDONLY)
          ├─ 路径解析：/  →  etc  →  shadow
          │   每进入一级目录都需要该目录的 x 位（search 权限）
          ├─ 找到 inode：属主 root(0)、属组 shadow(42)、mode 0640
          ├─ 权限检查：fsuid=1000 既不是 0，也不在 shadow 组
          │   → 用 other 位：---  → 拒绝
          ├─ capability 兜底：进程没有 CAP_DAC_READ_SEARCH → 不放行
          └─ LSM 兜底：AppArmor 也允许，但前面已经失败
      └─ open() 返回 -1，errno = EACCES(13)
  └─ cat 打印 "Permission denied"
```

这个例子里，**uid 检查是第一道门**；如果进程带着 `CAP_DAC_READ_SEARCH`，第一道门会被绕过。
这就是为什么「root 能读」和「普通用户被拒绝」不是魔法，而是两套机制（mode 位 + capability）。

### 1.3 为什么有了 uid 还要 capability

如果所有特权都绑在「uid 等于 0」上，会产生两个问题：

1. **粒度太粗**：nginx 只需要「绑定 80 端口」这一项特权，却必须整个进程以 root 运行；
2. **一旦泄露就是全部**：root 进程被攻破 = 整台机器失守。

Linux 把 root 的特权拆成 ~40 个 capability（`include/uapi/linux/capability.h`），
可以只给进程/C 程序「绑定特权端口」这一项：

```text
# 容器内实测：给一个静态程序只加 cap_dac_override，它就能读 root-only 文件
$ getcap /usr/local/bin/capread
/usr/local/bin/capread cap_dac_override=ep
$ su alice -c "/usr/local/bin/capread"
uid=1000 euid=1000 CapEff=	0000000000000002
read /root/secret.txt: OK -> TOP-SECRET
```

注意 `euid=1000`：**没有变成 root，只是多了 1 个 capability**（`0x2` = CAP_DAC_OVERRIDE）。
这就是「最小权限」的落地方式，也是 05 章的主题。

## 二、把模型拆开

### 2.1 主体：进程的凭证（credentials）

内核用 `struct cred` 表示一个进程的凭证（`来源：/usr/src/linux-headers-6.12.107+deb13-common/include/linux/cred.h`，字段注释原文保留）：

```c
struct cred {
	kuid_t	uid;		/* real UID of the task */
	kgid_t	gid;		/* real GID of the task */
	kuid_t	suid;		/* saved UID of the task */
	kgid_t	sgid;		/* saved GID of the task */
	kuid_t	euid;		/* effective UID of the task */
	kgid_t	egid;		/* effective GID of the task */
	kuid_t	fsuid;		/* UID for VFS ops */
	kgid_t	fsgid;		/* GID for VFS ops */
	kernel_cap_t	cap_inheritable; /* caps our children can inherit */
	kernel_cap_t	cap_permitted;	/* caps we're permitted */
	kernel_cap_t	cap_effective;	/* caps we can actually use */
	kernel_cap_t	cap_bset;	/* capability bounding set */
	kernel_cap_t	cap_ambient;	/* Ambient capability set */
	struct user_namespace *user_ns; /* user_ns the caps and keyrings are relative to. */
	struct group_info *group_info;	/* supplementary groups for euid/fsgid */
	...
};
```

#### 四套 uid，各管什么

| 名称 | 缩写 | 作用 | 典型场景 |
|---|---|---|---|
| 真实用户 ID | ruid | 「谁启动了进程」，用于信号权限、`access(2)`、`/proc` 记账 | `su`/`sudo` 后仍是登录用户 |
| 有效用户 ID | euid | **权限检查真正用的身份** | setuid 程序运行时 euid=文件属主 |
| 保存的用户 ID | suid | 允许进程在 euid 与 ruid 之间切换 | `sudo` 提权后还能降回普通用户 |
| 文件系统用户 ID | fsuid | **VFS 权限检查用的 uid**，通常等于 euid | 文件服务器/NFS 需要临时切换 |

GID 同理：`rgid`/`egid`/`sgid`/`fsgid`，再加一组**辅助组**（supplementary groups，
即 `id` 输出里逗号分隔的那些组）。

> 为什么要四套？以 `passwd` 为例：你以 `demo` 登录（ruid=1000），执行 `/usr/bin/passwd`
> （setuid root）后 euid=0 才能写 `/etc/shadow`；写完后程序可以把 euid 降回 1000，
> 保留 suid=0 以便需要时再提权。`ruid/euid/suid` 是 POSIX 为「临时提权再降权」设计的。

#### 怎么观察

```bash
id
grep -E '^(Uid|Gid|Groups|CapInh|CapPrm|CapEff|CapBnd|CapAmb|NoNewPrivs)' /proc/self/status
ps -o pid,user,euser,ruid,euid,suid,args -p $$
```

本机（宿主）实测：

```text
$ grep -E '^(Uid|Gid|Groups|CapEff|CapBnd|NoNewPrivs)' /proc/self/status
Uid:	1000	1000	1000	1000
Gid:	1000	1000	1000	1000
Groups:	65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 1000
CapEff:	0000000000000000
CapBnd:	0000000000000000
NoNewPrivs:	1
```

读法：

- `Uid:` 这一行有 **4 列**：real / effective / saved / fsuid；`Gid:` 同理；
- `Groups:` 是辅助组列表；本机出现多个 65534 是沙箱映射的副产物（见 06 章「溢出 UID」）；
- `CapEff: 0` 表示这个进程**没有任何生效的 capability**——本会话是受限沙箱；
- `NoNewPrivs: 1` 表示 `execve` 时不允许再获得新特权（setuid 位、文件 capability 都失效，05 章详述）。

再看 `ps` 的字段（本机实测）：

```text
$ ps -o pid,user,group,euser,egroup,ruid,euid,suid,rgid,egid,sgid -p $$
  PID USER     GROUP    EUSER    EGROUP    RUID  EUID  SUID  RGID  EGID  SGID
    2 demo   demo   demo   demo    1000  1000  1000  1000  1000  1000
```

> 注意 `ps` 的 `suid` 列是 **saved UID**，不是「setuid 位」；这是排障时最容易看错的字段之一。

#### capability 的五个集合

| 集合 | 含义 | 一句话记忆 |
|---|---|---|
| Permitted (P) | 进程**最多可以拥有**的 capability | 「有这个上限，才能用」 |
| Effective (E) | **当前实际生效**的 capability | 内核检查的就是它 |
| Inheritable (I) | 可以被**子进程继承**的 capability | 跨 execve 保留的「种子」 |
| Bounding (B) | 进程能拥有的 capability **上限** | 降权后不能通过 execve 涨回来 |
| Ambient (A) | 非特权进程也想**跨 execve 保留**的 cap | 非 root 服务也能「带着 cap 跑」 |

> 容器里实测的 root 默认集合（Docker 默认 14 个 cap）：

```text
# 容器内
$ capsh --print | grep -E '^(Current|Bounding)'
Current: cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap=ep
Bounding set =cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap
```

这就是为什么「容器里的 root」和「宿主机的 root」不是一回事：**容器 root 默认少了
`CAP_SYS_ADMIN`、`CAP_SYS_MODULE`、`CAP_NET_ADMIN` 等约 27 个 capability**（07 章详述）。

### 2.2 客体：资源上的权限信息

文件系统里，权限信息主要挂在 **inode** 上。`stat` 能看到的部分：

```text
$ stat /etc/passwd
  文件：/etc/passwd
  大小：...  块：...  IO 块大小：4096  regular file
设备：...    Inode: ...    硬链接：1
权限：(0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
```

#### 12 位 mode：不只是 rwx

`stat` 的「权限」括号里是 4 位八进制，展开成 12 个 bit：

```text
 0 6 4 4
 │ │ │ └─ other: r w x  (读/写/执行)
 │ │ └─── group: r w x
 │ └───── owner: r w x
 └─────── 特殊位: 4=setuid  2=setgid  1=sticky
```

```text
      特殊位      属主        属组        other
     ┌───┬───┐ ┌───┬───┬───┐ ┌───┬───┬───┐ ┌───┬───┬───┐
     │ 4 │ 2 │ │ r │ w │ x │ │ r │ w │ x │ │ r │ w │ x │
     │SUID│SGID│ │  │  │   │ │  │  │   │ │  │  │   │
     │   │sticky│ └───────────┘ └───────────┘ └───────────┘
     └───┴───┘
```

内核头文件里的常量（`来源：include/uapi/linux/stat.h`）：

```c
#define S_ISUID  0004000   // setuid
#define S_ISGID  0002000   // setgid
#define S_ISVTX  0001000   // sticky
#define S_IRUSR  00400
#define S_IWUSR  00200
#define S_IXUSR  00100
```

#### rwx 对文件和目录是两套语义

这是初学者最大的坑：

| 位 | 对文件 | 对目录 |
|---|---|---|
| r | 读内容 | **列出目录项**（`ls`） |
| w | 改内容 | **创建/删除/重命名**目录项 |
| x | 执行（`execve`） | **进入/遍历**（访问子路径必需） |

> 目录的 `x` 位是「通行证」：没有它，即使你知道文件名、文件本身 777，也打不开。
> 本机实测（属主自己也被拦）：

```text
$ mkdir nosearch; echo data > nosearch/f; chmod 600 nosearch
$ cat nosearch/f
cat: nosearch/f: 权限不够
$ chmod 700 nosearch; cat nosearch/f
data
```

#### 权限信息不止 mode：还有 ACL 和 xattr

| 载体 | 存什么 | 查看工具 | 本课程章节 |
|---|---|---|---|
| mode 12 位 | 属主/属组/other + 特殊位 | `ls -l`、`stat` | 03 |
| ACL | 额外的具名用户/组、mask、default 条目 | `getfacl` | 03 |
| `security.capability` xattr | 文件 capability（e/i/p 三组位） | `getcap`、`getfattr` | 05 |
| `security.selinux` / AppArmor 标签 | LSM 标签 | `ls -Z`、`aa-status` | 04 |
| `chattr` 标志 | immutable/append-only 等 | `lsattr` | 03 |

再看资源不只是文件：

| 资源 | 权限载体 | 检查点 |
|---|---|---|
| 普通文件/目录 | inode mode + ACL | `open`/`execve` |
| **特权端口**（<1024） | capability | `bind()` 需要 `CAP_NET_BIND_SERVICE`（或放宽 sysctl） |
| **UNIX socket** | socket 文件的 inode 权限 | `connect()` 按 socket 文件权限检查 |
| 设备节点 | inode mode + 属组（如 `video`/`disk`） | `open` |
| 进程信号 | ruid/euid 匹配（或 `CAP_KILL`） | `kill()` |
| System V/POSIX IPC | IPC 对象的 mode | `shmget`/`msgget`/`semget` |
| `/proc`、`/sys` | 各自的权限规则 + LSM | 读写文件 |
| `docker.sock` | 文件 mode 0660 + 属组 `docker` | `connect()` → **等价 root**（07 章） |

> 这一行值得先记住：**端口、socket、设备都能用「权限」解释**，不是只有文件才有权限。

### 2.3 规则：内核的检查顺序

把内核的检查压缩成伪代码（简化版；真实实现分散在 `fs/namei.c`，
本机只有头文件里的函数声明：`来源：include/linux/fs.h`，`inode_permission()` / `generic_permission()`）：

```text
// 打开 /a/b/c
for (每一级目录 d in /a, /a/b)        // 注意：不含最后一级文件
    需要 d 的 x 位（MAY_EXEC），否则 EACCES

// 最后一级
check_permission(inode, 请求的 mask):
    if (fsuid == inode.uid)                      // ① 属主
        用 owner 位判断
    else if (fsgid 或任一辅助组 == inode.gid      // ② 属组
             || ACL 中命中具名组/具名用户)          // ②' ACL 优先
        用 group 位 + ACL mask 判断
    else
        用 other 位判断                           // ③ 其他人

    if (上面拒绝):
        if (请求是读且进程有 CAP_DAC_READ_SEARCH) 放行   // ④ capability 兜底
        if (请求是写/执行且进程有 CAP_DAC_OVERRIDE) 放行
        else EACCES

    if (LSM 策略拒绝) EACCES/EPERM                // ⑤ 最后一道门
```

几个必须记住的细节：

1. **ACL 优先于 group 位**：文件有 ACL 时，检查的是 ACL 条目 + mask，而 mode 的 group 位只是 mask 的投影。
   这也是 `getfacl` 显示 `#effective` 的原因（03 章实测）。
2. **root 的「万能」有例外**：
   - 读文件：`CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH` 可以绕过 mode；
   - 执行文件：**必须至少有一个 x 位**，root 也不能执行 `chmod 000` 的程序（容器内实测）：

   ```text
   # 容器内，root
   $ cat /tmp/f                  # 文件 mode 000
   hello
   $ /tmp/true                   # 文件 mode 000
   bash: /tmp/true: Permission denied
   ```

   - 写只读文件系统：root 也写不了（`EROFS`）；LSM 拒绝时 root 也不行（`EPERM`）。
3. **检查只发生一次**：`open()` 成功后，后续 `read()`/`write()` 不再重新检查文件权限。
   实测（宿主，python）：

   ```text
   chmod 000 后 stat: 0o0
   已打开的 fd 再读取: b'payload'
   重新打开: 失败 [Errno 13] Permission denied: 'fdtest'
   ```

   推论：删掉权限/文件后，已经打开 fd 的进程仍能继续读写（/proc/PID/fd 也能拿到）；
   反过来，`rm -rf` 删不掉正在被写的文件时，空间不会立即释放。
4. **`access(2)` 用的是 ruid，不是 euid**（`来源：man 2 access`）。setuid 程序里用 `access()`
   判断「当前用户能不能读」会得到和 `open()` 不同的结果（容器内实测）：

   ```text
   # 容器内，setuid root 的 accesstest，以 alice 运行
   ruid=1000 euid=0
   access(R_OK)=-1 errno=13 (Permission denied)
   open(O_RDONLY)=3 errno=0 (ok)
   ```

   这是「euid 提权了，但 access() 仍按真实用户判断」的经典陷阱（09 章排障案例）。

#### errno 速记

| errno | 数值 | 典型含义 | 常见场景 |
|---|---|---|---|
| `EACCES` | 13 | Permission denied | mode/ACL 拒绝、目录缺 x、脚本无 x |
| `EPERM` | 1 | Operation not permitted | capability 不足、LSM 拒绝、不可变文件 |
| `EROFS` | 30 | Read-only file system | 只读挂载 |
| `ENOENT` | 2 | No such file or directory | 路径不存在（也可能父目录不可搜索） |
| `ENOTDIR` | 20 | Not a directory | 路径中间某一级是文件 |

> 排障第一问永远是：**是 EACCES 还是 EPERM？** 前者多半是 mode/ACL，后者多半是 capability/LSM。

### 2.4 execve：凭证在「执行那一刻」改变

`execve` 是权限模型里最特殊的一步：内核可能在 exec 时**主动给进程换身份**。
规则（`来源：man 7 capabilities`、`man 2 execve`，并用容器实测）：

| 可执行文件上有什么 | exec 后 euid | exec 后 capability | 实测 |
|---|---|---|---|
| 普通文件（属主 root） | 不变（调用者 euid） | 不变 | — |
| **setuid 位**（属主 root） | **0** | 按规则从 bounding 重新计算 | 见下 |
| 文件 capability `cap_dac_override=ep` | 不变（仍 1000） | **CapEff 多出 0x2** | 见下 |
| setuid + 进程 `no_new_privs=1` | **不变** | **不增加** | 见下 |
| 脚本 + setuid 位 | **不变**（内核忽略脚本的 setuid） | 不变 | 见下 |

容器内实测（`labs/04-setuid-caps` 的核心）：

```text
# 容器内：setuid root 的静态程序，由 alice(1000) 执行
$ su alice -c "/usr/local/bin/uidinfo"
real=1000 effective=0 saved=0 | gid real=1000 eff=1000 saved=1000
read /root/secret.txt: OK -> TOP-SECRET

# 加上 no_new_privs 后，setuid 位被忽略
$ su alice -c "setpriv --no-new-privs /usr/local/bin/uidinfo"
real=1000 effective=1000 saved=1000 | ...
read /root/secret.txt: DENIED (euid=1000)
```

```text
# 容器内：setuid 脚本不会提权
$ ls -l /usr/local/bin/suid-script
-rwsr-xr-x 1 root root 13 ... /usr/local/bin/suid-script
$ su alice -c "/usr/local/bin/suid-script"
uid=1000(alice) gid=1000(alice) groups=1000(alice)
```

> 这三行输出解释了很多「为什么我的 setuid 程序不生效」：挂了 `nosuid`、进程有 `no_new_privs`、
> 或者写成了 shell 脚本。05/07/09 章都会反复用到。

### 2.5 第五道门：不属于 uid/gid 的权限

以下机制会让「权限位都对，但仍然失败」：

| 机制 | 效果 | 怎么发现 |
|---|---|---|
| 挂载选项 `nosuid` | 忽略 setuid/setgid 位 | `findmnt -T <路径>` |
| 挂载选项 `noexec` | 禁止执行该挂载点上的程序 | `findmnt` |
| 只读挂载/只读文件系统 | 写操作 `EROFS` | `findmnt`、`touch` |
| LSM（AppArmor/SELinux） | 按路径/标签拒绝，可能 `EPERM` | `dmesg`、`journalctl -k`、`aa-status` |
| `chattr +i`（immutable） | 连 root 也不能改/删 | `lsattr` |
| Landlock | 进程自己给自己加的文件访问限制 | 应用自述 |
| seccomp | 拦截系统调用（容器常见） | `/proc/PID/status` 的 `Seccomp` |
| 用户命名空间/容器 capability 集 | 容器 root 只有部分 cap | `capsh --print` |
| quota / 磁盘满 | 写失败但不一定是权限 | `df`、`quota` |

本机就踩了第一条：`/home/demo` 的挂载选项是 `rw,nosuid,nodev`（06/07 章会讲为什么容器里能跑 setuid 而宿主不能）。

### 2.6 把四类应用放进模型

用同一张表看常见应用，你会发现它们的权限问题都是「凭证 × 资源」的组合：

| 应用/组件 | 主体（凭证） | 客体（资源） | 常见故障 |
|---|---|---|---|
| nginx master | root（需要 bind 80、打开日志） | 配置文件、日志、pid | 端口被占、日志目录不存在 |
| nginx worker | `nginx`（uid 101） | 静态文件、缓存/临时目录、上游 socket | **403**、`open() failed (13: Permission denied)` |
| dockerd | root（一直） | 镜像、容器、`/var/run/docker.sock` | socket 权限、卷属主 |
| docker 客户端 | 当前用户（经 socket 请求） | `docker.sock` | 不在 docker 组 → `permission denied` |
| 容器内进程 | 镜像 `USER` 或 `-u` 指定 | 容器内文件系统 + 挂载卷 | **卷属主不匹配** |
| `sudo` | 调用者 → root（setuid） | `/etc/sudoers`、目标命令 | 策略不允许、`no_new_privs` |
| sshd | root → 登录用户 | `~/.ssh`、`authorized_keys` | 权限过宽被拒绝 |
| systemd 服务 | `User=` 指定 | 服务文件、日志 | `ProtectHome` 导致读不到家目录 |
| cron | 用户身份 | 脚本、环境变量 | PATH/umask 与交互式不同 |

回到开头三个现象，现在可以一句话解释（细节见对应章节）：

- **现象 A**：`/etc/shadow` mode 0640 root:shadow，普通用户 uid/gid 都不匹配，且无 `CAP_DAC_READ_SEARCH` → 03/04 章；
- **现象 B**：docker 客户端只是把请求发给 root 的 dockerd，容器内 root 默认就是宿主 root（无 userns 映射）→ 07 章；
- **现象 C**：nginx worker 以 uid 101 运行，600 文件只有 uid 1000 能读 → 08 章。

## 三、动手验证

### 3.1 宿主上能直接做的（无需 root）

```bash
# 1) 看自己的完整凭证
id
grep -E '^(Uid|Gid|Groups|CapInh|CapPrm|CapEff|CapBnd|CapAmb|NoNewPrivs)' /proc/self/status

# 2) 看 ps 的四套 uid 字段（注意 suid 是 saved uid）
ps -o pid,user,euser,ruid,euid,suid,args -p $$

# 3) 看一个文件的 12 位 mode 与 inode 元数据
stat /etc/passwd
stat -c 'mode=%a %A uid=%u gid=%g' /etc/passwd

# 4) 看 ACL（即使没有 ACL，也会显示基础三项）
getfacl -p /etc/passwd

# 5) 看 setuid/setgid 文件清单
find /usr/bin /usr/sbin /bin /sbin -maxdepth 1 -perm -4000 -type f 2>/dev/null

# 6) 看本机的 capability 边界（没有 capsh 时用 /proc）
grep -E '^Cap(Eff|Bnd)' /proc/self/status

# 7) 进入一个「假 root」命名空间，观察 uid 映射
unshare -Ur sh -c 'id; cat /proc/self/uid_map; grep -E "^(CapEff|NoNewPrivs)" /proc/self/status'

# 8) 看挂载选项（nosuid/noexec 会改变权限行为）
findmnt -T /home/demo -o TARGET,SOURCE,FSTYPE,OPTIONS
```

### 3.2 需要「真 root」的（用容器）

```bash
# 容器内：观察 root 的 cap 集、执行 setuid 程序、验证 no_new_privs
docker run --rm debian:13 bash -c '
  apt-get update -qq && apt-get install -y -qq --no-install-recommends libcap2-bin >/dev/null
  capsh --print | grep -E "^(Current|Bounding)"
  grep -E "^(CapEff|CapBnd)" /proc/self/status
'
```

完整的跨用户实验（setuid、capability、sudo）在 [`labs/04-setuid-caps`](../labs/04-setuid-caps/) 里，
按脚本跑即可，不需要手工敲。

### 3.3 看到什么 → 说明什么

| 你看到 | 说明 |
|---|---|
| `CapEff: 0000000000000000` | 进程没有任何生效 capability，只能靠 uid/gid |
| `Uid:` 四个值不同 | 有 setuid/降权发生（如 euid=0、ruid=1000） |
| `NoNewPrivs: 1` | 后续 execve 不会获得新特权，setuid/文件 cap 失效 |
| `ls -l` 里 `rws` / `rws` / `rwt` | setuid / setgid / sticky 位生效 |
| `ls -l` 里 `rwS` / `rwS` | 特殊位在，但**对应的 x 位缺失**（常见错误配置） |
| 文件属主显示 `65534` | 该 uid 在当前 namespace 未映射（06 章） |
| `findmnt` 有 `nosuid` | setuid 位会被忽略 |

## 四、常见误解

❌ **「root 什么都能做」**
✅ root 受 capability 集、LSM、只读文件系统、immutable 标志限制；执行一个没有任何 x 位的程序也会被拒绝。
（验证：容器内 `chmod 000 /tmp/true && /tmp/true` → `Permission denied`）

❌ **「euid=0 就有全部 capability」**
✅ euid 0 只是让进程在 exec 时按规则获得 capability；实际能用的是 `CapEff`，还可能被 Bounding 集削减。
（验证：容器内 `capsh --print`，Docker 默认只有 14 个 cap）

❌ **「有 ACL 就按 ACL 给权限，chmod 不会影响 ACL」**
✅ ACL 有 mask，`chmod` 改 group 位时**实际改的是 mask**，会连带压掉具名条目的 effective 权限。
（验证：`setfacl -m u:demo:rwx f && chmod 640 f && getfacl f` 会看到 `#effective:r--`）

❌ **「权限只看目标文件」**
✅ 路径上每一级目录都需要 x 位；挂载选项、LSM、父目录 sticky 位都会参与。
（验证：`chmod 600 dir; cat dir/f` → `Permission denied`）

❌ **「每次 read 都要检查权限」**
✅ 权限只在 `open` 时检查一次；已打开的 fd 之后不再检查。
（验证：python 打开文件后 `chmod 000`，仍可 `os.read`）

❌ **「`access()` 检查的是进程当前的有效权限」**
✅ `access()` 用 **ruid**，在 setuid 程序里和 `open()` 的结论可能相反。
（验证：容器内 setuid 程序 `access()` 返回 -1，`open()` 返回 3）

❌ **「文件属主显示 nobody，说明它属于 nobody 用户」**
✅ 显示 `65534`（overflow uid）通常表示该文件的 uid 在当前 namespace **没有映射**，不一定是真的 `nobody` 账户。
（验证：宿主 root 文件在本会话显示 `nobody:nogroup`；容器内 root 创建的文件在宿主视角也是 65534）

❌ **「组权限只看主组」**
✅ 主组 + 全部辅助组都参与匹配；`id` 只显示主组和辅助组，`getent group <名>` 能看到成员。
（验证：容器内 `usermod -aG devs alice` 后，`id alice` 里出现 `2000(devs)`）

❌ **「容器里的 root 就是宿主 root」或「容器里的 root 一定被隔离」**
✅ 两种都可能，取决于是否启用 userns-remap/rootless。本机 Docker 默认 **rootful**，容器 root 就是宿主 root；
但 capability 被削减、还有 seccomp/AppArmor。（验证：容器 root 在宿主目录创建的文件属主是 0）

## 五、速查表

| 我想知道 | 命令 | 看什么 |
|---|---|---|
| 我是谁、有哪些组 | `id` | uid/gid、辅助组 |
| 进程的完整凭证 | `grep -E '^(Uid|Gid|Groups|Cap|NoNewPrivs)' /proc/self/status` | 四套 uid、cap 五集合 |
| 某进程的凭证 | `grep ... /proc/<pid>/status` | 同上 |
| 进程的 caps 可读形式 | `capsh --print`（需 libcap2-bin） | Current/Bounding |
| 文件权限与属主 | `stat -c '%a %A %U:%G %n' <f>` | 12 位 mode |
| 文件 ACL | `getfacl -p <f>` | 具名条目 + mask/effective |
| 文件 capability | `getcap -r /usr 2>/dev/null` | 哪些程序带 cap |
| 挂载是否 nosuid/noexec | `findmnt -T <path>` | OPTIONS 列 |

| 文件是否不可变 | `lsattr <f>` | `i`/`a` 标志 |
| 路径每级权限 | `namei -l /a/b/c` | 每一级 mode |
| uid 是否被映射 | `cat /proc/<pid>/uid_map`、`ls -n` | 65534 = 未映射 |
