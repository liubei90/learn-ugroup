## 一、先建立直觉

### 1.1 本章在全局模型里的位置

全书的模型只有一行：**进程凭证 × 资源上的权限信息 × 检查规则 + 其他关卡 = 能不能访问**。
[01-权限模型全景](01-权限模型全景.md) 把这四项展开；本章只做其中两件事：

1. 把**进程凭证**这一侧讲细：到底有哪些字段、怎么观察、fork/exec 时怎么变；
2. 把**检查规则**这一侧讲细：内核按什么顺序判定、检查发生在哪一刻、哪些东西在文件名/权限位之外也能拒绝你。

```text
                 ┌─────────────────────────────┐
                 │  进程凭证 struct cred       │
                 │  ruid/euid/suid/fsuid       │
                 │  rgid/egid/sgid/fsgid       │
                 │  辅助组 group_info          │
                 │  cap P/E/I/B/A              │
                 │  no_new_privs / dumpable    │
                 └──────────────┬──────────────┘
                                │  在 open()/execve() 时刻参与判定
                 ┌──────────────▼──────────────┐
                 │  资源：inode 的 mode/ACL    │
                 │  挂载选项、LSM、seccomp、   │
                 │  Landlock、只读文件系统…    │
                 └──────────────┬──────────────┘
                                │
                        允许 / EACCES / EPERM
```

图：进程凭证、资源权限与检查规则的关系。凭证是一侧输入，资源权限是另一侧输入，
“检查规则”决定怎么比较两者；`EACCES`（13）通常来自 mode/ACL，`EPERM`（1）通常来自 capability/LSM。

### 1.2 一次文件访问到底用了哪几样东西

| 访问动作 | 实际参与判定的凭证 | 观察入口 |
|---|---|---|
| 打开/读写普通文件 | **fsuid**（不是 euid！）、fsgid、辅助组、`CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH` | `stat -c %u`、`/proc/self/status` 的 `Uid:` 第 4 列 |
| 遍历目录 / 执行程序 | 同上，但需要目录/程序的 **x** 位 | `namei -l <路径>` |
| 创建文件 | fsuid 决定属主，fsgid / 目录 SGID 位决定属组，umask 决定 mode | `stat`、`umask` |
| 发信号、改 nice、读 `/proc/<别人的 pid>` | **ruid/euid**（内核按 euid 与目标进程的 ruid 比较） | `man 7 credentials` |
| 记账（`ps`、`/proc` 显示谁启动的） | ruid | `ps -o ruid` |

关键点只有一句：**VFS 权限检查用 fsuid/fsgid，不是 euid/egid**；只是正常进程里
`seteuid` 会同步修改 fsuid，所以两者“通常相等”。`来源：man 7 credentials`（Filesystem user ID 一节）、
`来源：man 7 path_resolution`（“Linux uses the fsuid instead of the effective user ID”）。

### 1.3 凭证在内核里是一个结构体

`struct cred` 把本章要讲的字段打包在一起，内核头文件就能看到（本机实测存在该文件）：

```bash
grep -n -A14 'struct cred {' /usr/src/linux-headers-*/include/linux/cred.h | head -18
```

```text
113:struct cred {
114-	atomic_long_t	usage;
115-	kuid_t	uid;		/* real UID of the task */
116-	kgid_t	gid;		/* real GID of the task */
117-	kuid_t	suid;		/* saved UID of the task */
118-	kgid_t	sgid;		/* saved GID of the task */
119-	kuid_t	euid;		/* effective UID of the task */
120-	kgid_t	egid;		/* effective GID of the task */
121-	kuid_t	fsuid;		/* UID for VFS ops */
122-	kgid_t	fsgid;		/* GID for VFS ops */
123-	unsigned	securebits;	/* SUID-less security management */
124-	kernel_cap_t	cap_inheritable; /* caps our children can inherit */
125-	kernel_cap_t	cap_permitted;	/* caps we're permitted */
126-	kernel_cap_t	cap_effective;	/* caps we can actually use */
127-	kernel_cap_t	cap_bset;	/* capability bounding set */
```

验证：`grep -n fsuid /usr/src/linux-headers-6.12.107+deb13-common/include/linux/cred.h`
（本机输出 `121:	kuid_t	fsuid;		/* UID for VFS ops */`）。

两个容易漏的字段：

- `user_ns`：**同一份 cap 位在不同 user namespace 里的“威力”不同**（06 章）。
- `group_info`：辅助组参与文件权限判定，但**不属于 euid/egid 这套三元组**；
  `setgroups()` 改的是它（05 章讲降权为什么要先 `setgroups`）。

### 1.4 四套 uid 速记（细节回 01）

| 缩写 | 名字 | 一句话 |
|---|---|---|
| ruid | 真实用户 ID（real UID） | 谁启动的进程；`ps`/记账/信号场景 |
| euid | 有效用户 ID（effective UID） | 信号、`access(2)`、传统权限模型的“身份” |
| suid | 保存的用户 ID（saved UID） | `seteuid()` 可以在 euid 与它之间来回切 |
| fsuid | 文件系统用户 ID（fsuid） | **VFS 真正用来查文件权限的那个** |

完整对照表见 [01-权限模型全景](01-权限模型全景.md) 的 2.1 节；本章只补一个易错点：
`ps` 的 `suid` 列 **不是 setuid 位**，而是 saved uid（见 2.1 节实测）。

### 1.5 检查发生在“打开/执行”那一刻

内核不会在每次 `read()`/`write()` 时重新查 inode 的 mode。`open()` 成功那一刻，
VFS 做一次权限判定，之后拿到的是 `struct file` + `fd`；后续读写只验证“这个 fd 是否可读写”。

这解释了三类现象（本章 2.4 节逐个实测）：

1. `chmod 000` 之后，**已经打开的 fd 仍能继续读**；
2. 通过 unix socket 用 `SCM_RIGHTS` 把 fd 传给别的进程，接收方**不受文件当前 mode 限制**；
3. 想通过 `/proc/PID/fd/N` 去“借”别人的 fd 时，**打开这个符号链接本身会重新做一次权限检查**。

### 1.6 本章要回答的三个问题

- 进程凭证有哪些字段，分别在哪里能看到？（2.1）
- `fork()` / `execve()` 之后，哪些字段变、哪些不变？（2.2）
- 内核为什么拒绝我：是文件 mode、目录 x、ACL、capability，还是 LSM/挂载选项？（2.3、2.5）

## 二、进程凭证与权限检查

### 2.1 凭证清单与观测

#### `/proc/PID/status`：字段最全的入口

宿主实测（`/proc/self` 是读取时那个进程自己，本机是受限沙箱，所以 cap 全 0）：

```bash
grep -E '^(Uid|Gid|Groups|CapInh|CapPrm|CapEff|CapBnd|CapAmb|NoNewPrivs|Seccomp|NSpid)' /proc/self/status
```

```text
Uid:	1000	1000	1000	1000
Gid:	1000	1000	1000	1000
Groups:	65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 65534 1000
NSpid:	6
CapInh:	0000000000000000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000
CapAmb:	0000000000000000
NoNewPrivs:	1
Seccomp:	0
Seccomp_filters:	0
```

逐行读法（`来源：man 5 proc` 的 `/proc/pid/status` 一节）：

| 字段 | 含义 | 本机为什么是这个值 |
|---|---|---|
| `Uid:` | 四列：real / effective / saved / **filesystem** uid | 本会话在受限沙箱里，四列都是 1000 |
| `Gid:` | 四列：real / effective / saved / filesystem gid | 同上 |
| `Groups:` | 辅助组列表（内核按调用者能看到的 uid 显示） | 大量 65534 是沙箱 userns 的溢出 UID 副产物（06 章） |
| `CapInh/Prm/Eff/Bnd/Amb` | capability 的 I/P/E/B/A 五个集合，十六进制位图 | 本会话 `CapEff=0`：无任何生效 capability |
| `NoNewPrivs:` | 进程的 no_new_privs 属性 | 本会话被强制设为 1，导致 `sudo`/SUID 全部失效 |
| `Seccomp:` | seccomp 模式（0 关闭 / 2 过滤） | 宿主 0；容器里通常为 2（见 2.5） |
| `Seccomp_filters:` | 已安装的 seccomp 过滤器数量 | 宿主 0 |
| `NSpid:` | 在各级 PID namespace 里的 PID；只有嵌套 PID ns 时才多列 | 本会话只有一个 PID ns，故单列 |

`Uid:` 有 4 列而不是 3 列，是最容易被忽略的细节：第 4 列是 fsuid。
root 进程若 `setfsuid(1000)`，`open()` 会按 uid 1000 查权限，而 `id`/`ps` 仍显示 root 身份。

#### `id` 与 `ps`：名字不同，来源相同

```bash
id
ps -o pid,uid,euid,suid,ruid,cmd -p $$
```

```text
uid=1000(demo) gid=1000(demo) 组=1000(demo),65534(nogroup)
    PID   UID  EUID  SUID  RUID CMD
      2  1000  1000  1000  1000 bash -c ...
```

`ps` 的字段语义（`来源：man 1 ps`，procps 实现）：

| 字段 | 实际含义 | 易错点 |
|---|---|---|
| `uid` | effective uid | 与 `euid` 同义 |
| `euid` | effective uid | — |
| `ruid` | real uid | `ps` 默认的 `USER` 列显示 euid 对应的名字 |
| `suid` | **saved uid** | 不是 setuid 位；排障时最容易看错 |

容器内用 SUID 程序验证这一点（`uidsleep` 打印 `getresuid()` 后睡 20 秒）：

```text
# 容器内：alice(1000) 执行 root 属主的 SUID 程序
uids=1000/0/0 gids=1000/1000/1000
    PID   UID  EUID  SUID  RUID CMD
    210     0     0     0  1000 /usr/local/bin/uidsleep

# 对照：普通程序
    PID   UID  EUID  SUID  RUID CMD
    217  1000  1000  1000  1000 sleep 8
```

验证：容器内 `su alice -c "/usr/local/bin/uidsleep > /tmp/o 2>&1 &"; ps -o pid,uid,euid,suid,ruid,cmd -C uidsleep`。
可见 `UID/EUID=0`（effective）、`SUID=0`（saved）、`RUID=1000`（real）。

#### `/proc/PID/attr/`：LSM 与 exec 时安全属性的接口

```bash
ls /proc/self/attr/
for f in current exec fscreate prev; do printf 'attr/%s -> ' "$f"; cat /proc/self/attr/$f; done
```

```text
attr/current -> unconfined
attr/exec -> cat: /proc/self/attr/exec: 无效的参数
attr/fscreate -> cat: /proc/self/attr/fscreate: 无效的参数
attr/prev -> cat: /proc/self/attr/prev: 无效的参数
```

读法：

- `attr/current` 是**当前进程的 LSM 标签**；本机 AppArmor 为 `unconfined`，容器里则是
  `docker-default (enforce)`（见 2.5）。
- `attr/exec`、`fscreate`、`sockcreate` 是**写接口**（设置下一次 exec/创建文件时套用的标签），
  没有设置时读取返回 `EINVAL` 是正常现象。
- `attr/prev` 只在进程发生过标签切换后可读。

验证：上表命令在宿主执行；`attr/current` 输出 `unconfined`。

#### `dumpable`：为什么 SUID 进程的 `/proc/PID` 变了主人

`dumpable` 不在 `/proc/PID/status` 里，用 `prctl(PR_GET_DUMPABLE)` 读：

```text
# 容器内
uids=1000/0/0 dumpable=0          # SUID root 程序（euid 变了）
uids=1000/1000/1000 dumpable=1    # 同一程序 + no_new_privs（euid 没变）
```

验证：容器内 `su alice -c /usr/local/bin/dumpable` 与
`su alice -c "setpriv --no-new-privs /usr/local/bin/dumpable"`。
`来源：man 2 prctl`（PR_SET_DUMPABLE 一节）：`execve` 使 euid/egid 改变时，
内核把 dumpable 重置为 `/proc/sys/fs/suid_dumpable` 的值（通常 0）。

影响：dumpable=0 时 `/proc/PID/*` 的属主变成 root，同 uid 的其他进程要读它的
`/proc/PID/fd`、`/proc/PID/maps` 会先过 ptrace 访问检查——排障“为什么 strace 别人的进程失败”时先看这个
（`来源：man 7 credentials`、`man 5 proc`；本机容器内看到 SUID 进程 dumpable=0，未复现 strace 拒绝）。

### 2.2 fork/exec 时凭证如何变

#### fork：全量复制，之后各改各的

`fork()` 的子进程拿到父进程凭证的一份拷贝；`clone(CLONE_THREAD)` 的线程共享同一份 cred。
`来源：man 7 credentials`（“A child process created by fork(2) inherits copies of its parent's
user and group IDs”）。

所以“父进程改了 euid，子进程会受影响吗”答案是：**不会**——fork 之后两边独立
（线程除外）。这也意味着在 shell 里 `su alice -c ...` 起的子进程，父 shell 的凭证不变。

#### execve：三件事同时发生

`execve()` 是唯一能在“执行一个文件”的瞬间**主动改变 euid/suid 和 capability** 的操作。
本章只给规则，提权机制的完整推导在 [05-提权与降权机制](05-提权与降权机制.md)。

| 可执行文件带什么 | euid / saved uid | capability | 实测 |
|---|---|---|---|
| 普通文件 | 不变 | 按 exec 规则重算（通常清空非零部分） | `sleep 8` 的 ps 输出（2.1） |
| setuid 位 | euid=文件属主，saved=euid | 从 bounding 重新授予（root 程序） | 2.1 的 uidsleep |
| setgid 位 | egid=文件属组，saved=egid | 不影响 cap | — |
| 文件 capability | 不变 | 按公式把文件 cap 并入 P/E | `CapEff=...2`（05 章实测） |
| setuid **脚本** | **不变** | 不变 | 见下 |
| 上述任一项 + `no_new_privs=1` | **不变** | **不增加** | 见下 |
| 上述任一项 + `nosuid` 挂载 | **不变** | **不增加** | 见下 |

规则来源：`来源：man 2 execve`——setuid/setgid 位与文件 capability 在以下情况被忽略：
调用线程设置了 `no_new_privs`、文件系统以 `nosuid` 挂载、进程正在被 ptrace。
`来源：man 5 proc`、`man 2 prctl`：`no_new_privs` 一旦设置不可撤销，且会被子进程继承。

三个必须记住的实测结论（容器内）：

```text
# 1) SUID root 程序：euid=0，saved=0
$ su alice -c "/usr/local/bin/uidinfo"
real=1000 effective=0 saved=0 | gid real=1000 eff=1000 saved=1000
read /root/secret.txt: OK -> TOP-SECRET

# 2) 加上 no_new_privs：SUID 位被忽略
$ su alice -c "setpriv --no-new-privs /usr/local/bin/uidinfo"
real=1000 effective=1000 saved=1000 | gid real=1000 eff=1000 saved=1000
read /root/secret.txt: DENIED (euid=1000)

# 3) SUID shell 脚本：提权无效（内核忽略脚本上的 setuid 位）
$ ls -l /usr/local/bin/suidscript
-rwsr-xr-x 1 root root 13 ... /usr/local/bin/suidscript
$ su alice -c "/usr/local/bin/suidscript"
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)
```

验证：以上三条即容器内完整命令与输出；“脚本 SUID 无效”也可由 `man 2 execve` 的
Interpreter scripts 一节佐证。

`no_new_privs` 还会**继承**：设了它之后 fork/exec 出来的所有后代都带着它（实测）：

```text
# 容器内
$ su alice -c "setpriv --no-new-privs sh -c 'grep NoNewPrivs /proc/self/status; /usr/local/bin/uidinfo'"
NoNewPrivs:	1
real=1000 effective=1000 saved=1000 | ...
read /root/secret.txt: DENIED (euid=1000)
```

验证：容器内 `setpriv --no-new-privs sh -c ...` 的上述输出；`NoNewPrivs` 字段在 exec 后仍是 1。

### 2.3 权限检查顺序：从 `open()` 到 `acl_permission_check`

#### 调用链（源码级，标注验证程度）

内核打开文件的路径大致是（函数名可在本机头文件/运行内核 BTF 中核对）：

```text
open()/openat()
  └─ do_sys_openat2() → do_filp_open()
       └─ path_openat()                     # 路径解析
            ├─ 逐级目录 link_path_walk()：每级需要 x（MAY_EXEC）
            └─ do_open() → may_open()       # 最后一级：拒绝写只读文件、写目录等
                 └─ inode_permission()      # 权限判定（fsuid/fsgid/辅助组/cap）
                      └─ generic_permission()
                           ├─ acl_permission_check()   # mode/ACL 判定
                           └─ CAP_DAC_OVERRIDE / CAP_DAC_READ_SEARCH 兜底
       └─ LSM hook（security_inode_permission 等）  # 最后一道门
```

可靠性标注：

- `inode_permission()`、`generic_permission()`：本机内核头文件有原型，
  验证：`grep -nE 'inode_permission|generic_permission' /usr/src/linux-headers-6.12.107+deb13-common/include/linux/fs.h`
  （输出含 `int inode_permission(struct mnt_idmap *, struct inode *, int);`）。
- 上图其余函数名（`do_sys_openat2`、`do_filp_open`、`link_path_walk`、`security_inode_permission`、
  `path_openat`、`do_open`、`may_open`）：都出现在运行内核的 BTF 字符串表中，
  验证：`grep -aco may_open /sys/kernel/btf/vmlinux` 输出 `1`，其余名字同样为 `1`。
- `acl_permission_check()`：BTF 中未搜到（`grep -aco acl_permission_check /sys/kernel/btf/vmlinux` 输出 `0`），
  BTF 中没有导出这个名字（内联或未导出，本机无法区分），**源码中的确切调用层次未验证**；本机也没有内核源码，只有头文件。
- 因此上图的**函数名**有依据，但“精确到哪一行”的调用顺序属于源码级描述，本机未逐行核对。

#### 判定顺序：先比身份，再用 capability 兜底

`generic_permission()` 的核心逻辑可以压缩成（`来源：man 7 path_resolution`）：

```text
1. 若 fsuid == inode.uid              → 用 owner 的三位（rwx）判定
2. 否则若 fsgid 或某个辅助组 == inode.gid → 用 group 的三位判定
3. 否则                                → 用 other 的三位判定
4. 若 ACL 存在，用 ACL 条目 + mask 取代/细化第 1~3 步（03 章）
5. 若仍拒绝：读/搜索可由 CAP_DAC_READ_SEARCH 放行；
             写/执行可由 CAP_DAC_OVERRIDE 放行
             （执行仍要求至少一个 x 位）
6. 最后 LSM 可以再拒绝一次
```

两个结论：

- **“root 绕过权限”不是魔法，而是第 5 步的两个 capability**（`CAP_DAC_OVERRIDE` 可覆盖读写执行、
  `CAP_DAC_READ_SEARCH` 只管读和目录搜索）。`来源：man 7 path_resolution`（Bypassing permission checks）。
- 第 5 步**只兜底 mode/ACL**，管不了只读文件系统（`EROFS`）、LSM（`EPERM`）、锁（`ETXTBSY`）等。

容器内用三种 root 验证“root 的绕过靠 capability”：

```text
# 容器内：文件 /w/owned1000.txt 属主 uid 1000、mode 600
# 默认 capability 的 root：可读
$ cat /w/owned1000.txt
owned-by-1000

# 默认 capability：读成功

owned-by-1000

CapEff:	0000000000000000

$ docker run --rm --cap-drop DAC_OVERRIDE -v "$PWD/.tmp/out":/w:ro debian:13 \

cat: /w/owned1000.txt: Permission denied

# 只给 CAP_DAC_READ_SEARCH：读成功（CapEff 只剩 bit 2）
```

验证：上述四条 `docker run ... debian:13` 命令，输出即上方文本（宿主目录 `$PWD/.tmp/out`
里的 `owned1000.txt` 由宿主用户创建，mode 600）。

#### 目录：路径每一级都要 x

```bash
mkdir -p .tmp/noexecdir/sub; echo data > .tmp/noexecdir/sub/f; chmod 600 .tmp/noexecdir
namei -l .tmp/noexecdir/sub/f
cat .tmp/noexecdir/sub/f
chmod 700 .tmp/noexecdir
```

```text
f: .tmp/noexecdir/sub/f
drwxrwxr-x demo demo .tmp
drw------- demo demo noexecdir
                          sub - 权限不够
cat: .tmp/noexecdir/sub/f: 权限不够
```

验证：上述命令在宿主执行（`namei -l` 会逐级显示每一级目录的权限，并对无 x 的目录报错）。
注意失败发生在**路径解析阶段**，还没走到文件本身的 mode 判定——所以报错来自目录缺 x，
而不是文件的 r 位（`namei -l` 正是把每一级的判定显示出来）。

#### execve 的额外要求：x 位 + 解释器路径

`execve()` 除了对目标文件要求 x 位，对脚本还要求**解释器**（shebang 那一行）可执行；
并且内核会忽略脚本文件自身的 setuid 位（2.2 已实测）。这个规则解释了：
“我给脚本 `chmod 4755` 了，为什么还是 euid=1000”。

验证：容器内 `ls -l /usr/local/bin/suidscript` 显示 `-rwsr-xr-x`，但
`su alice -c /usr/local/bin/suidscript` 输出的 euid 仍是 1000。

### 2.4 “检查一次”语义：fd、`/proc/PID/fd`、`SCM_RIGHTS`

#### 已打开的 fd 不再检查

```bash
python3 - <<'PY'
import os
p = '.tmp/fdtest'
open(p, 'w').write('payload')
fd = os.open(p, os.O_RDONLY)
os.chmod(p, 0)
print('chmod 000 后 stat:', oct(os.stat(p).st_mode & 0o777))
print('已打开的 fd 再读取:', os.read(fd, 64))
try:
    os.open(p, os.O_RDONLY)
except OSError as e:
    print('重新打开: 失败', e)
PY
```

```text
chmod 000 后 stat: 0o0
已打开的 fd 再读取: b'payload'
重新打开: 失败 [Errno 13] Permission denied: '.tmp/fdtest'
```

验证：上述 python 片段在宿主执行（[01-权限模型全景](01-权限模型全景.md) 也用过同一现象；
这里是完整可复制版本）。

#### `SCM_RIGHTS`：fd 可以跨进程传递

```bash
python3 - <<'PY'
import os, socket
p = '.tmp/fdtest3'
open(p, 'w').write('payload3')
fd = os.open(p, os.O_RDONLY)
os.chmod(p, 0)
a, b = socket.socketpair(socket.AF_UNIX, socket.SOCK_DGRAM)
socket.send_fds(a, [b'x'], [fd])
os.close(fd)
msg, fds, flags, addr = socket.recv_fds(b, 16, 1)
print('收到的 fd:', fds[0], '读到的内容:', os.read(fds[0], 64))
PY
```

```text
收到的 fd: 3 读到的内容: b'payload3'
```

验证：上述片段在宿主执行。`SCM_RIGHTS` 传递的是**已打开文件的引用**，
接收方拿到 fd 后不再受文件当前 mode 限制——这也是 `systemd` socket 激活、nginx 传
listen fd、容器运行时传 fd 的原理（应用侧见 07/08 章）。

#### `/proc/PID/fd/N`：能“看到”fd，但打开它会重新检查

```text
# 宿主：另一进程持有 fd（文件已 chmod 000），从 shell 读 /proc/<pid>/fd/3
lr-x------ 1 demo demo 64 ... 3 -> .tmp/fd/fdtest2
cat: /proc/17/fd/3: 权限不够
```

验证：宿主上先运行一个 python 进程打开文件后 `chmod 000` 并 sleep，再在另一个 shell
执行 `cat /proc/<pid>/fd/3`。结论有两层：

1. `/proc/PID/fd/N` 是一个**指向已打开文件的入口**，能看到 fd 指向哪个 inode；
2. 但**打开这个入口会重新走一次权限检查**，所以文件 mode 000 时仍然 `EACCES`。
   要读“已经打开、但权限被改掉”的文件，必须由**持有 fd 的进程自己**读，
   或通过 `SCM_RIGHTS`/继承 fd 拿到引用。

### 2.5 其他关卡：不止 uid/gid 和 mode

[01-权限模型全景](01-权限模型全景.md) 的 2.5 节列了清单；本章给出“这些关卡分别怎么验证”。

#### LSM（本机是 AppArmor）

```bash
cat /sys/kernel/security/lsm
cat /sys/module/apparmor/parameters/enabled
```


验证：上述三条在宿主执行（最后一条输出 `unconfined`，因为本会话没套 AppArmor 策略）。

容器里则套着 `docker-default` 策略：

```text

$ cat /proc/self/attr/current
docker-default (enforce)
```

验证：`docker run --rm debian:13 cat /proc/self/attr/current`。

关键交互实测：**capability 有了，LSM 仍能拒绝**。

```text
# 容器内：mounttest 直接调用 mount(2) 并打印 errno
# 默认 capability（没有 CAP_SYS_ADMIN）
$ /b/mounttest
mount rc=-1 errno=1 (Operation not permitted)

# 加上 --cap-add SYS_ADMIN 后：CapEff 多出 bit 21，但 mount(2) 返回 errno=13
$ docker run --rm --cap-add SYS_ADMIN -v "$PWD/.tmp/bin":/b:ro debian:13 \
    bash -c 'mkdir -p /mnt2; grep CapEff /proc/self/status; /b/mounttest'
CapEff:	00000000a82425fb
mount rc=-1 errno=13 (Permission denied)
```

验证：上述两条容器命令。CapEff 位确实增加了（`a80425fb` → `a82425fb`，bit 21 = `CAP_SYS_ADMIN`），
但 `mount(2)` 从“缺 capability 的 `EPERM(1)`”变成“被 LSM 拒绝的 `EACCES(13)`”——
AppArmor 的 `docker-default` 策略仍然拦截 mount，**capability 不是唯一关卡**。

#### 挂载选项：`nosuid` / `noexec` / 只读

宿主 `/home` 是 `nosuid`（这就是本机不能在 `/home` 下跑 SUID 提权的原因）：

```bash

```

```text
TARGET       SOURCE                                FSTYPE OPTIONS
...          /dev/mapper/demo--vg-root[...] ext4   rw,nosuid,nodev,relatime,errors=remount-ro
```

验证：上述 `findmnt` 在宿主执行。

容器内用 `--tmpfs /x:nosuid,exec` 复现“SUID 在同一文件、不同挂载点上结果不同”：

```text
# 容器内：/x 是 nosuid tmpfs；/usr/local/bin 是普通 overlay

/x     tmpfs  rw,nosuid,nodev,relatime,size=10240k,inode64

$ su alice -c "/usr/local/bin/uidinfo"

```

验证：`docker run --rm --tmpfs /x:nosuid,exec,size=10m ... debian:13`，两个二进制的属主/权限相同
（`-rwsr-xr-x root root`）。`来源：man 2 execve`（nosuid 时忽略 setuid 位）。

只读挂载则直接返回 `EROFS`，与权限位无关：

```text
# 容器内：把宿主目录以 :ro 挂进来后写
$ touch /b/x
touch: cannot touch '/b/x': Read-only file system
```

验证：`docker run --rm -v "$PWD/.tmp/bin":/b:ro debian:13 touch /b/x`。

注意一个容易误判的点：**容器内 bind mount 不会自动继承宿主挂载的 `nosuid`**。本机实测宿主
`/home` 是 `nosuid`，但同一目录挂进容器后 `findmnt -T /b` 显示：

```text
TARGET SOURCE                                 FSTYPE OPTIONS
/b     /dev/mapper/demo--vg-root[...]  ext4   ro,relatime,errors=remount-ro
```

验证：容器内 `findmnt -T /b -o TARGET,SOURCE,FSTYPE,OPTIONS`（没有 `nosuid`）。
所以“宿主上 SUID 失效、容器里却生效”时，先查挂载选项差异，再怀疑权限位。

#### seccomp 与 Landlock

quota 与磁盘满不在本章展开：它们表现为写失败但通常不是 `EACCES`，排查入口是 `df`、`quota`、

### 2.6 容器视角：`CapEff` 只是 Docker 默认集

容器内的 root 不是“完整 root”。以下为容器内实测：


`--cap-drop` / `--cap-add` 的实测影响（对应 `CapEff` 的十六进制位）：

| Docker 参数 | `CapEff` | 结果 |
|---|---|---|
| 默认 | `00000000a80425fb` | 可读 600/1000 文件、可 `chown`（两条均已实测） |

## 四、常见误解

❌ 「root 就是万能的，权限检查对它无效。」 → ✅ root 的绕过来自 `CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH`；容器里 `--cap-drop ALL` 的 root 读 600 文件照样 `EACCES`，`--cap-drop DAC_OVERRIDE` 也失败（2.3 节，容器内实测）。

❌ 「euid=0 就一定拥有全部 capability。」 → ✅ capability 还受 Bounding 集限制；容器 root 的 `Bounding set` 只有 14 个，`CAP_SYS_ADMIN` 不在其中，所以 mount 失败（2.6 节，容器内 `capsh --print`）。

❌ 「每次 `read()`/`write()` 都会重新检查文件权限。」 → ✅ 权限只在 `open()` 时检查一次；`chmod 000` 后已打开的 fd 仍可读（2.4 节，宿主 python 实测）。要拿到这种 fd，必须继承或 `SCM_RIGHTS` 传递。

❌ 「`/proc/PID/fd/N` 能绕过权限，直接读别人已打开的文件。」 → ✅ 打开这个符号链接会重新做权限检查；文件 mode 000 时 `cat /proc/PID/fd/N` 仍 `EACCES`（2.4 节，宿主实测）。

❌ 「权限只看文件本身的 mode，和目录无关。」 → ✅ 路径上每一级目录都要有 x（搜索）权限；缺一级就在路径解析阶段 `EACCES`，根本到不了文件（2.3 节，`namei -l` 实测）。

❌ 「`ps` 的 `SUID` 列表示这个进程有 setuid 位。」 → ✅ `ps` 的 `suid` 是 **saved uid**；SUID 程序运行后该列显示 0，是因为 saved uid 被设成文件属主（2.1 节，容器内 SUID 进程实测）。

❌ 「SUID 程序里 euid=0，所以它读任何文件都能成功。」 → ✅ 还要看该进程的 capability（Bounding 集）与 LSM；例如容器里 SUID root 程序 `CapEff` 只有 Docker 默认 14 个 cap，`CAP_SYS_ADMIN` 操作照样失败（2.2、2.5 节）。

❌ 「`no_new_privs` 只影响当前进程。」 → ✅ 它会被子进程继承且不可撤销；`setpriv --no-new-privs sh -c ...` 里再 exec SUID 程序，`NoNewPrivs` 仍为 1、euid 不变（2.2 节，容器内实测）。

| 命令 / 配置 | 作用 | 现象 / 判读 |
