# 02 用户与组数据库：账户、UID 与组从哪来

> **一句话总结**：说清 passwd/shadow/group/gshadow/subuid 五个数据库、UID 空间与 NSS，让 `id` 的每个数字都有出处。

> **本机验证**：⚠️ 部分需容器 —— 宿主可只读观察账户库、文件模式与挂载；`useradd/usermod/userdel/groupadd` 未安装，创建与修改账户须在 `debian:13` 容器内完成（基线 §2、§4）。

| 项目 | 内容 |
|---|---|
| 回答的问题 | 用户名、UID、GID、密码、组成员关系分别存在哪？`id` 的数字从哪来？为什么改用户名不等于改文件属主？ |
| 适合读者 | 会 `chmod` 但说不清「这个 uid 是谁」的工程师；需要创建服务账户、排查 `unknown uid` 的人 |

## 一、先建立直觉

### 1.1 这一章在全局模型中的位置

全书的主干是「进程凭证 × 资源权限 × 检查规则」：

```text
        进程侧                         资源侧
  ruid/euid/suid、rgid、          inode 的 uid/gid + mode
  辅助组、capability                   +
        │                              │
        └────── 内核按规则比较 ────────┘
                     │
              允许 / 拒绝（EACCES/EPERM）
```

本章只负责左、右两侧里**数字的来源**：某个进程的 uid 是 1000，这个 1000 对应哪个账户、哪些组；某个文件的属主是 1001，这个 1001 现在还存在吗。进程如何持有凭证、内核如何比较，分别在 [04-进程凭证与权限检查](04-进程凭证与权限检查.md) 与 [01-权限模型全景](01-权限模型全景.md)。

图：第 1 层（02/03/04）三章各管一段——02 管「名字→数字的数据库」，03 管「数字权限位怎么写」，04 管「进程带着什么数字去做检查」。

### 1.2 五个数据库各管一件事

| 文件 | 管什么 | 每行字段数 | 普通用户可读 |
|---|---|---|---|
| `/etc/passwd` | 账户名、UID、主 GID、家目录、登录 shell | 7 | 是（644） |
| `/etc/shadow` | 密码哈希与密码/账户期限 | 9 | 否（640，`root:shadow`） |
| `/etc/group` | 组名、GID、成员列表 | 4 | 是（644） |
| `/etc/gshadow` | 组密码、组管理员、组成员 | 4 | 否（640，`root:shadow`） |
| `/etc/subuid`、`/etc/subgid` | 给用户命名空间分配的从属 UID/GID 区间 | 3 | 是（644） |

验证（宿主，只读）：

```bash
stat -c '%a %A %U:%G %n' /etc/passwd /etc/shadow /etc/group /etc/gshadow /etc/subuid /etc/subgid
```

在本机执行该命令的输出（本会话处于嵌套用户命名空间，root 文件显示为 `nobody:nogroup`，见基线 §1）：

```text
644 -rw-r--r-- nobody:nogroup /etc/passwd
640 -rw-r----- nobody:nogroup /etc/shadow
644 -rw-r--r-- nobody:nogroup /etc/group
640 -rw-r----- nobody:nogroup /etc/gshadow
644 -rw-r--r-- nobody:nogroup /etc/subuid
644 -rw-r--r-- nobody:nogroup /etc/subgid
```

### 1.3 名字只给人看，数字才给内核

内核的权限判断从来不比较用户名。`ls -l` 里看到的 `demo` 是用户态程序拿 inode 里的数字 UID 去 NSS 反查出来的名字（`来源：man 3 getpwuid`）。

验证（宿主，在当前目录新建一个文件观察）：

```bash
touch numdemo
stat -c '%u %g %n' numdemo
ls -ln numdemo
rm -f numdemo
```

```text
1000 1000 numdemo
-rw-rw-r-- 1 1000 1000 0 10月18日 09:49 numdemo
```

`ls -ln` 的 `-n` 关掉名字反查，直接显示数字。数字一旦比名字更「真实」，就得到一个贯穿本章的结论：**数据库里改名字不影响已存在文件里记录的 uid**；只有改数字才会。

### 1.4 数据库是 NSS 接口，不是四个文本文件

`getent passwd` 走的是名称服务开关（Name Service Switch，NSS），`/etc/nsswitch.conf` 决定按什么顺序查哪些后端。

验证（宿主）：

```bash
grep -E '^(passwd|group|shadow):' /etc/nsswitch.conf
```

```text
passwd:         files systemd
group:          files systemd
shadow:         files systemd
```

本机的 `files` 后端读 `/etc/passwd` 等文件，`systemd` 后端提供 systemd 动态账户。若把 `sssd` 或 `ldap` 加进这一行，同一个 `getent passwd alice` 就会从网络目录服务取数据（取决于 `nsswitch.conf` 的顺序）——这也是为什么「不要用 `grep /etc/passwd` 判断账户是否存在」（见 2.6 与第四节）。

### 1.5 本章边界

- 本章不讲文件权限位与 ACL（[03-文件权限与ACL](03-文件权限与ACL.md)）。
- 本章不讲进程 euid/fsuid 与 `open()` 的检查顺序（[04-进程凭证与权限检查](04-进程凭证与权限检查.md)）。
- 本章不讲 `setuid` 程序如何提权（[05-提权与降权机制](05-提权与降权机制.md)）。
- `/etc/subuid` 只在「格式与存在性」层面介绍，映射规则见 [06-命名空间与uid映射](06-命名空间与uid映射.md)。

## 二、账户库逐字段拆解

### 2.1 `/etc/passwd` 的七个字段

`来源：man 5 passwd` 给出字段顺序：登录名、可选的加密密码、数字 UID、数字 GID、注释字段（gecos）、家目录、命令解释器。

| # | 字段 | 含义 | 常见坑 |
|---|---|---|---|
| 1 | login name | 登录名 | 只用于查找，不是权限判断依据 |
| 2 | 密码 | 现代系统写 `x`，哈希在 `/etc/shadow` | 写 `x` 但 shadow 无对应行 → 账户无效（来源：`man 5 passwd`） |
| 3 | UID | 数字用户 ID | 允许重复（`useradd -o`），内核只看数字 |
| 4 | GID | 主组 ID | 与 UID 不要求相等，见 2.3 |
| 5 | gecos | 注释；可藏 `umask=` 供 `pam_umask` 使用 | 脚本不应按逗号切它做业务字段 |
| 6 | home | 家目录 | 可以不存在（服务账户常见） |
| 7 | shell | 登录 shell | `nologin` 只影响登录，不影响进程以该 uid 运行 |

容器内 `debian:13` 实测（新建 alice）：

```bash
getent passwd alice
getent passwd alice | awk -F: '{printf "name=%s passwd=%s uid=%s gid=%s gecos=%s home=%s shell=%s\n",$1,$2,$3,$4,$5,$6,$7}'
```

输出（容器内）：

```text
alice:x:1000:1000::/home/alice:/bin/bash
name=alice passwd=x uid=1000 gid=1000 gecos= home=/home/alice shell=/bin/bash
```

宿主上的真实账户同样把哈希放在 `/etc/shadow`，`/etc/passwd` 里只写 `x`（下面两条可在宿主直接复现）：

```text
root:x:0:0:root:/root:/bin/bash
nobody:x:65534:65534:nobody:/nonexistent:/usr/sbin/nologin
```

验证（宿主）：`getent passwd root nobody`。

**shell 字段不是安全边界。** 把 shell 设成 `/usr/sbin/nologin` 只阻止交互式登录；服务仍可通过 `setuid`/`setgid` 以该账户运行。反向也成立：shell 是 `/bin/bash` 的账户，如果密码被锁定，一样不能登录。所以，遇到「这个账户为什么还能跑服务」时看这里：查进程 uid，而不是查 shell 字段。

### 2.2 `/etc/shadow` 的九个字段

`来源：man 5 shadow`：每行 9 个冒号分隔字段——登录名、加密密码、最后修改日（距 1970-01-01 的天数）、最小密码年龄、最大密码年龄、过期前警告天数、密码失效后的宽限天数、账户过期日、保留标志。

容器内用「只打印结构、不打印哈希」的方式观测（基线 §3.1 的 alice 示例同源）：

```bash
getent shadow alice | awk -F: '{printf "login=%s hash=<%d 字符> lastchg=%s min=%s max=%s warn=%s inactive=%s expire=%s flag=%s\n",$1,length($2),$3,$4,$5,$6,$7,$8,$9}'
```

输出（容器内，新建 alice，密码字段为 `!`）：

```text
login=alice hash=<1 字符> lastchg=20744 min=0 max=99999 warn=7 inactive= expire= flag=
```

`20744` 是 2026-10-18 距 1970-01-01 的天数；同一天 `chage -l alice` 显示 `Last password change : Oct 18, 2026`（验证：容器内 `chage -l alice`）。所以看到阴影里一个 20xxx 的数字，不要当成 uid 或 gid。

密码字段的几种取值及其含义（来源：`man 5 shadow`）：

| 字段值形态 | 含义 | 结果 |
|---|---|---|
| 空 | 不需要密码 | 是否允许无密码登录由读取该库的程序决定（来源：`man 5 shadow`） |
| `!` 开头（包括 `!!`） | 密码被锁定，剩余字符是锁定前的内容 | 不能用 Unix 密码登录（`man 5 shadow` 只规定 `!` 前缀，`!!` 是同一语义的常见形态） |
| `*` | 不是任何合法 `crypt(3)` 结果 | 不能用 Unix 密码登录 |
| `$y$...` | yescrypt 哈希（本机 `ENCRYPT_METHOD YESCRYPT`） | 可校验密码 |

锁定/解锁的实测（容器内先设真实密码，再锁定）：

```bash
echo 'alice:Secret123' | chpasswd
passwd -S alice
passwd -l alice; getent shadow alice | cut -d: -f2 | cut -c1-4
passwd -u alice; getent shadow alice | cut -d: -f2 | cut -c1-3
```

```text
alice P 2026-10-18 0 99999 7 -1
!$y$
$y$
```

`passwd -S` 的三态：`P` 有可用密码、`L` 锁定、`NP` 无密码（容器内实测：`svcnopw` 依次出现 `L`、`P`、`L`、`NP`）。

**为什么 `/etc/shadow` 是 640、属组是 `shadow`？** 因为校验密码的辅助程序需要读它，但不该让所有用户读：

验证（容器内）：

```bash
getent group shadow
stat -c '%a %A %U:%G %n' /etc/shadow
ls -l /usr/sbin/unix_chkpwd /usr/bin/chage /usr/bin/expiry /usr/bin/passwd
```

```text
shadow:x:42:
640 -rw-r----- root:shadow /etc/shadow
-rwxr-sr-x 1 root shadow 113848 Apr 19  2025 /usr/bin/chage
-rwxr-sr-x 1 root shadow  31256 Apr 19  2025 /usr/bin/expiry
-rwxr-sr-x 1 root shadow  43256 Jun 29  2025 /usr/sbin/unix_chkpwd
-rwsr-xr-x 1 root root   118168 Apr 19  2025 /usr/bin/passwd
```

`unix_chkpwd`、`chage`、`expiry` 是 SGID `shadow` 的程序：进程以调用者身份运行，但有效组变成 `shadow`，因此能读 640 的 shadow；`passwd` 是 SUID root。普通用户直接 `cat /etc/shadow` 会被拒（容器内以 alice 实测：`cat: /etc/shadow: Permission denied`，`getent shadow alice` 返回码 2 且无输出）。

所以，遇到「`su`/`passwd` 能验密码、普通程序读不了 shadow」时看这里：这是 640 + SGID 辅助程序的组合，不是 shadow 文件开放给所有人。

### 2.3 `/etc/group` 与 `/etc/gshadow`：主组、辅助组与 `newgrp`

`来源：man 5 group`：每行 `group_name:passwd:GID:user_list` 四字段。`/etc/gshadow` 同名四字段为组名、加密组密码、管理员列表、成员列表（来源：`man 5 gshadow`）。

容器内实测：

```bash
getent group devs
getent gshadow devs
```

```text
devs:x:2000:alice
devs:!::alice
```

- **主组（primary group）**：`/etc/passwd` 第 4 字段，是新建文件默认的属组，也是 `id` 里 `gid=` 的值。
- **辅助组（supplementary group）**：`/etc/group` 第 4 字段的成员列表，登录时由 PAM/NSS 装进进程的组集合。`id` 的 `groups=` 与 `id -G` 能看到全部。

`useradd` 默认给新用户建一个与用户名相同的私有组（`USERGROUPS_ENAB yes`，验证：`grep -E '^USERGROUPS_ENAB' /etc/login.defs` → `USERGROUPS_ENAB yes`），这也是 `/etc/login.defs` 里 `USERGROUPS_ENAB` 的实际效果：

```bash
useradd -m -u 1000 -s /bin/bash alice
getent group alice
id alice
```

```text
alice:x:1000:
uid=1000(alice) gid=1000(alice) groups=1000(alice),2000(devs)
```

**`newgrp` 的实际效果**：在登录会话里切换「当前组」，只影响该 shell 及其子进程，不回写数据库。容器内实测：

```bash
su - alice -c 'id -gn; id -nG'
su - alice -c 'printf "id -gn\nid -nG\nexit\n" | newgrp devs'
```

```text
alice
alice devs
devs
devs alice
```

两次输出说明：`newgrp devs` 后当前组（`id -gn`）从 `alice` 变成 `devs`，组的枚举顺序也随之变化。注意 `newgrp` 只对当前 shell 生效，重新登录即恢复。

`gpasswd` 管组成员与组密码（本机装了 `gpasswd`，宿主可读、容器内可写）：

```bash
gpasswd -a alice devs    # 加成员
gpasswd -d bob devs      # 删成员
gpasswd -M alice,dave ops # 一次性设置成员列表
getent group devs
```

```text
devs:x:2000:alice
```

`gshadow` 第 2 字段非空表示组密码：非成员执行 `newgrp` 时需要输入组密码（来源：`man 5 gshadow`）。日常几乎不用组密码，`gpasswd -r devs` 可以移除它。

所以，遇到「文件属组为什么不是我的主组」「为什么 `id` 里有而 `getent` 看不到某个成员」时看这里：先分主组/辅助组，再查 `/etc/group` 与 `/etc/gshadow` 的成员/管理员字段。

### 2.4 UID/GID 空间：范围、系统账户、`nobody` 与重复 UID

本机 `/etc/login.defs` 的关键值（宿主实测）：

```text
UID_MIN			 1000
UID_MAX			60000
GID_MIN			 1000
GID_MAX			60000
PASS_MAX_DAYS	99999
PASS_MIN_DAYS	0
PASS_WARN_AGE	7
ENCRYPT_METHOD YESCRYPT
USERGROUPS_ENAB yes
```

同文件里还有被注释掉的系统账户区间默认值（宿主实测，`grep -n 'SYS_UID' /etc/login.defs`）：

```text
107:#SYS_UID_MIN		  101
108:#SYS_UID_MAX		  999
120:#SYS_GID_MIN		  101
121:#SYS_GID_MAX		  999
```

被注释不等于不生效：工具会用内置默认值。容器内实测两种工具的分配策略相反：

```bash
useradd --system --home-dir /var/lib/svcapp --shell /usr/sbin/nologin svcapp
getent passwd svcapp
adduser --system --no-create-home --group svcdeb
getent passwd svcdeb; getent group svcdeb
```

```text
svcapp:x:999:999::/var/lib/svcapp:/usr/sbin/nologin
svcdeb:x:100:101::/nonexistent:/usr/sbin/nologin
svcdeb:x:101:
```

本次实测 `useradd --system` 取到 999（系统账户区间的高端），`adduser --system` 取到 100（`/etc/adduser.conf` 注释里的默认区间起点）。这两个数字都不是固定值，取决于工具版本与现有账户占用（来源：`man 8 useradd`、`man 5 adduser.conf`）；不要硬编码。

容器内系统账户清单的前几项：

```text
root:0:/bin/bash
daemon:1:/usr/sbin/nologin
bin:2:/usr/sbin/nologin
sync:4:/bin/sync
www-data:33:/usr/sbin/nologin
_apt:42:/usr/sbin/nologin
```

验证（容器内）：`awk -F: '$3<1000{print $1":"$3":"$7}' /etc/passwd | head -20`。判断「哪些系统账户能登录」时，用第 7 字段过滤：

```bash
getent passwd | awk -F: '$3<1000 && $7 !~ /(nologin|false|sync)$/ {print $1":"$3":"$7}'
```

容器内输出只有 `root:0:/bin/bash`（宿主同理，验证：同一条命令在宿主执行）。

**`nobody` 与溢出 UID（overflow uid）**：本机 `nobody` 是 65534，`/proc/sys/kernel/overflowuid` 也是 65534。

```bash
cat /proc/sys/kernel/overflowuid /proc/sys/kernel/overflowgid
getent passwd nobody
getent group nogroup
```

```text
65534
65534
nobody:x:65534:65534:nobody:/nonexistent:/usr/sbin/nologin
nogroup:x:65534:
```

溢出 UID 的用途：当一个文件/进程的 uid 在当前用户命名空间里**没有映射**时，用户态程序看到的是 65534。本会话的宿主文件显示 `nobody:nogroup` 就是这个机制（基线 §1），不是文件真的属于 nobody。

**UID 可以重复。** `useradd -o -u <uid>` 允许创建与既有账户共用 UID 的账户。以下在容器内执行
（宿主上本会话没有 `useradd`；宿主 `grep -c ':1000:' /etc/passwd` 为 1）：

```bash
useradd -o -u 1000 -M -s /bin/bash clone
id clone
getent passwd 1000
grep -c ':1000:' /etc/passwd
```

```text
uid=1000(alice) gid=2001(clone) groups=1000(alice)
alice:x:1000:1000::/home/alice:/bin/bash
2
```

两个账户共用 1000，`getent passwd 1000` 只返回第一个匹配，`grep` 能看到两行。这就是 2.6 要展开的「文件查询 ≠ 服务查询」问题的根源。

所以，遇到「进程 uid 是 1001 但 `getent` 说没这个用户」「新用户 uid 为什么从 999 开始」时看这里：查区间配置与实际占用，而不是猜。

### 2.5 `/etc/subuid` 与 `/etc/subgid`：给命名空间用的区间

格式为 `用户名:起始UID:数量`，每行三字段（来源：`man 5 subuid`）。

验证（宿主）：

```bash
cat /etc/subuid; cat /etc/subgid
```

```text
demo:100000:65536
demo:100000:65536
```

含义：允许 `demo` 启动的用户命名空间把宿主上的 100000–165535 映射为容器内的 UID 0–65535。这是 rootless 容器/`unshare -Ur` 的基础；本机 `newuidmap/newgidmap` 未安装且只能做单 uid 映射，具体实测与限制见 [06-命名空间与uid映射](06-命名空间与uid映射.md)。

所以，遇到「rootless 容器里文件属主变成 100000 左右」时看这里：先看 `/etc/subuid` 是否给了区间、容器是否真的用了 userns。

### 2.6 NSS：`getent` 与直接读文件的区别

`getent` 是查询 NSS 的标准入口；它知道 `/etc/nsswitch.conf` 里配置的所有后端。直接 `grep /etc/passwd` 只看到 `files` 后端。

容器内做一个能复现的差异：

```bash
getent passwd 1000
grep ':1000:' /etc/passwd
getent passwd nosuchuser; echo "getent rc=$?"
grep '^nosuchuser:' /etc/passwd; echo "grep rc=$?"
```

```text
alice:x:1000:1000::/home/alice:/bin/bash
alice:x:1000:1000::/home/alice:/bin/bash
clone:x:1000:1001::/home/clone:/bin/bash
getent rc=2
grep rc=1
```

三个可直接记住的结论：

1. **数字反查与文件 grep 结果会不同（重复 UID 时）。** `getent passwd 1000` 只返回一个账户，`grep` 返回两行；在接入了 LDAP/sssd 的机器上，`grep` 甚至一行都看不到。
2. **`getent` 的返回码是权威信号。** 查不到账户返回 2，而 `grep` 无匹配返回 1——脚本里 `if ! getent passwd "$u"` 比 `grep -q` 更可靠。
3. **普通用户查不到 shadow 属正常。** 容器内以 alice 执行 `getent shadow alice` 返回码 2、无输出；这是 `/etc/shadow` 的访问控制生效（验证：容器内 `su alice -c 'getent shadow alice; echo rc=$?'`）。

接入 LDAP/SSSD 时，`/etc/nsswitch.conf` 会变成类似 `passwd: files sss`（来源：`man 5 nsswitch.conf`），账户来自网络目录，本机文件里没有。此时任何「读文件判断账户」的脚本都会漏掉网络账户。

所以，遇到「脚本判断用户存在但服务说不存在」时看这里：统一换成 `getent`，并检查 `nsswitch.conf`。

### 2.7 管理命令表：最小可用示例

宿主未安装 `useradd/usermod/userdel/groupadd`（基线 §4），以下带「容器」标注的示例都在 `debian:13` 内执行（模板见 3.2）。宿主可直接跑观察类命令。

| 命令 | 最小示例 | 作用 | 本机验证方式 |
|---|---|---|---|
| `groupadd` | `groupadd -g 2000 devs` | 建组 | 容器：`getent group devs` |
| `useradd` | `useradd -m -u 1000 -s /bin/bash alice` | 建用户（不设密码） | 容器：`getent passwd alice` |
| `adduser` | `adduser --system --group svc` | Debian 包装脚本，交互式/策略不同 | 容器：需 `apt-get install adduser` |
| `usermod` | `usermod -aG devs alice` | 改属性；`-aG` 追加组 | 容器：`id alice` |
| `userdel` | `userdel bob` | 删账户；`-r` 连家目录 | 容器：`getent passwd bob; echo $?` |
| `groupdel` | `groupdel devs` | 删组 | 容器：`getent group devs; echo $?` |
| `groupmod` | `groupmod -n newname oldname` | 改组名/GID | 容器：`getent group newname` |
| `gpasswd` | `gpasswd -a alice devs` | 组成员管理 | 容器：`getent group devs` |
| `passwd` | `passwd -l alice` / `passwd -S alice` | 设/锁/查密码状态 | 容器：`passwd -S alice` |
| `chage` | `chage -M 90 -m 7 -W 14 -I 30 alice` | 密码与账户期限 | 容器：`chage -l alice` |
| `id` | `id alice` / `id -u` / `id -nG` | 看凭证与组 | 宿主：`id` |
| `groups` | `groups alice` | 看组成员关系 | 宿主：`groups demo` |
| `getent` | `getent passwd 1000` | 按 NSS 查库 | 宿主：`getent passwd demo` |

两个容易踩的坑：

- `usermod -G` **覆盖**辅助组，`usermod -aG` 才是追加。容器内实测：`usermod -G ops alice` 之后 `id alice` 只剩 `ops`；再 `usermod -aG devs alice` 才把 `devs` 加回来。
- `userdel` 默认**不动**家目录与文件；`userdel -r` 才删家目录（容器内 `userdel -r frank` 输出 `userdel: frank mail spool (/var/mail/frank) not found`，家目录消失）。

所以，遇到「加组没生效」「删了用户文件还在」时看这里：先确认命令是覆盖还是追加、有没有 `-r`。

### 2.8 密码与锁定：状态、期限与过期

容器内一次性演示状态变化：

```bash
useradd -m -u 1000 -s /bin/bash alice
echo 'alice:Secret123' | chpasswd
passwd -S alice
passwd -l alice; passwd -S alice
passwd -u alice; passwd -S alice
```

```text
alice P 2026-10-18 0 99999 7 -1
alice L 2026-10-18 0 99999 7 -1
alice P 2026-10-18 0 99999 7 -1
```

密码字段随操作变化（只显示前几个字符）：

| 操作 | 字段变化 | 结果 |
|---|---|---|
| `passwd -l` | `$y$...` → `!$y$...` | 锁定 |
| `passwd -u` | `!$y$...` → `$y$...` | 解锁 |
| `usermod -L` | 在已锁定字段上**不会**重复加 `!`（实测第二次仍是 `!$y$`） | 幂等锁定 |
| `passwd -d` | 清空字段 | 无密码（危险） |
| `usermod -p '*'` | 写入字面 `*` | 不可用密码登录 |

容器内实测锁定后的字段：

```text
passwd -l 后第2字段: !$y$
```

**密码期限**用 `chage` 修改，写回 shadow 的第 3–7 字段：

```bash
chage -M 90 -m 7 -W 14 -I 30 alice
chage -l alice
getent shadow alice | awk -F: '{printf "lastchg=%s min=%s max=%s warn=%s inactive=%s\n",$3,$4,$5,$6,$7}'
```

```text
Last password change					: Oct 18, 2026
Password expires					: Jan 16, 2027
Password inactive					: Feb 15, 2027
Account expires						: never
Minimum number of days between password change		: 7
Maximum number of days between password change		: 90
Number of days of warning before password expires	: 14
lastchg=20744 min=7 max=90 warn=14 inactive=30
```

账户过期日（第 8 字段）用 `chage -E` 或 `usermod -e` 设置，容器内实测 `chage -E 2027-01-01 alice` 写入 `expire(字段8)=20819`；过期账户登录会被拒：

```bash
useradd -M -u 1600 -s /bin/bash expired
chage -E 2020-01-01 expired
su - expired -c 'id'
```

```text
Your account has expired; please contact your system administrator.
su: Authentication failure
```

注意区分两件事：**密码过期**（第 5 字段到期，登录时会要求改密码）与**账户过期**（第 8 字段到期，直接拒绝登录，来源：`man 5 shadow`）。前者通常可自助恢复，后者必须管理员改期限。

所以，遇到「账户密码正确但登录被拒」时看这里：先 `chage -l` 查两个过期时间，再看密码字段是不是 `!` 开头。

### 2.9 家目录、`/etc/skel` 与默认 umask 的来源

`useradd -m` 会创建家目录、复制 `/etc/skel`、按默认模式设权限。默认值来自三处：

```bash
useradd -D
grep -E '^(SKEL|HOME|SHELL|CREATE_MAIL_SPOOL)' /etc/default/useradd
```

```text
GROUP=100
GROUPS=
HOME=/home
INACTIVE=-1
EXPIRE=
SHELL=/bin/sh
SKEL=/etc/skel
USRSKEL=/usr/etc/skel
CREATE_MAIL_SPOOL=no
LOG_INIT=yes
```

家目录模式来自 `/etc/login.defs` 的 `HOME_MODE`（宿主实测：`HOME_MODE 0700`，验证：`grep -n HOME_MODE /etc/login.defs`）；`adduser` 的默认值写在 `/etc/adduser.conf` 的注释里（容器内实测）：

```text
# Default: DIR_MODE=0700
# Default: SYS_DIR_MODE=0755
# Default: DSHELL=/bin/bash
# Default: DHOME=/home
# Default: FIRST_SYSTEM_UID=100, LAST_SYSTEM_UID=999
# Default: USERGROUPS=yes
```

容器内新建家目录与 skel 复制的证据：

```text
700 drwx------ alice:alice /home/alice
.bash_logout
.bashrc
.profile
644 /home/alice/.bashrc
```

**默认 umask 不是账户库里的字段**，而是登录会话时由 shell 或 PAM 设置：本机 `/etc/pam.d/common-session` 有一行 `session optional pam_umask.so`（宿主与容器一致，验证：`grep pam_umask /etc/pam.d/common-session`）。shell 侧也会设 umask：登录 shell 读 `/etc/profile`，交互式非登录 shell 读 `~/.bashrc`（来源：`man 1 bash` 的 INVOCATION 一节），排查时要分清是 PAM 还是 shell 配置生效。所以「新用户默认 umask」要在 PAM/login.defs/`~/.bashrc` 三处一起看，细节与实测矩阵见 [03-文件权限与ACL](03-文件权限与ACL.md) 的 umask 一节。

所以，遇到「新用户家目录权限为什么是 700」「默认 umask 为什么是 002」时看这里：`/etc/login.defs` + `/etc/default/useradd` + PAM `pam_umask` 三处。

### 2.10 服务账户实践：`--system`、`nologin`、`/var/lib`

服务账户的典型配方：

```bash
useradd --system --home-dir /var/lib/svcapp --shell /usr/sbin/nologin svcapp
getent passwd svcapp
id svcapp
getent passwd | awk -F: '$3<1000 && $7 !~ /(nologin|false|sync)$/ {print $1}'
```

容器内实测：

```text
svcapp:x:999:999::/var/lib/svcapp:/usr/sbin/nologin
uid=999(svcapp) gid=999(svcapp) groups=999(svcapp)
```

三条实践经验都能在本机复现：

1. **home 可以不存在。** 容器内 `ls -ld /var/lib/svcapp` 报 `No such file or directory`，`su - svcapp -c 'echo x'` 输出 `su: warning: cannot change directory to /var/lib/svcapp: No such file or directory`，随后 `This account is currently not available.`。
2. **`nologin` 不是「不能运行」**：它阻止的是登录 shell；systemd 服务或 `setuid` 调用仍可用该账户启动进程。审计时看进程的 uid（见 [04-进程凭证与权限检查](04-进程凭证与权限检查.md)），而不是只看 shell 字段。
3. **不要给服务账户 `-m` 到 `/home`**：家目录应是 `/var/lib/<service>` 或 `/nonexistent`，避免 `/home` 的 `nosuid` 等挂载属性影响（本机 `/home` 挂载选项见 3.1）。

以 nginx 为例：官方 `nginx:1.20-alpine` 镜像内 `id nginx` 是 `uid=101(nginx) gid=101(nginx)`（基线 §3.8），配置里默认 `user nginx;`。这解释了 08 章「worker 以 uid 101 写目录失败」的现象，账户是怎么来的只到这一步，nginx 配置展开见 [08-Nginx用户与权限实战](08-Nginx用户与权限实战.md)。

所以，遇到「服务账户明明存在但服务起不来」时看这里：确认 home 是否存在、shell 是否 nologin、以及进程实际以哪个 uid 运行。

### 2.11 改名、删除与孤儿文件

**改名不改数字**：`usermod -l` 只改第 1 字段，UID、家目录、文件属主都不动。

```bash
useradd -m -u 1002 -s /bin/bash carol
su - carol -c 'echo hello > /home/carol/note.txt'
ls -ln /home/carol/note.txt
usermod -l dave carol
getent passwd dave
ls -l /home/carol/note.txt
```

```text
-rw-rw-r-- 1 1002 1002 6 Oct 18 01:39 /home/carol/note.txt
dave:x:1002:1002::/home/carol:/bin/bash
-rw-rw-r-- 1 dave carol 6 Oct 18 01:39 /home/carol/note.txt
```

`ls -l` 显示的名字变了（因为数字 1002 现在反查为 dave），但家目录仍是 `/home/carol`——`usermod -l` 不会改 home 字段，也不会重命名目录。

**删除账户后文件变孤儿**：

```bash
useradd -m -u 1003 -s /bin/bash erin
su - erin -c 'echo erin > /home/erin/e.txt'
userdel erin
getent passwd erin; echo "rc=$?"
ls -ln /home/erin/e.txt
find /home -maxdepth 1 -type d -nouser
```

```text
rc=2
-rw-rw-r-- 1 1003 1003 5 Oct 18 01:39 /home/erin/e.txt
/home/erin
```

文件还在，属主数字 1003 还在，只是没有名字了。如果以后新用户正好拿到 1003，他就会「继承」这些文件——这就是 `userdel -r` 和离职账户处理要成对做的原因。审计孤儿文件的命令见 [10-账户安全基线与审计](10-账户安全基线与审计.md)。

所以，遇到「同名用户能看到旧文件」「改名后家目录没变」时看这里：名字是查出来的，数字是存下来的。

## 三、动手验证

### 3.1 宿主上能做的（只读）

```bash
id
getent passwd demo root nobody
getent group docker sudo nogroup
grep -E '^(passwd|group|shadow):' /etc/nsswitch.conf
grep -E '^(UID_MIN|UID_MAX|GID_MIN|GID_MAX|USERGROUPS_ENAB|ENCRYPT_METHOD|UMASK)' /etc/login.defs
grep -n 'SYS_UID\|SYS_GID' /etc/login.defs
stat -c '%a %A %U:%G %n' /etc/passwd /etc/shadow /etc/group /etc/gshadow
cat /etc/subuid /etc/subgid
findmnt -T . -o OPTIONS
```

每条要看什么：

- `id` 的 `uid/gid/groups` 是本章所有数字的入口；本机额外有一个 `65534(nogroup)` 辅助组。
- `getent passwd` 两个账户足以核对 7 字段；`nobody` 的 home 是 `/nonexistent`。
- `nsswitch.conf` 决定 `getent` 查哪些后端；本机是 `files systemd`。
- 本机 `/etc/login.defs` 没有 `UMASK` 项（验证：`grep -n UMASK /etc/login.defs` 无输出）；不同发行版的差异用同一条 `grep` 确认，别把缺失当错误。
- `SYS_UID` 行是注释，但工具仍按默认 101–999 分配系统账户。
- `/etc/shadow` 出现在 `stat` 里只输出模式，不输出内容；**不要 `cat` 它**。
- `findmnt` 确认当前工作区所在挂载带 `nosuid,nodev`（本机输出 `rw,nosuid,nodev,relatime,errors=remount-ro`），这会影响放在家目录的 SUID 程序（见 03）。

### 3.2 容器内做完整流程

宿主没有 `useradd`，用 `--rm` + 唯一 name 的一次性容器（模板来自基线 §2），不要挂载 `/`，不要把容器里的账户写入宿主：

> 需要：docker

```bash
docker run --rm --name learnugroup-02-$$ -v "$PWD":/w debian:13 bash -c '
  set -e
  export DEBIAN_FRONTEND=noninteractive
  apt-get update -qq >/dev/null 2>&1
  apt-get install -y -qq --no-install-recommends acl attr libcap2-bin adduser >/dev/null 2>&1

  groupadd -g 2000 devs
  useradd -m -u 1000 -s /bin/bash alice
  useradd -m -u 1001 -s /bin/bash bob
  usermod -aG devs alice; usermod -aG devs bob
  id alice; getent group devs
  getent shadow alice | cut -d: -f2        # 只取密码字段，且此时应为 !
  passwd -S alice
  chage -M 90 -W 14 alice; chage -l alice
  useradd --system --home-dir /var/lib/svcapp --shell /usr/sbin/nologin svcapp
  getent passwd svcapp
  userdel bob; getent passwd bob || echo "bob 已删除（rc=$?）"
  find /home -maxdepth 1 -type d -nouser
'
```

在容器内要看的点：

- `id alice` 的 `groups=` 是否包含 `devs`；`getent group devs` 的成员列表是否与 `id` 一致。
- `getent shadow alice | cut -d: -f2` 只取第 2 字段；`!` 表示无可用密码。
- `chage -l` 的四个日期是否与 `chage -M/-W` 参数对应。
- `svcapp` 的 uid 是否落在 999 附近、shell 是否 `nologin`。
- `userdel` 后 `getent passwd` 的退出码是否为 2、`/home` 下是否出现 `-nouser` 目录。

## 四、常见误解

1. ❌ 用户名就是身份 → ✅ 内核只看 UID/GID，用户名只是 NSS 反查结果；同一 UID 可以有多个账户（验证：容器内 `useradd -o -u 1000 clone` 后 `id clone` 与 `getent passwd 1000`）。
2. ❌ 改了用户名，文件属主也会跟着变 → ✅ `usermod -l dave carol` 只改第 1 字段，文件的数字属主仍是 1002，只是 `ls -l` 反查出的名字变成 dave（验证：2.11 输出）。
3. ❌ 删掉用户，文件就安全了 → ✅ `userdel erin` 后文件仍在、属主数字 1003 仍在，`find /home -maxdepth 1 -type d -nouser` 能找到孤儿目录（验证：2.11）。
4. ❌ 新用户没设密码 = 没有密码就能登录 → ✅ `useradd` 生成的密码字段是 `!`，`passwd -S` 显示 `L`，属于锁定状态（验证：容器内 `passwd -S svcnopw` → `L`）。
5. ❌ `usermod -G` 是「加组」 → ✅ 它覆盖整个辅助组列表；追加要用 `-aG`（验证：容器内 `usermod -G ops alice` 后 `id alice` 只剩 ops）。
6. ❌ `adduser` 就是 `useradd` 的别名 → ✅ `adduser` 是 Debian 独立的 Perl 包装脚本（容器内 `head -1 /usr/sbin/adduser` 为 `#!/usr/bin/perl -T`），默认策略与 UID 分配不同（2.4 实测 100 vs 999）。
7. ❌ 用 `grep /etc/passwd` 就能判断账户是否存在 → ✅ 应使用 `getent`；重复 UID 时 `grep` 与 `getent passwd 1000` 结果不同，接入 LDAP 后 `grep` 完全失效（验证：2.6）。
8. ❌ `/etc/shadow` 是 640 只是「怕别人看」 → ✅ 属组 `shadow` 配合 SGID 程序（`unix_chkpwd` 等）在不暴露哈希的前提下校验密码；普通用户 `cat` 被拒（验证：2.2）。
