## 一、先建立直觉

### 1.1 先分清 `EACCES` 与 `EPERM`

两个错误都叫「权限不够」，但原因完全不同：

| 错误码 | 编号 | 典型含义 | 常见触发 |
|---|---|---|---|
| `EACCES` | 13 | DAC 规则拒绝：mode/ACL/父目录 x 不满足 | 打开 600 文件、目录缺 x、执行无 x 的文件、bind 特权端口 |
| `EPERM` | 1 | 操作本身需要特权/特殊条件，不只是 DAC | `chmod`/`chown` 非自己的文件、sticky 目录删别人文件、`chattr +i` 后写、某些 capability 缺失 |
| `ENOENT` | 2 | 路径不存在（常被误判为权限） | docroot 拼错、符号链接目标缺失 |
| `EROFS` | 30 | 只读文件系统 | `:ro` 挂载、只读卷 |
| `EISDIR`/`ENOTDIR` | 21/20 | 路径类型不匹配 | 组件不是目录/却是目录 |

验证：同一台机器上分别构造 `EACCES` 与 `EPERM`。

```bash
mkdir -p errtest/dir700
printf 'readable-by-other\n' > errtest/dir700/x && chmod 644 errtest/dir700/x
printf 'secret600\n' > errtest/f600
printf '#!/bin/sh\necho run\n' > errtest/noexec && chmod 644 errtest/noexec
docker run --rm --name learnugroup-09-prep -v "$PWD/errtest":/e alpine:latest sh -c 'chown 101:101 /e/f600; chmod 600 /e/f600; chown 101:101 /e/dir700; chmod 700 /e/dir700'
python3 - <<'PY'
import errno, os, subprocess
def run(label, fn):
    try:
        fn(); print(f"{label}: OK")
    except OSError as e:
        print(f"{label}: errno={e.errno} {errno.errorcode.get(e.errno)} {e.strerror}")
run("open 600 owned-by-101", lambda: open("errtest/f600").read())
run("chmod 600 owned-by-101", lambda: os.chmod("errtest/f600", 0o644))
run("open dir700/x (no x on dir)", lambda: open("errtest/dir700/x").read())
try:
    subprocess.run([os.path.abspath("errtest/noexec")], check=True)
    print("exec noexec: OK")
except OSError as e:
    print(f"exec noexec: errno={e.errno} {errno.errorcode.get(e.errno)} {e.strerror}")
PY
```

在本机执行上述命令的输出：

```text
open 600 owned-by-101: errno=13 EACCES Permission denied
chmod 600 owned-by-101: errno=1 EPERM Operation not permitted
open dir700/x (no x on dir): errno=13 EACCES Permission denied
exec noexec: errno=13 EACCES Permission denied
```

`chmod` 失败是 `EPERM` 而不是 `EACCES`：内核在 `chmod` 路径里先检查「是不是文件属主或是否有 `CAP_FOWNER`」，不满足直接 `EPERM`，与文件的 mode 位无关。

### 1.2 三问：谁在访问、访问什么、规则是什么

任何权限故障都先回答三问，顺序不能反：

1. **谁在访问**：真实运行的那个进程是谁？`id` 是 shell 的，不是服务的；要用 `ps -o uid,euid,suid` 或 `/proc/<pid>/status` 看目标进程。容器里还要看容器内 uid。
2. **访问什么**：目标文件/目录/socket/端口的**真实 inode** 或内核对象。绑定挂载要看宿主 inode；容器里 `ls -ln` 与宿主的名字解析可以不同（uid 数字相同）。
3. **规则是什么**：DAC（属主/属组/other/ACL）、capability、挂载选项（`ro`、`nosuid`、`noexec`）、LSM（AppArmor/SELinux），以及容器/命名空间带来的 uid 映射。

```text
        ┌───────────────────────┐
        │ ① 主体：谁在访问       │
        │ id / ps / /proc/PID   │
        └──────────┬────────────┘
                   │
        ┌──────────▼────────────┐
        │ ③ 规则：内核怎么检查    │
        │ mode/ACL/cap/mount/LSM │
        └──────────┬────────────┘
                   │
        ┌──────────▼────────────┐
        │ ② 资源：访问什么       │
        │ ls -ln/stat/namei     │
        └───────────────────────┘
```

> 图：排障视角的三要素。先定位主体与资源，再判断哪条规则拒绝；三个节点任何一个没确认，修法都会偏。

### 1.3 五分钟诊断流程

```text
第 0 分钟：记录原始错误
  命令 + 完整报错 + errno（"Permission denied"=EACCES，"Operation not permitted"=EPERM）
  ↓
第 1 分钟：谁在访问
  id；ps -o pid,uid,euid,suid,args -p PID；grep -E '^(Uid|Gid|CapEff|NoNewPrivs)' /proc/PID/status
  容器场景：docker exec C id；docker top C
  ↓
第 2 分钟：访问什么
  ls -ln PATH；stat -c '%a %u:%g %n' PATH；namei -l PATH
  逐级看：哪一级目录缺 x？文件缺 r/w？属主/属组是否匹配？
  ↓
第 3 分钟：规则还有什么
  getfacl PATH；getcap PATH（容器内）；findmnt -T PATH；lsattr PATH
  LSM：dmesg | tail；journalctl -k | tail；aa-status
  ↓
第 4 分钟：容器/命名空间
  容器内 uid 是否等于宿主 inode 属主？挂载是否 :ro/nosuid？镜像里有没有该用户？
  入口命令是否以 root 启动后降权？
  ↓
第 5 分钟：改一侧并复验
  改资源侧（chmod/chown/setfacl）或改主体侧（-u/User/capability/组）
  重跑同一命令；记录修复；补监控/测试
```

> 图：五分钟诊断流程。**先确定 errno 和主体，再看路径逐级权限**，不要一上来就 `chmod -R 777`。

## 二、工具、案例与容器特有问题

### 2.1 诊断工具箱

| 工具 | 看什么 | 本机可用性 |
|---|---|---|
| `id`、`getent passwd/group` | 当前 shell 的 uid/gid/组；账户是否存在 | ✅ |
| `ps -o pid,uid,euid,suid,args -p PID` | 目标进程的真实/有效/保存 uid | ✅（部分基础镜像没有 `ps`，用 `/proc`） |
| `/proc/PID/status` | `Uid`/`Gid`/`CapEff`/`NoNewPrivs`/`Groups` | ✅ |
| `ls -ln` | 文件属主、属组的**数字**与 mode | ✅ |
| `stat -c '%a %u:%g %n'` | mode 与 uid/gid 数字 | ✅ |
| `namei -l PATH` | 路径每一级的 mode/属主，定位缺 x 的目录 | ✅ |
| `getfacl -p PATH` | ACL 条目、mask、`#effective` | ✅ |
| `getcap PATH`、`getcap -r /` | 文件 capability | ❌ 宿主未安装；容器内 `libcap2-bin` 可装 |
| `lsattr PATH` | 扩展属性（`+i`/`+a`） | ✅（读他属主文件的 flags 会返回 EACCES） |
| `findmnt -T PATH` | 挂载选项（`ro`/`nosuid`/`noexec`） | ✅ |
| `ss -xlpn` | Unix socket 监听者与路径 | ✅ |
| `dmesg` | LSM/内核拒绝记录 | ⚠️ 需要 `CAP_SYSLOG`，本机返回 EPERM |
| `journalctl -k`/`journalctl -u 服务` | 内核与服务日志 | ✅ 命令存在；无 systemd 服务可查 |
| `strace -e trace=file` | 具体哪个 syscall 失败 | ❌ 宿主未安装；容器内可装 |
| `ausearch -m avc` | SELinux 拒绝审计 | ❌ 宿主未安装 |
| `docker exec C ...` | 容器内视角的 uid/文件/日志 | ✅ |

验证：本机工具缺失与权限限制。

```bash
for c in getcap strace ausearch; do printf '%-10s ' "$c"; command -v "$c" || echo MISSING; done
dmesg 2>&1 | head -1
lsattr errtest/f600 2>&1
```

在本机执行上述命令的输出：

```text
getcap     MISSING
strace     MISSING
ausearch   MISSING
dmesg: read kernel buffer failed: 不允许的操作
lsattr: 权限不够 While reading flags on errtest/f600
```

`dmesg` 需要 `CAP_SYSLOG`（或被 `kernel.dmesg_restrict` 限制），`lsattr` 读取别人文件的 flags 也会被 DAC 拒绝；工具不可用时要换路径（容器内 root、有权限的账户）。

### 2.2 现象 → 命令速查表

| 现象 | 先跑这些命令 | 关键点 |
|---|---|---|
| `cat: ...: Permission denied` | `ls -ln F; namei -l F; stat -c '%a %u:%g' F` | 13=EACCES；看文件 r 与每级目录 x |
| `cd: ...: Permission denied` | `ls -ldn D; namei -l D` | 目录缺 x（进入）或 r（列目录） |
| `bash: ./x: Permission denied` | `ls -ln x; findmnt -T .` | 文件缺 x；或挂载 `noexec`；脚本 shebang 解释器不可执行 |
| 服务启动 `Permission denied` | `journalctl -u SVC; ps -o uid,euid,suid -p PID; grep CapEff /proc/PID/status` | 看服务真实 uid 与 capability，不看 shell |
| bind 80 失败 | `cat /proc/sys/net/ipv4/ip_unprivileged_port_start; getcap $(command -v BIN)` | 1024 起需 `CAP_NET_BIND_SERVICE` |
| 日志写不进去 | `ls -ldn LOGDIR; ls -ln LOGFILE; ps -o uid -p PID` | 目录 w+x 或已打开 fd；logrotate 后属主变化 |
| docker 卷写失败 | `ls -ldn HOSTDIR; docker run --rm -v ... id` | 宿主 inode 属主 vs 容器 uid（07 章） |
| 容器 root 创建的文件读不了 | `ls -ln; stat -c '%u:%g'` | 本会话显示 65534 是 userns 溢出；用容器内数字 |
| `su`/`sudo` 失败 | `id; getent passwd USER; passwd -S USER; journalctl -u sshd` | 账户锁定、PAM、no_new_privs、sudoers |
| ssh key 被拒 | `ls -ld ~/.ssh; ls -ln ~/.ssh/authorized_keys; journalctl -u sshd` | StrictModes：家目录/文件 mode 与属主 |
| `git ... dubious ownership` | `ls -ldn $(git rev-parse --show-toplevel)`；`git -C D status` | 仓库属主 ≠ 当前用户；safe.directory |
| cron 任务失败 | `journalctl -u cron; grep -n . /var/log/syslog`；任务里用绝对路径 | cron 环境变量/工作目录/家目录与登录 shell 不同 |
| systemd 服务看不到 home | `systemctl show SVC -p ProtectHome,ProtectSystem,User` | `ProtectHome=`、`ProtectSystem=` 会隐藏/只读路径 |
| 写只读挂载 | `findmnt -T PATH`；`touch PATH/x` | 报 `Read-only file system`（EROFS），不是 EACCES |
| NFS 上 root 写失败 | `findmnt -T MOUNT; grep nfs /proc/mounts` | 服务端 `root_squash` 把 root 映射成 nobody（本机无 NFS，未验证） |
| Unix socket 连接失败 | `ls -ln SOCK; ss -xlpn; stat -c '%a' SOCK` | socket 文件需要 w（`man 7 unix`） |
| docker API 被拒 | `ls -ln /var/run/docker.sock; getent group docker; id` | socket 660 root:docker；组内成员才可读写 |
| mysql/postgres 数据目录失败 | `ls -ldn DATADIR; ps -o uid -p PID; getent passwd DBUSER` | 数据目录属主必须匹配服务 uid |
| 上传目录失败 | `ls -ldn UPLOAD; ps -o uid -p PID` | worker/服务 uid 需要目录 w+x |
| 权限改完仍失败 | `namei -l`、`getfacl`、`findmnt`、`getcap`、LSM 日志 | 还有 ACL mask、ro/noexec、capability、LSM 四层 |

### 2.3 案例集

每个案例固定给 **现象 / 根因 / 诊断命令与输出 / 修复 / 如何预防**。案例 1~7 在本机复现过（部分在容器内），案例 8~10 标注了「未验证」并给出替代验证方式。

#### 案例 1：普通用户读 600 文件被拒（EACCES）

**现象**：`cat: f600: Permission denied`；同一文件 root 能读。

**根因**：文件属主 101、mode 600；访问者 uid 1000 既非属主也不在属组，other 无 r。

**诊断命令与输出**：

```bash
printf 'secret600\n' > errtest/f600
docker run --rm --name learnugroup-09-c1 -v "$PWD/errtest":/e alpine:latest sh -c 'chown 101:101 /e/f600; chmod 600 /e/f600; ls -ln /e/f600'
python3 -c 'import os
try: open("errtest/f600").read()
except OSError as e: print(e.errno, e.strerror)'
```

在本机执行上述命令的输出（第一段容器内，第二段宿主）：

```text
-rw-------    1 101      101              10 Oct 18 01:49 /e/f600
13 Permission denied
```

**修复**：按需求选一侧——资源侧 `chmod 644 f600` 或 `setfacl -m u:1000:r f600`；主体侧改用属主/属组访问（`-u 101`、加入组、`chown` 给服务用户）。

**如何预防**：部署时固定服务 uid/组；共享文件用组权限或 ACL，不用 777；把「文件属主与消费者 uid」写进部署检查。

#### 案例 2：目录缺 x 导致文件读不了（EACCES，易误判为文件权限）

**现象**：文件本身 644，其他用户仍无法读；`namei -l` 显示某一级目录是 700。

**根因**：路径解析需要对每一级目录有 `x`（搜索权限），与文件最终 mode 无关；内核在 `path_resolution` 阶段就返回 `EACCES`（来源：`man 7 path_resolution`：If the process does not have search permission on the current lookup directory, an EACCES error is returned）。

**诊断命令与输出**：

```bash
mkdir -p errtest/dir700 && printf 'x\n' > errtest/dir700/x && chmod 644 errtest/dir700/x
docker run --rm --name learnugroup-09-c2 -v "$PWD/errtest":/e alpine:latest sh -c 'chown 101:101 /e/dir700; chmod 700 /e/dir700'
namei -l errtest/dir700/x
```

在本机执行上述命令的输出：

```text
f: errtest/dir700/x
drwxrwxr-x demo demo  errtest
drwx------ nobody nogroup dir700
                           x - 权限不够
```

**修复**：给目录补 x（`chmod 711 dir700` 或 ACL `setfacl -m u:1000:x dir700`）；不要直接 777。

**如何预防**：部署时检查 docroot 每一级目录的 x；用 `namei -l` 作为上线检查项；容器镜像里别用 700 的父目录包住需要读取的文件。

#### 案例 3：sticky 目录里删别人的文件（EPERM，容器内复现）

**现象**：`rm: cannot remove '/tmp/shared/a.txt': Operation not permitted`；目录是 1777，当前用户对目录有 w。

**根因**：sticky 位（`t`）限制删除：只有文件属主、目录属主或 root 能删；`EPERM` 不是 `EACCES`。

**诊断命令与输出**：

```bash
docker run --rm --name learnugroup-09-c3 debian:13 sh -c 'mkdir -p /tmp/shared && chmod 1777 /tmp/shared && useradd -m alice >/dev/null 2>&1 && useradd -m bob >/dev/null 2>&1 && su alice -c "echo a > /tmp/shared/a.txt" && su bob -c "rm -f /tmp/shared/a.txt" 2>&1; ls -ln /tmp/shared'
```

在本机执行上述命令的输出（容器内）：

```text
rm: cannot remove '/tmp/shared/a.txt': Operation not permitted
total 4
-rw-rw-r-- 1 1000 1000 2 Oct 18 01:42 a.txt
```

**修复**：让文件属主自己删；由目录属主/root 删；需要多人协作时改用组 + SGID 目录（`2775`），用 ACL 控制写，而不是 1777。

**如何预防**：共享目录优先 SGID + 组，不要用 1777；理解 sticky 只保护删除，不保护读。

#### 案例 4：Docker 绑定挂载 uid 不匹配（EACCES，容器内复现）

**现象**：容器以 `-u 101:101` 运行，`touch /data/x: Permission denied`；宿主目录属主 1000、mode 750。

**根因**：绑定挂载不翻译 uid；容器进程 fsuid=101 对宿主 inode 只能是 other，other 无 w。

**诊断命令与输出**：

```bash
mkdir -p demo/data && chmod 750 demo/data
docker run --rm --name learnugroup-09-c4 -u 101:101 -v "$PWD/demo/data":/data alpine:latest sh -c 'id; touch /data/x'
ls -ldn demo/data
```

在本机执行上述命令的输出（第一段容器内，第二段宿主）：

```text
uid=101 gid=101 groups=101
touch: /data/x: Permission denied
drwxr-x--- 2 1000 1000 4096 10月18日 09:39 demo/data
```

**修复**：`docker run --rm -v "$PWD/demo/data":/data alpine:latest chown 101:101 /data`，或改用 `-u 1000:1000`，或 compose `user:`/`group_add:`（详见 [07-Docker用户与权限实战](07-Docker用户与权限实战.md) §2.4 的对比表）。

**如何预防**：部署前固定容器 uid 并 chown 数据目录；CI 里加「容器内写一次测试文件」的 smoke test；不要把「容器 root 能写」当作非 root 也能写。

#### 案例 5：容器 root 创建的文件，属主与删除权限要分开看

**现象 A**：容器 root 在绑定目录创建文件，`ls -ln` 显示属主 65534；宿主普通用户能读（mode 644 的 other 位）但不能写，`chown`/`chmod` 报 `EPERM`。若文件 mode 是 600/640，连读也会 `EACCES`。
**现象 B**：同样文件在宿主可写父目录里 `rm` 成功，但在 root 属主的 755 目录里删除失败。

**根因**：现象 A 是 uid 不匹配（容器 root=宿主 root，本会话 userns 只映射 1000，故显示 65534；文件 mode 644 时其实 other 可读，只有写/改属主受限）；现象 B 是 `unlink` 只检查父目录 w+x 与 sticky，不检查文件属主。

**诊断命令与输出**：

```bash
mkdir -p demo/mnt && chmod 777 demo/mnt
docker run --rm --name learnugroup-09-c5 -v "$PWD/demo/mnt":/w alpine:latest sh -c 'touch /w/root-created; ls -ln /w/root-created'
ls -ln demo/mnt/root-created
rm -f demo/mnt/root-created; echo "rm rc=$?"
```

在本机执行上述命令的输出（第一行容器内，后两行宿主）：

```text
-rw-r--r--    1 0        0                0 Oct 18 01:49 /w/root-created
-rw-r--r-- 1 65534 65534 0 10月18日 09:49 demo/mnt/root-created
rm rc=0
```

对照：root 属主的 755 `.git` 目录内，普通用户删除失败：

```text
rm: 无法删除 'repo/.git/index': 权限不够
```

**修复**：用容器清理 root 属主产物（`docker run --rm -v "$PWD":/w ... rm -rf`）；需要宿主直接管理时 chown 给宿主用户；不要用 `sudo rm -rf` 一把梭。

**如何预防**：容器写宿主目录时默认按「非 root + 明确 uid」设计；目录属主与容器 uid 对齐；清理逻辑放进部署脚本。

#### 案例 6：非 root 启动 nginx 失败（EACCES/EPERM 的启动期表现，容器内复现）

**现象**：`-u 101:101` 启动 `nginx:1.20-alpine` 报 `[warn] "user" directive ... ignored` 与 `[emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)`。

**根因**：master 非 root 时不能 setuid worker（`user` 被忽略），且默认 pid/日志/缓存路径属于 root，非 root 无法 mkdir/open。

**诊断命令与输出**：

```bash
docker run --rm --name learnugroup-09-c6 -u 101:101 --entrypoint nginx nginx:1.20-alpine -g 'daemon off;'
```

在本机执行上述命令的输出（容器内）：

```text
2026/10/18 01:49:40 [warn] 1#1: the "user" directive makes sense only if the master process runs with super-user privileges, ignored in /etc/nginx/nginx.conf:2
nginx: [warn] the "user" directive makes sense only if the master process runs with super-user privileges, ignored in /etc/nginx/nginx.conf:2
2026/10/18 01:49:40 [emerg] 1#1: mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)
nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)
```

**修复**：按 [08-Nginx用户与权限实战](08-Nginx用户与权限实战.md) §2.10 的非 root 配方改 pid/日志/temp 路径到可写目录、监听 8080、去掉 `user` 指令；或继续用 root master + worker 降权。

**如何预防**：容器镜像若要以非 root 运行，构建时就把路径改好（nginx-unprivileged 类镜像即此思路）；启动脚本先做可写性检查。

#### 案例 7：unix socket 权限导致 502（容器内复现）

**现象**：nginx 反代 php-fpm/socket 后端，返回 502；error.log 是 `connect() ... failed (13: Permission denied)`。

**根因**：worker 对上游 socket 文件没有写权限；`man 7 unix`：connecting to a stream socket object requires write permission on that socket。

**诊断命令与输出**（完整复现见 [08-Nginx用户与权限实战](08-Nginx用户与权限实战.md) §2.7）：

```bash
docker logs learnugroup-08-unix 2>&1 | grep -E 'connect\(\)|Permission denied' | tail -1
ls -ln demo/sockproxy/sock/app.sock
```

在本机执行上述命令的输出：

```text
[crit] 32#32: *1 connect() to unix:/sock/app.sock failed (13: Permission denied) while connecting to upstream, ...
srwx------ 1 1000 1000 0 10月18日 09:41 demo/sockproxy/sock/app.sock
```

**修复**：`chmod 660`/`666`（谨慎）或改成同组可写（`chown :GROUP` + `660`），给 nginx worker 与后端用户共同组；目录也要有 x。

**如何预防**：php-fpm 的 `listen.owner/group/mode` 与 nginx worker uid 成组设计；把 socket 权限纳入部署检查，不靠 777。

#### 案例 8：git 仓库属主不对（`dubious ownership`，本机复现）

**现象**：`git status` 报「检测到可疑的仓库所有权」，拒绝操作。

**根因**：仓库/`.git` 的属主与当前用户不一致（本机是容器 root 在绑定目录创建的仓库，宿主看到属主 65534），git 为防止恶意仓库执行 hook 而拒绝解析（来源：`git help config` 的 `safe.directory`：Git will refuse to even parse a Git config of a repository owned by someone else）。

**诊断命令与输出**：

```bash
docker run --rm --name learnugroup-09-c8 -v "$PWD":/w debian:13 bash -c 'rm -rf /w/repo; mkdir -p /w/repo && cd /w/repo && git init -q && git -c user.name=t -c user.email=t@t commit -q --allow-empty -m init'
git -C repo status
git -C repo -c safe.directory="$PWD/repo" status
```

在本机执行上述命令的输出：

```text
致命错误：在 '.../repo' 检测到可疑的仓库所有权
...
	git config --global --add safe.directory <仓库绝对路径>
位于分支 master
无文件要提交，干净的工作区
```

**修复**：把仓库属主改为当前用户（`chown -R`）；或按提示把目录加入 `safe.directory`（只对被信任的路径）；不要全局关闭保护。

**如何预防**：容器/CI 里创建仓库时用与使用者一致的 uid；共享仓库用明确的属主/组；不在多用户可写目录里放 `.git`。

#### 案例 9：非 root 绑定 80 端口失败（EACCES，宿主复现）

**现象**：服务以普通用户启动，绑定 80 报 `EACCES`；在容器里同样代码却能绑 80。

**根因**：宿主 `ip_unprivileged_port_start=1024`，绑定 <1024 需要 `CAP_NET_BIND_SERVICE`；容器网络命名空间把该值设为 0，所以容器内普通用户也能绑。

**诊断命令与输出**：

```bash
cat /proc/sys/net/ipv4/ip_unprivileged_port_start
python3 -c 'import socket
s=socket.socket()
try: s.bind(("127.0.0.1",80)); print("host bind 80 OK")
except OSError as e: print("host bind 80 failed:", e.errno, e.strerror)'
docker run --rm --name learnugroup-09-c9 -u 101:101 nginx:1.20-alpine sh -c 'cat /proc/sys/net/ipv4/ip_unprivileged_port_start; nc -l -p 80 >/dev/null 2>&1 & sleep 1; netstat -ltn 2>/dev/null | grep -q ":80 " && echo "bind 80 OK as uid $(id -u)" || echo "bind 80 FAILED"'
```

在本机执行上述命令的输出（第一段宿主，第二段容器内）：

```text
1024
host bind 80 failed: 13 Permission denied
0
bind 80 OK as uid 101
```

**修复**：监听 8080 + 端口转发/反代；或给二进制 `setcap cap_net_bind_service=+ep`；或 systemd `AmbientCapabilities=CAP_NET_BIND_SERVICE`（来源：`man 5 systemd.exec`）。不要用 root 跑整个应用。

**如何预防**：部署设计阶段就决定端口策略；不要把容器内 sysctl 当成宿主事实；用能力而不是 root 解决单点需求。

#### 案例 10：docker.sock 权限不足（未验证负例，给替代验证）

**现象**：`docker ps` 报 `permission denied while trying to connect to the Docker daemon socket`。

**根因**：当前用户对 `/var/run/docker.sock` 没有读/写权限：socket 通常是 `660 root:docker`，用户不在 `docker` 组，或 socket 属组/模式被改过（`man 7 unix`：connect 需要 socket 的 w）。

**诊断命令与输出**：

```bash
ls -ln /var/run/docker.sock
getent group docker
docker ps >/dev/null && echo "docker ok"
```

在本机执行上述命令的输出：

```text
srw-rw---- 1 65534 65534 0 10月11日 09:24 /var/run/docker.sock
docker:x:989:demo
docker ok
```

本机当前用户能访问，**负例未复现**：本会话的 userns 只映射了 uid 1000，无法用 `setpriv` 切到未映射 uid 去触发 EACCES。替代验证：在容器内创建 660 的 unix socket，用不同 uid 连接，观察 `EACCES`（机制与 docker.sock 相同）；或用 `getfacl` 检查 socket 的 ACL。

**修复**：把用户加入 `docker` 组并重新登录（`gpasswd -a user docker`）；不要 `chmod 777 /var/run/docker.sock`；更安全的方案是 rootless 或受控 API。

**如何预防**：`docker` 组按 root 等价审计（[10-账户安全基线与审计](10-账户安全基线与审计.md)）；监控 socket mode 是否被放宽。

#### 案例 11：SSH 公钥登录被拒（未验证，给判定路径）

**现象**：`authorized_keys` 内容正确，sshd 仍拒绝或忽略该 key。

**根因**：sshd 的 `StrictModes` 会检查用户家目录与文件的属主/mode，world-writable 的家目录、他人可写的 `authorized_keys` 会导致拒绝（来源：`man 5 sshd_config` 的 `StrictModes`：check file modes and ownership of the user's files and home directory before accepting login）。

**诊断命令**：`ls -ld ~/.ssh; ls -ln ~/.ssh/authorized_keys; journalctl -u sshd`（或 `/var/log/auth.log`）。应满足 `~/.ssh 700`、`authorized_keys 600`、家目录不 world-writable、属主是登录用户。

**修复**：`chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys; chown -R user:user ~`；检查 `/etc/ssh/sshd_config` 是否设置了 `StrictModes no`（不建议关闭）。

**如何预防**：把家目录/`.ssh` 权限纳入账户基线（[10-账户安全基线与审计](10-账户安全基线与审计.md)）；不要用 `777` 家目录。

本机未复现原因：宿主无 `sshd`，且沙箱里 `/etc/ssh` 配置属主异常；上述判定以 `man 5 sshd_config` 与标准 sshd 行为为准。

#### 案例 12：cron 任务失败（未验证，给判定路径）

**现象**：手动执行成功的脚本，放进 cron 后找不到命令、读不到文件或写日志失败。

**根因**：cron 的任务环境与登录 shell 不同：`PATH`、工作目录、家目录、环境变量与登录 shell 不同；脚本里的相对路径与依赖 `~/.bashrc` 的配置会失效（来源：`man 5 crontab` 对任务环境的说明）。

**诊断命令**：`journalctl -u cron`（或 `/var/log/syslog` 中的 `CRON` 行）；在 crontab 里临时加 `* * * * * id > /tmp/cron-id 2>&1`；用绝对路径调用命令与文件。

**修复**：脚本开头显式设置 `PATH` 与 `cd`；使用绝对路径；需要用户环境时用 `bash -lc` 或登录 shell（取决于 cron 实现）；把输出重定向到文件便于排障。

**如何预防**：cron 脚本最小环境自测；关键任务改用 systemd timer（有明确 `User=`/`Environment=`）。

### 2.4 容器特有问题

| 问题 | 现象 | 定位 | 处理 |
|---|---|---|---|
| uid 不一致 | 容器写宿主目录 EACCES | `ls -ldn` 宿主 vs 容器 `id` | chown、`-u`、`group_add`、命名卷（07 章） |
| 镜像内没有该用户 | `-u 1234` 运行正常但 `$HOME`/`/etc/passwd` 缺项 | `docker run -u 1234 IMAGE id; getent passwd 1234` | 数字 uid 可运行；需要 home/名字时构建镜像时 useradd |
| bind mount 的 `nosuid`/`noexec` | SUID 不生效；脚本报 `Permission denied` | `findmnt -T DIR` 看 `nosuid`/`noexec` | 换挂载点或去掉选项；不要指望 SUID 在 nosuid 挂载生效 |
| 只读挂载 | `Read-only file system` | `findmnt -T DIR`；`touch` 测试 | 去掉 `:ro` 或改写入路径 |
| 容器 root 写的宿主文件 | 宿主属主 root/65534，改不了 | 容器内 `ls -ln` + 宿主 `stat` | 容器清理/chown；见案例 5 |
| userns 显示 65534 | `ls -ln` 显示 nobody | `/proc/self/uid_map`、`uname` | 用容器内数字判断真实属主；见 06 章 |
| docker.sock 权限 | 客户端连不上 daemon | `ls -ln /var/run/docker.sock`、`getent group docker` | 加组/rootless；见案例 10 |
| 容器内 sysctl 与宿主不同 | 容器内能绑 80，宿主不能 | 两边读 `/proc/sys/net/ipv4/ip_unprivileged_port_start` | 以宿主/目标环境为准；见案例 9 |
| `/proc/<pid>/fd` 读不到 | `Permission denied` | 目标进程 `dumpable=0`（如降权后的 nginx worker） | 用日志/`docker logs` 代替；不要为此加 `--privileged` |

### 2.5 本机验证方式与生产环境注意

**本机验证方式**：宿主是受限沙箱（`NoNewPrivs: 1`、`CapEff: 0`、无 sudo/useradd/getcap/strace），所以：

- 「主体侧」实验（切 uid、useradd、setcap、sticky 删除）在 `debian:13`/`alpine` 容器内做；
- 「资源侧」实验（mode/ACL/mount/namei/stat）在宿主自有文件上做；
- docker、curl、python3、git 可用；容器输出在文中标注「容器内」；
- 无法复现的负例（docker.sock 拒绝、sshd、cron、NFS）明确标「未验证」，并给出判定命令或替代验证。

**生产环境注意**：

1. 先看错误码，再改权限；不要用 `chmod -R 777` 掩盖问题。
2. 修「资源侧」优先于「主体侧」：能 chown/ACL 就不要把服务改成 root。
3. 记录每次修复的「谁/什么/规则」三要素，补一条监控或部署检查。
4. 容器场景同时看容器内 uid 与宿主 inode；不要用宿主 65534 当真实属主。
5. 改动 `/etc/sudoers`、SSH、systemd 单元前先备份并保留一个可用会话。
6. LSM/审计（AppArmor、SELinux、auditd）的拒绝不一定出现在应用日志里；dmesg/journalctl/ausearch 要一起看。

### 2.6 配置项 → 权限影响

| 配置项 | 作用 | 权限影响 | 排查提示 |
|---|---|---|---|
| 容器 `user:`/`-u` | 改变容器进程 uid | 决定绑定挂载 inode 的访问资格 | 同时看宿主 inode 属主 |
| 绑定挂载 | 宿主 inode 直通 | 不翻译 uid；`:ro` 变只读 | `findmnt -T`、`ls -ldn` |
| 命名卷 | Docker 管理 inode | 默认 root:root；首次 copy-up 继承镜像属主 | 卷根目录也要 chown |
| `userns-remap`/rootless | 容器 uid → subuid | 宿主看到的属主是 subuid，非当前用户 | 对照 `uid_map`、`ls -n` |
| systemd `User=`/`Group=` | 服务运行身份 | 决定服务对文件的访问 | `systemctl show -p User,Group` |
| systemd `ProtectHome=`/`ProtectSystem=` | 隐藏/只读挂载路径 | 服务看不到 home 或写入被拒 | 查单元文件与 `systemctl show` |
| `NoNewPrivileges=` | 禁止 exec 提权 | SUID/文件 capability 不生效 | 与 `CapabilityBoundingSet=` 一起看 |
| `sshd_config StrictModes` | 检查家目录/文件 mode 与属主 | 权限过宽时拒绝登录 | `ls -ld ~/.ssh; ls -ln ~/.ssh/authorized_keys` |
| `crontab` 环境 | 任务运行环境 | `PATH`/工作目录/变量与登录 shell 不同 | 用绝对路径、显式 `PATH` |
| `git safe.directory` | 允许非本用户属主的仓库 | 未配置时拒绝解析仓库 | 改属主或按需加白名单 |
| 挂载 `nosuid`/`noexec` | 禁用 SUID/执行 | SUID 不生效、脚本执行 EACCES | `findmnt -T` |
| 默认 ACL | 目录新建文件继承 ACL | 子文件获得额外访问条目 | `getfacl -p` 看 default 条目 |

## 四、常见误解

❌ 「`Permission denied` 都是文件 mode 的问题。」 → ✅ 还包括父目录缺 x、ACL mask、只读挂载、LSM；先 `namei -l` 与 `findmnt`（验证：案例 2、9）。

❌ 「`Operation not permitted` 和 `Permission denied` 是一回事。」 → ✅ 前者通常是 `EPERM`（特权/sticky/immutable 等），后者通常是 `EACCES`（DAC）；修法不同（验证：§1.1 的 errno 输出）。

❌ 「`chmod 777` 是万能修复。」 → ✅ 777 不修缺 x 的父目录链之外的规则问题（如 index、LSM、ro 挂载），还会扩大攻击面；应改属主/组/ACL。

❌ 「文件 owner 是 root，普通用户就删不掉。」 → ✅ 删除由父目录 w+x 与 sticky 决定；在可写父目录里可删，在 root 的 755 目录里才删不掉（验证：案例 5）。

❌ 「容器里 root 能写，说明宿主用户也能写。」 → ✅ 容器 root 是宿主 root（默认 rootful），宿主普通用户是另一身份；绑定挂载按宿主 inode 检查（验证：案例 4、5）。

❌ 「用 `sudo` 跑一下服务就能绕过权限问题。」 → ✅ 那只是把服务变成 root，问题与风险都变大；正确做法是改资源属主/ACL 或给最小 capability。

❌ 「`/proc/PID/fd` 总能读到，所以能确认进程打开了什么。」 → ✅ 进程降权后 `dumpable=0`，无 `CAP_SYS_PTRACE` 的 root 同样读不到（验证：08 章 nginx worker fd 的 `Permission denied`）。

❌ 「git 的 dubious ownership 是仓库坏了。」 → ✅ 是属主与当前用户不一致的保护机制；用 `safe.directory` 或改属主，不要删 `.git` 重来（验证：案例 8）。

❌ 「cron 里手动能跑，cron 里也一定能跑。」 → ✅ cron 的 `PATH`/工作目录/环境与登录 shell 不同；用绝对路径与显式环境（来源：`man 5 crontab`，本机未复现）。

## 五、速查表

| 现象 | 命令 | 关键点 |
|---|---|---|
| 打不开文件 | `ls -ln F; namei -l F; stat -c '%a %u:%g' F` | EACCES：文件 r 或父目录 x |
| 进不去目录 | `ls -ldn D; namei -l D` | 缺 x（进入）或 r（列目录） |
| 执行失败 | `ls -ln X; findmnt -T .; head -1 X` | 文件 x、noexec、shebang 解释器 |
| bind 端口失败 | `cat /proc/sys/net/ipv4/ip_unprivileged_port_start; getcap BIN` | <1024 需 CAP_NET_BIND_SERVICE |
| 写日志失败 | `ls -ldn LOGDIR; ls -ln LOGFILE; ps -o uid -p PID` | 目录 w+x 或已打开 fd |
| docker 卷失败 | `ls -ldn HOSTDIR; docker run --rm -v ... id` | 宿主 inode 与容器 uid |
| docker API 失败 | `ls -ln /var/run/docker.sock; getent group docker` | socket 660 root:docker |
| su/sudo 失败 | `id; getent passwd U; passwd -S U; journalctl -u sshd` | 账户锁定/PAM/sudoers |
| ssh key 被拒 | `ls -ld ~/.ssh; ls -ln ~/.ssh/authorized_keys` | StrictModes：700/600 + 属主 |
| git dubious ownership | `git -C D status; git -C D -c safe.directory=D status` | 仓库属主不一致 |
| cron 失败 | `journalctl -u cron`；任务内 `id`/绝对路径 | 环境/工作目录不同 |
| 服务看不到 home | `systemctl show SVC -p ProtectHome,ProtectSystem,User` | systemd 沙箱选项 |
| NFS root 写失败 | `findmnt -T M; grep nfs /proc/mounts` | 服务端 root_squash（未验证） |
| unix socket 502 | `ls -ln SOCK; ss -xlpn; docker logs C` | 连接需 socket w |
| 只读文件系统 | `findmnt -T P; touch P/x` | EROFS，不是 EACCES |
| 权限改完仍失败 | `getfacl; findmnt; getcap; dmesg/journalctl` | ACL mask/ro/cap/LSM |
| 看进程真实身份 | `ps -o pid,uid,euid,suid,args -p PID; grep '^Uid' /proc/PID/status; grep '^CapEff' /proc/PID/status` | shell 的 id 不算 |
| 看路径逐级权限 | `namei -l PATH` | 定位缺 x 的目录 |
| 看 ACL | `getfacl -p PATH` | mask 与 #effective |
| 看挂载选项 | `findmnt -T PATH` | ro/nosuid/noexec |
| 看 capability | `getcap PATH`（容器内） | 文件能力 vs 进程能力 |
| 看 socket | `ss -xlpn; ls -ln SOCK` | 监听者与 socket 权限 |
| 看内核拒绝 | `dmesg; journalctl -k` | LSM/audit，需权限 |
| 清理 root 属主产物 | 一次性容器 `rm -rf` | 不用宿主 sudo 硬删 |
