# 10 账户安全基线与审计

> **一句话总结**：把最小权限原则落到账户、文件、服务三层，并给出可直接运行的只读审计命令。

## 一、先建立直觉

### 1.1 基线：三层各自收紧什么

安全基线的目标不是「让系统不能用」，而是**限制 credential 的数量与可达范围**。落到本课的三层：

| 层次 | 要收紧的东西 | 本章对应 |
|---|---|---|
| 账户层 | uid 0 的数量、可登录账户、密码策略、sudo/docker 组成员 | 2.1 |
| 文件层 | 关键数据库与密钥文件的 mode、SUID/SGID/file capability、world-writable | 2.2、2.3 |
| 服务层 | 服务以哪个用户运行、能拿到哪些 capability、能看/写哪些目录 | 2.5 |

```text
最小权限 = 账户少而窄 × 提权面小 × 关键文件不可写 × 服务降权运行
```

### 1.2 「最小权限」不是一句口号

它在本课可以量化成四个可审计的问题：

1. 有几个 uid 0 的账户？（应只有 `root`）
2. 有多少「普通人执行后会变成 root」的入口？（SUID、file capability、sudo 规则、`docker` 组）
3. 关键文件/目录是否被非特权用户写？（`/etc/passwd`、`/etc/shadow`、`/etc/sudoers`、`~/.ssh`）
4. 服务是否以 root 常驻？能否用 systemd 的 `User=`、`NoNewPrivileges=` 等降下来？

四个问题都有对应的只读命令，且都能在本机或容器跑出真实结果——本章后面逐条给。

### 1.3 这一章在全局模型中的位置

前九章在解释「权限如何工作」，本章是「如何把它收紧到基线」：

```text
       进程凭证（04/05）        资源权限（02/03）        检查规则（04/09）
             │                       │                        │
      少给凭证：非 root、      收紧文件：644/640/440、    减少绕过：
      无多余 cap、NoNewPrivs   去 SUID、去 world-writable  LSM、挂载选项、审计
             └─────────────── 账户/文件/服务基线 ───────────┘
```

图：基线不是新机制，而是把前面章节的每个可调项拨到安全侧，并留下可复查的证据。

### 1.4 审计三问与本章命令索引

| 问题 | 首查命令 | 章节 |
|---|---|---|
| 谁有 uid 0？ | `getent passwd \| awk -F: '$3==0'` | 2.1 |
| 谁能提权？ | SUID/SGID `find`、`getcap -r /`、`getent group sudo docker` | 2.1、2.3 |
| 谁能写关键文件？ | `stat`、world-writable `find`、`ls -ld ~/.ssh` | 2.2 |
| 有没有异常登录？ | `last`、`faillock`、`journalctl` | 2.4 |

### 1.5 本章边界

- 不展开 su/sudo/capability 的机制（[05-提权与降权机制](05-提权与降权机制.md)）。
- 不展开 Docker 的 uid 问题（[07-Docker用户与权限实战](07-Docker用户与权限实战.md)），只在 2.1 点明「docker 组 = root 等价」并链接过去。
- 不写 SELinux/AppArmor 策略（只在 2.4 说明审计入口，排障见 [09-权限排障手册](09-权限排障手册.md)）。
- 本章所有脚本**只读**：不 `chmod`、不 `chattr`、不写系统路径。

## 二、基线与审计

### 2.1 账户基线

#### UID 0 必须唯一

```bash
getent passwd | awk -F: '$3==0{print "uid0:", $1, $7}'
```

容器内输出：

```text
uid0: root /bin/bash
```

本机宿主用同一条命令也只得到 `root`（验证：宿主执行同一命令）。出现第二个 uid 0 账户时，优先怀疑「为了省事复制 root 行」或「后门账户」。

#### 系统账户的 shell 必须是 nologin/false

```bash
getent passwd | awk -F: '$3<1000 && $7 !~ /(nologin|false|sync)$/ {print $1":"$3":"$7}'
```

容器内输出：

```text
root:0:/bin/bash
```

除了 root，服务账户都应落到 `nologin`。容器内系统账户清单（节选）：

```text
daemon:1:/usr/sbin/nologin
bin:2:/usr/sbin/nologin
sys:3:/usr/sbin/nologin
www-data:33:/usr/sbin/nologin
_apt:42:/usr/sbin/nologin
```

注意：`nologin` 只阻止登录，不阻止服务以该 uid 运行（02 章 2.10）；审计时两者要分开看。

#### 密码策略：`login.defs` 给默认值，PAM 负责执行

宿主 `/etc/login.defs`（验证：`grep -E '^(PASS_|ENCRYPT_METHOD)' /etc/login.defs`）：

```text
PASS_MAX_DAYS	99999
PASS_MIN_DAYS	0
PASS_WARN_AGE	7
ENCRYPT_METHOD YESCRYPT
```

`99999` 意味着密码永不过期——生产基线通常会把 `PASS_MAX_DAYS` 收到 90 左右、`PASS_MIN_DAYS` 至少 1。改这里只影响 `chage`/`useradd` 的默认值，**真正拦截弱口令的是 PAM**。

容器内安装 `libpam-pwquality` 后，`/etc/pam.d/common-password` 的密码栈（容器内实测）：

```text
password	requisite			pam_pwquality.so retry=3
password	[success=1 default=ignore]	pam_unix.so obscure use_authtok try_first_pass yescrypt
password	requisite			pam_deny.so
password	required			pam_permit.so
```

`/etc/security/pwquality.conf` 在 Debian 里默认全部注释（容器内 `grep -vE '^\s*#|^\s*$' /etc/security/pwquality.conf` 无输出），内置默认 `minlen=8`——弱口令报错信息就是证据（见下）。

**关键细节：root 代设密码时策略默认不强制。** 容器内以 root 执行 `passwd alice` 并输入 `12345`：

```text
New password: 
BAD PASSWORD: The password is shorter than 8 characters
Retype new password: 
passwd: password updated successfully
```

只打印告警，仍然设置成功。原因在 `man 8 pam_pwquality` 的 `enforce_for_root` 选项（该 man 页由容器内 `libpam-pwquality` 包提供，宿主未安装该包）：

```text
The module will return error on failed check even if the user changing the
password is root. This option is off by default which means that just
the message about the failed check is printed but root can change
the password anyway.
```

而以 alice 自己执行 `passwd` 改密码时，弱口令会被要求重新输入（容器内实测）：

```text
Current password: 
New password: 
BAD PASSWORD: The password is shorter than 8 characters
New password: 
```

紧接着用**旧密码**仍能通过 `Current password:` 校验并成功改成强密码，说明弱口令没有写入。所以基线检查不能只看「common-password 里有 pwquality」，还要确认：

- `enforce_for_root` 是否需要打开（默认关）；
- 实际用非 root 账户走一次改密流程验证；
- root 自己改密码时 root 的密码同样受 `enforce_for_root` 影响。

#### 锁定、过期与空密码账户

`passwd -S` 给账户状态（P 可用/L 锁定/NP 无密码），`chage -l` 给期限，细节见 [02-用户与组数据库](02-用户与组数据库.md) 2.8。审计时只打印用户名、不打印哈希：

```bash
getent shadow | awk -F: '$2==""{print "空密码:",$1} $2 ~ /^[!*]/{print "锁定:",$1}'
```

容器内输出（节选）：

```text
锁定: root
锁定: daemon
...
锁定: bob
```

宿主以普通用户执行 `getent shadow` 无输出、返回码为 0（验证：宿主执行 `getent shadow >/dev/null 2>&1; echo $?` → `0`，但没有任何条目）；容器内以 alice 执行则返回码 2 且无输出（验证：容器内 `su alice -c 'getent shadow alice; echo rc=$?'`）。两者都说明完整审计需要 root。

过期账户的实测（容器内 `chage -E 2020-01-01 expired` 后登录）：

```text
Your account has expired; please contact your system administrator.
su: Authentication failure
```

#### `sudo` 组与 `docker` 组

```bash
getent group sudo
getent group docker
```

宿主输出：

```text
sudo:x:27:demo
docker:x:989:demo
```

`sudo` 组成员能否提权取决于 sudoers 规则（[05-提权与降权机制](05-提权与降权机制.md)）；而 **`docker` 组成员等价于 root**：docker daemon 以 root 运行，能控制 daemon 就能挂载宿主根目录、启动特权容器。宿主 socket 权限：

```text
660 srw-rw---- nobody:nogroup /var/run/docker.sock
```

（宿主以 `stat -c '%a %A %U:%G %n' /var/run/docker.sock` 实测；`nobody:nogroup` 是本会话 userns 的显示映射，真实属主为 `root:docker`，基线 §2。）所以把用户加进 `docker` 组，等于给他一条 root 等价路径——详见 [07-Docker用户与权限实战](07-Docker用户与权限实战.md)；不能把「docker 组」当普通业务组来用。

### 2.2 文件基线

关键文件的目标模式（容器内实测，属主属组完整；宿主受 userns 影响只显示数字）：

| 文件 | 目标模式 | 属主:属组 | 理由 |
|---|---|---|---|
| `/etc/passwd` | 644 | `root:root` | 所有人需读，只有 root 可写 |
| `/etc/shadow` | 640 | `root:shadow` | 哈希只给校验程序（SGID）读 |
| `/etc/group` | 644 | `root:root` | 所有进程需读组信息 |
| `/etc/gshadow` | 640 | `root:shadow` | 组密码/管理员信息 |
| `/etc/sudoers` | 440 | `root:root` | 只读；写入必须走 `visudo` |
| `/etc/sudoers.d` | 755 | `root:root` | 目录本身可读、内容 440 |
| `~/.ssh` | 700 | 用户自己 | 防止他人读私钥/篡改 authorized_keys |
| `~/.ssh/authorized_keys` | 600 | 用户自己 | 同上 |

容器内 `stat` 实测：

```text
644 -rw-r--r-- root:root /etc/passwd
640 -rw-r----- root:shadow /etc/shadow
644 -rw-r--r-- root:root /etc/group
640 -rw-r----- root:shadow /etc/gshadow
440 -r--r----- root:root /etc/sudoers
755 drwxr-xr-x root:root /etc/sudoers.d
```

宿主同一条命令（属主显示为 `nobody:nogroup` 是 userns 映射，模式与目标一致）：

```text
644 -rw-r--r-- nobody:nogroup /etc/passwd
640 -rw-r----- nobody:nogroup /etc/shadow
644 -rw-r--r-- nobody:nogroup /etc/group
640 -rw-r----- nobody:nogroup /etc/gshadow
440 -r--r----- nobody:nogroup /etc/sudoers
```

**SSH 权限为什么必须 700/600？** `sshd` 的 `StrictModes` 默认开启（来源：`man 5 sshd_config`）：

```text
StrictModes
    Specifies whether sshd(8) should check file modes and ownership
    of the user's files and home directory before accepting login.
    ... The default is yes.
```

容器内实测目标与实际：

```text
700 drwx------ root:root /root
700 drwx------ root:root /root/.ssh
600 -rw------- root:root /root/.ssh/authorized_keys
--- 错误模式对照:
644 -rw-r--r-- /root/.ssh/authorized_keys
```

宿主现有账户的 SSH 目录同样符合要求（验证：宿主 `stat -c '%a' ~/.ssh` → `700`；`ls -l ~/.ssh` 显示私钥 `id_ed25519` 为 `600`；本机没有 `authorized_keys`）。

**world-writable 扫描**：关键目录不应出现「其他人可写且无 sticky」。容器内实测为 0 项：

```bash
find / -xdev -type d -perm -0002 ! -perm -1000 2>/dev/null | sort
find / -xdev -type f -perm -0002 2>/dev/null | sort
```

```text
（目录：无输出）
（文件：无输出，计数 0）
```

宿主排除 `/home` 后同样是 0（验证：宿主 `find / -xdev -type d -perm -0002 ! -perm -1000 2>/dev/null | grep -vc '^/home/'` → `0`）。容器内 `/tmp` 与 `/run/lock` 是 1777（带 sticky，允许写但不可互删）：

```text
1777 drwxrwxrwt root:root /tmp
1777 drwxrwxrwt root:root /run/lock
```

注意：本会话沙箱的 `/tmp` 是私有 tmpfs，模式 755（验证：宿主 `stat -c '%a %A' /tmp` → `755 drwxr-xr-x`），`/run/lock` 仍是 1777。不要把沙箱的 `/tmp` 当生产样本。

所以，遇到「基线检查脚本该怎么写」时看这里：先 `stat` 关键文件，再扫 world-writable，最后看 SSH 与 sudoers。

#### file capability 清单

宿主没有 `getcap`（基线 §4），容器内安装 `libcap2-bin` 后可使用。容器内先给一个普通程序副本加 capability，再扫描全盘：

```bash
cp /bin/true /usr/local/bin/capdemo
chmod 755 /usr/local/bin/capdemo
setcap cap_net_bind_service=ep /usr/local/bin/capdemo
getcap /usr/local/bin/capdemo
getcap -r / 2>/dev/null
```

```text
/usr/local/bin/capdemo cap_net_bind_service=ep
--- getcap -r / :
/usr/local/bin/capdemo cap_net_bind_service=ep
--- rc=0
```

`cap_net_bind_service=ep` 是「文件 capability 的 Effective + Permitted 都置位」：程序获得绑定 1024 以下端口的能力，而不是完整的 root。生产基线里 **任何 file capability 都应被解释清楚**（谁装的、为什么、能否用 systemd `AmbientCapabilities` 替代）。生产基线里 **任何 file capability 都应被解释清楚**（谁装的、为什么、能否用 systemd `AmbientCapabilities` 替代）。机制见 [05-提权与降权机制](05-提权与降权机制.md)。

#### 如何判断异常项

| 检查点 | 判断依据 | 命令 |
|---|---|---|
| 是否标准包自带 | `/usr/bin` 下且包管理可查 | `dpkg -S <path>`（Debian） |
| 是否近期被改 | mtime 晚于系统安装时间 | `stat -c '%y %n' <path>` |
| 属主是否 root | 非 root 属主的 SUID 是红旗 | `stat -c '%U:%G' <path>` |
| 是否在非常规路径 | `/tmp`、`/home`、`/dev/shm` 下的 SUID 高度可疑 | `find` 范围 |
| 是否被 `nosuid` 中和 | 挂载选项 | `findmnt -T <path> -o OPTIONS` |

所以，遇到「服务器被扫出 SUID 提权风险」时看这里：先列清单，再逐条用 `dpkg -S` 与 `stat` 证明来源，而不是一刀切删 SUID。

### 2.4 审计与日志

#### 登录记录：`last`、`lastb`、`wtmp/lastlog/btmp`

宿主安装了 `wtmpdb`：`last` 从 `/var/log/wtmp.db` 读取（验证：宿主 `last -n 3` 可输出最近登录；记录数据库文件如下）：

-rw-rw---- 1 nobody nogroup      0 10月11日 10:10 /var/log/btmp
-rw-rw-r-- 1 nobody nogroup 292292 10月11日 13:32 /var/log/lastlog

- 容器内 `last` 因 `/var/log/wtmp.db` 不存在而失败（容器内实测）：`open_database_ro: Cannot open database (/var/log/wtmp.db): unable to open database file`。

`pam_faillock` 模块在宿主存在（`/usr/lib/x86_64-linux-gnu/security/pam_faillock.so`），但 `faillock` 命令行工具未安装（验证：宿主 `command -v faillock` 无输出）；容器内安装 `libpam-modules-bin` 后可用：

```

```

表头为空的含义：该用户当前没有失败记录（且 PAM 里默认**未启用** `pam_faillock`，容器内 `grep -rn pam_faillock /etc/pam.d/` 无配置）。要让它生效，需要在 `common-auth` 中加 `auth required pam_faillock.so`（模块语义见 `man 8 pam_faillock`），这是「配置变更」而不是本章的只读审计范围。

#### systemd journal

宿主 `journalctl` 可用，但普通用户只能看到自己的消息（宿主实测）：

```text
Hint: You are currently not seeing messages from other users and the system.
      Users in groups '4294967295', 'systemd-journal' can see all messages.
```

（`4294967295` 是本会话 userns 的组显示映射；真实组名是 `systemd-journal`。）读取全量认证日志需要把审计用户加入 `adm` 或 `systemd-journal` 组：

```bash

```

#### `ausearch` 与 auditd

本机与容器都**没有** `ausearch`（验证：宿主 `command -v ausearch` 无输出；容器内同）。它属于 auditd 生态，审计规则语法属于 auditd 文档（本机未安装，未验证），典型命令是 `ausearch -m USER_ACCT`。本课未安装 auditd，因此本章不提供 `ausearch` 的真实输出；替代方案是 `last` + `faillock` + `journalctl`，这三者在本机/容器都有可复现输出。

#### 三个可直接运行的只读审计脚本

**脚本 A：账户基线**

```bash
#!/usr/bin/env bash

else
  echo "SKIP: 当前用户读不到 shadow 数据库（需 root）"

getent group sudo
getent group docker
```

### 2.5 服务侧基线

systemd 的 unit 可以在**不修改程序**的情况下限制服务的凭证与可见范围。关键指令（来源：`man 5 systemd.exec`）：

| 指令 | 作用 | 基线建议 |
|---|---|---|
| `User=` / `Group=` | 服务以哪个 uid/gid 运行 | 非必要不用 root |
| `NoNewPrivileges=` | 禁止 execve 获得新凭证（SUID/file caps 失效） | `yes` |
| `CapabilityBoundingSet=` | 限制可持有的 capability 集合 | 按需最小集 |
| `AmbientCapabilities=` | 让非 root 服务保留指定 cap（如绑定低端口） | 只给需要的 |
| `ProtectSystem=` | 只读挂载 `/usr`、`/boot` 等 | `strict`/`full` |
| `ProtectHome=` | 隐藏或只读 `/home`、`/root`、`/run/user` | `yes`/`read-only` |
| `PrivateTmp=` | 独立的 `/tmp`、`/var/tmp` | `yes` |

一个带注释的示例（**仅示意，本机未应用**）：

```ini
[Service]
User=svcapp
Group=svcapp
NoNewPrivileges=yes
CapabilityBoundingSet=
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/var/lib/svcapp
```

宿主上可以直接检查某个服务的「暴露面」评分（测试了 `ssh.service`，只读）：

```bash
systemd-analyze security --no-pager ssh.service | head -8
```

```text
  NAME                                                        DESCRIPTION                                                             EXPOSURE
✗ RootDirectory=/RootImage=                                   Service runs within the host's root directory                                0.1
  SupplementaryGroups=                                        Service runs as root, option does not matter                            
  RemoveIPC=                                                  Service runs as root, option does not apply                             
✗ User=/DynamicUser=                                          Service runs as root user                                                    0.4
✗ CapabilityBoundingSet=~CAP_SYS_TIME                         Service processes may change the system clock                                0.2
✗ NoNewPrivileges=                                            Service processes may acquire new privileges                                 0.2
✓ AmbientCapabilities=                                        Service process does not receive ambient capabilities                   
```

评分不是「必须满分」——`ssh` 需要 root 来切换用户，`User=` 一项必然扣分。基线读法是：**逐项看带 ✗ 的行，判断该服务是否真的需要这项能力**，需要就接受并记录，不需要就收紧。

### 2.6 落地顺序与例外管理

基线不是一次性脚本，而是「盘点 → 定基线 → 小步收紧 → 验证 → 记录例外」的循环：

| 步骤 | 做什么 | 验证 |
|---|---|---|
| 1. 盘点 | 跑 2.4 的三个脚本，保存输出 | 输出与本文档对应段落比对 |
| 2. 定基线 | 关键文件模式、UID 0、SUID 白名单、密码策略 | 每项写成「文件/命令 + 期望值」 |
| 3. 小步改 | 一次只改一类，先测试环境 | 改完重跑脚本 |
| 4. 验证业务 | 登录、SSH、服务重启、`passwd` 是否正常 | 真实登录 + `journalctl` |
| 5. 记录例外 | 某 SUID 必须保留、某服务必须 root | 写清原因与补偿措施 |

破坏性最大的四类改动，必须先在测试机验证：

1. 改 `~/.ssh` 或 `authorized_keys` 权限：错了直接锁死 SSH（`StrictModes`）。
2. 改 `/etc/shadow` 属主属组：`passwd`/`su` 立刻不可用（SGID 辅助程序读不到）。
3. 去掉 SUID：`mount`/`su`/`passwd` 等系统工具失效。
4. 改 `PASS_MAX_DAYS`：所有用户被要求改密码，配合弱口令策略会引发大面积登录失败（在用户必须改密时）。

## 三、动手验证

### 3.1 宿主上可跑的命令（只读）

```bash
getent passwd | awk -F: '$3==0{print $1}'
getent passwd | awk -F: '$3<1000 && $7 !~ /(nologin|false|sync)$/ {print $1":"$3":"$7}'
stat -c '%a %A %U:%G %n' /etc/passwd /etc/shadow /etc/group /etc/gshadow /etc/sudoers 2>&1
find / -xdev -type f -perm -4000 2>/dev/null | grep -v '^/home/' | sort
find / -xdev -type f -perm -2000 2>/dev/null | grep -v '^/home/' | sort
find / -xdev -type f -perm -0002 2>/dev/null | grep -vc '^/home/'
find / -xdev -type d -perm -0002 ! -perm -1000 2>/dev/null | grep -vc '^/home/'
stat -c '%a %A %n' /tmp /run/lock
stat -c '%a %U:%G %n' ~/.ssh 2>/dev/null
last -n 3
systemd-analyze security --no-pager ssh.service | head -8
```

每条要看什么：

- 第 1 条：只有 `root` 才正常。
- 第 2 条：除 `root` 外的系统账户应全是 `nologin`。
- 第 3 条：`640` 与 `root:shadow` 是 shadow/gshadow 的正确形态；宿主显示 `nobody:nogroup` 是 userns 映射。
- 第 4、5 条：清单应有已知解释；出现 `/home`、`/tmp`、`/dev/shm` 下的条目要重点查。
- 第 6、7 条：排除 `/home` 后应为 0；`/tmp` 本身是 1777（sticky 允许）。
- `last` 与 `systemd-analyze` 提供登录与暴露面证据。

### 3.2 容器内补齐 `getcap` 与完整 shadow 审计

> 需要：docker / 网络（apt 装 libcap2-bin、libpam-modules-bin、acl）

```bash
docker run --rm --name learnugroup-10-$$ -v "$PWD":/w debian:13 bash -c '
  set -e
  export DEBIAN_FRONTEND=noninteractive
  apt-get update -qq >/dev/null 2>&1

  find / -xdev -type f -perm -4000 2>/dev/null | sort
  echo "== SGID =="
  find / -xdev -type f -perm -2000 2>/dev/null | sort

  cp /bin/true /usr/local/bin/capdemo && chmod 755 /usr/local/bin/capdemo
  setcap cap_net_bind_service=ep /usr/local/bin/capdemo

  echo "== shadow 审计（只打印用户名） =="
  getent shadow | awk -F: '\''$2==""{print "空密码:",$1} $2 ~ /^[!*]/{print "锁定:",$1}'\''
  echo "== faillock =="

  echo "== last =="

```

在容器内要看的点：

- SUID 数量与清单是否与 2.3 一致（本机为 10 条）；多出来的项要能解释。

- `faillock` 的空表与 `last` 的失败信息，说明容器内没有登录历史数据库。

## 四、常见误解

1. ❌ 只做密码策略就安全了 → ✅ 密码只是账户层的一项；uid 0 数量、SUID/capability、sudo/docker 组、文件模式都要审计（本章 2.1–2.3）。
2. ❌ 删掉所有 SUID 就安全了 → ✅ `mount/su/passwd` 等依赖 SUID，删了会让系统不可用；正确做法是白名单 + 解释每个 SUID 的来源（2.3「如何判断异常项」）。
3. ❌ `docker` 组只是普通组 → ✅ 组成员可通过 daemon 获得 root 等价能力，宿主 `docker.sock` 为 660 `root:docker`（2.1）；应视同 sudo 权限管理（详见 [07-Docker用户与权限实战](07-Docker用户与权限实战.md)）。
4. ❌ 把 root 账户禁用/改名就安全了 → ✅ 提权路径还有 SUID、file capability、sudo 规则、`docker` 组、容器逃逸；只处理账户名不改变这些入口（2.3）。
5. ❌ 配了 `pam_pwquality` 弱口令就进不来 → ✅ `enforce_for_root` 默认关闭，root 代设密码只告警不拦截（容器内实测，2.1）；且策略是否生效要以非 root 账户实际改密验证。
6. ❌ `/etc/shadow` 640 已足够，改不改属组无所谓 → ✅ 640 的读权限依赖 `shadow` 组；把属组改错会让 `passwd`/`su` 立刻失效（2.6「破坏性最大的四类改动」）。
7. ❌ 基线配一次就一劳永逸 → ✅ 新装软件会带来新 SUID/capability，人员变动会带来新组成员；2.4 的脚本应周期运行并 diff 历史输出（2.6 的循环）。
8. ❌ 装了 auditd 就自动有审计日志 → ✅ 需要写审计规则（属 auditd 文档，本机未安装）；本机未装 auditd，`ausearch` 不可用，本章不提供伪造输出（2.4）。

## 五、速查表

| 检查项 | 命令 | 期望/结论 |
|---|---|---|
| uid 0 账户 | `getent passwd \| awk -F: '$3==0'` | 只有 root |
| 可登录系统账户 | `getent passwd \| awk -F: '$3<1000 && $7 !~ /nologin/'` | 只有 root |
| 空密码/锁定账户 | `getent shadow \| awk -F: '$2=="" \|\| $2 ~ /^[!*]/'` | 需 root；只打印用户名 |
| 账户库模式 | `stat -c '%a %U:%G %n' /etc/passwd /etc/shadow` | 644 / 640 root:shadow |
| sudo 规则文件 | `stat -c '%a %U:%G' /etc/sudoers /etc/sudoers.d` | 440 / 755 |
| SUID 清单 | `find / -xdev -type f -perm -4000` | 白名单，逐项解释 |
| SGID 清单 | `find / -xdev -type f -perm -2000` | 关注 SGID shadow 等 |
| file capability | `getcap -r /` | 生产应为空或有解释 |
| world-writable 目录 | `find / -xdev -type d -perm -0002 ! -perm -1000` | 应为空（/tmp 是 1777 带 sticky） |
| 孤儿文件 | `find / -xdev \( -nouser -o -nogroup \)` | 清理或重新归属 |
| SSH 目录 | `stat -c '%a %U:%G' ~/.ssh ~/.ssh/authorized_keys` | 700 / 600 |
| 密码策略默认值 | `grep -E '^PASS_' /etc/login.defs` | 按组织策略收紧 |
| PAM 密码质量 | `grep pwquality /etc/pam.d/common-password` | 有配置 ≠ 已强制（root 例外） |
| 失败登录计数 | `faillock --user <user>` | 需安装 libpam-modules-bin 并启用 PAM |
| 最近登录 | `last -n 20` | 异常时间/来源要追 |
| 认证日志 | `journalctl -u ssh -n 20` | 需 adm/systemd-journal 组 |
| 服务暴露面 | `systemd-analyze security <unit>` | 逐项处理 ✗ |
| 服务降权 | `systemctl cat <unit>` + `User=`/`NoNewPrivileges=` | 非必要不用 root |
